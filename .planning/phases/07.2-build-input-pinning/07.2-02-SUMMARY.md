# Phase 7.2 Plan 02: Kernel pinned to 6.12.96 Summary

**The kernel is now installed from six digest-pinned debs instead of resolved by apt: the four unpinnable meta packages are stripped from the upstream firmware sub-stage, a new index-00 run script installs 6.12.96 before anything can resolve a kernel, and three independent gates — the pre-build digest check, an in-chroot exact-set assertion, and a post-build rootfs assertion — each fail loudly if a second kernel ever appears.**

## What was actually proven, and how

### The six digests were re-fetched, not transcribed — three independent sources agree

The plan's table was treated as an expected result, not a source. All six were fetched
twice (once on the arm64 build host, once from the Mac driving the manifest's own `url`
fields) and cross-checked against the archive's own published `SHA256:` fields in
`dists/bookworm/main/binary-arm64/Packages.gz`.

```
OK  linux-image-6.12.96+rpt-rpi-2712_...deb     (32734444 B)
OK  linux-image-6.12.96+rpt-rpi-v8_...deb       (32739088 B)
OK  linux-headers-6.12.96+rpt-rpi-2712_...deb    (1347420 B)
OK  linux-headers-6.12.96+rpt-rpi-v8_...deb      (1347400 B)
OK  linux-headers-6.12.96+rpt-common-rpi_...deb  (8771560 B)
OK  linux-kbuild-6.12.96+rpt_...deb              (1193816 B)
```

All three sources match on every digest and every byte count. Total 78,133,728 B.

### The corrected premise, measured

The index `Packages.gz` is 46,701 lines and carries **eleven** versioned
`linux-image-*-rpt-rpi-2712` packages, 6.12.19 through 6.12.109 — including 6.12.96. What
carries exactly one version is the meta package:

```
Package: linux-headers-rpi-2712
Version: 1:6.12.109-1+rpt1
```

That is why the metas are removed rather than pinned, and it is not the reason for the pool
fetch. The refuted inflection appears in no shipped file.

### The safety premise re-checked, with a negative control

```
Depends|Pre-Depends|Recommends naming the four metas:  0 hits
same grep shape against a package that IS depended on:  2 hits (raspi-firmware)
the four meta packages exist in this index:             4 stanzas
```

The zero is a measurement, not a grep pointed at the wrong file or a pattern that can never
match. Nothing in the Pi archive depends on the four meta packages.

### Ordering and the silent-skip hazard, confirmed against upstream source

`run_sub_stage` in pi-gen at `PIGEN_REF` loops `for i in {00..99}` and completes every
handler at one index before the next, so `00-run.sh` runs before `01-packages`. It guards
with `[ -x ${i}-run.sh ]` — a non-executable run script is skipped with no log line at all.
Applied to a pristine clone, the mode lands exactly:

```
755 /tmp/pg3/stage0/02-firmware/00-run.sh     -> EXECUTABLE (run_sub_stage will run it)
644 /tmp/pg3/stage0/02-firmware/01-packages
```

`on_chroot` is `export -f`'d by pi-gen's `scripts/common`, so the run script can call it.

Also confirmed: upstream's own `02-firmware/02-run.sh` (which sets `update_initramfs=no` and
`do_symlinks=0`) runs *after* the kernel install in both the upstream and the overlaid
ordering, so installing at index 00 does not change its relationship to the kernel packages.

### The kernel install is what apt actually receives

pi-gen strips comments from package lists with `scripts/remove-comments.sed`, so the header
comment cannot leak into apt. Measured on the overlaid tree:

```
what pi-gen passes to apt:   initramfs-tools raspi-firmware
any linux-* in that string:  rc=1 (none)
```

The apt command rendered into the chroot:

```
cd /tmp/arlowe-kernel
apt-get -o Acquire::Retries=3 install -y --no-install-recommends ./*.deb
```

The `./` prefix is present via `cd` + `./*.deb`, so apt reads local files rather than
package names.

### The in-chroot exact-set assertion has teeth — negative-controlled

The rendered chroot assertion was extracted and run against fabricated module trees:

| `/lib/modules` contents | rc |
|---|---|
| exactly the two pinned flavours | **0** |
| plus `6.12.109+rpt-rpi-2712` | **1** |
| missing `6.12.96+rpt-rpi-v8` | **1** |

The middle row is the exact failure this phase exists to prevent. `IMG_KVER` selection was
confirmed in the real tree at `stage-arlowe/01-runtime/00-run-chroot.sh:193`:

```
find /lib/modules -maxdepth 1 -name '*-rpi-2712' -printf '%f\n' | sort -V | tail -1
```

`tail -1` on a version sort — so a second kernel is silently preferred, which is why the
assertion is exact-set rather than existence-only.

## Deviations from Plan

### 1. [Rule 2 — missing critical] `third_party/kernel/*.deb` was not gitignored

`INSTALL.md` names `third_party/kernel/` as a staging location and the search order looks
there, but no ignore rule existed — `git check-ignore` returned rc=1. A builder following
the documentation could commit 75 MiB of debs. `third_party/axcl/*.deb` and
`third_party/node/*.tar.xz` both have rules for exactly this reason.

Fixed by adding the rule, which also makes the doc's "never committed" claim true rather
than aspirational. Found by verifying the claim instead of writing it. **Commit:** `d9941d9`.

### 2. [Rule 2 — missing critical] The plan's meta-package grep matches its own required comment

The plan asks for a header comment on `01-packages` "naming `third_party/kernel/manifest.yml`
as where the kernel now comes from", and the file must explain *which* packages were removed
to be useful. It then verifies with:

```
grep -E 'linux-(image|headers)-rpi-(v8|2712)' .../01-packages   # expect rc=1
```

Those two requirements are contradictory: the explanatory comment names the packages, so the
grep returns rc=0 against correct code. This is wave 1's deviation 2 inverted — there a grep
was satisfied by a comment and passed while measuring nothing; here one is tripped by a
comment and fails while measuring nothing.

**Resolved by measuring the load-bearing fact instead of the file's raw text.** Two stronger
assertions replace it, both run:

```
active (non-comment) lines naming a meta package:  rc=1
what remove-comments.sed hands apt, grepped for linux-:  rc=1
```

The second is the real one: it measures the string pi-gen actually passes to `apt-get`. The
comment was kept — a reader of `01-packages` who cannot tell what was removed or why is the
person who re-adds it. The durable runtime guard is the rootfs exact-set assertion, which is
immune to comments entirely.

### 3. [Rule 1 — bug] `shellcheck -S warning` would have passed while CI fails

Both the plan and wave 1 verify with `shellcheck -S warning`. CI (`.github/workflows/pr-checks.yml`)
runs plain `shellcheck` at **default severity**, which includes `info`. My three
`printf '%s\n' ${VAR}` word-splits are SC2086 (info): invisible to the plan's check, fatal to CI.

Fixed in the code, not by loosening the check — `printf '%s\n' "$VAR" | sed 's/^/  /'` and
`tr '\n' ' '`. Verified by reproducing CI's exact multi-file invocation, which is also how
the pre-existing SC1091 findings resolve (passing all files together lets shellcheck follow
`source`), so CI is clean rather than clean-modulo-known-noise.

**This is the generalisable finding: a verification weaker than the gate it stands in for is
a green check that measures less than it appears to.**

### 4. [Rule 2 — missing critical] `00-run.sh` needs the manifest, and the plan forwards only the cache

The plan requires the six filenames and version strings be derived from
`third_party/kernel/manifest.yml` ("two copies of a version number is how a pin
half-applies") but specifies forwarding only `ARLOWE_KERNEL_CACHE` across the `sudo`
boundary. `00-run.sh` executes inside the pi-gen tree with no reliable path back to the repo,
so as specified it could only have hardcoded the values.

Added `ARLOWE_KERNEL_MANIFEST` to the export and to the `sudo` variable list, with a hard
failure when unset. Deriving from the cache directory's contents was rejected: it would
accept whatever happens to be in the directory, which is a check that measures nothing.

### 5. [Rule 2 — missing critical] A stale cache pointer would outlive a failed verification

Not specified either way by the plan. `build/.arlowe-kernel-cache` is forwarded into the
chroot installer, so a pointer left behind after a failed run names a directory containing a
deb that just failed its digest check. Check 7 now removes the file on any failure path, and
`build-image.sh` hard-fails when it is absent.

### 6. [Addition] The in-chroot assertion is exact-set, and both diagnostics distinguish direction

The plan's step 5 asks only that both module directories exist. Existence-only cannot see the
failure that actually breaks the build — a *third* directory. Made it an exact-set comparison
in the chroot as well as in `build-image.sh`, so the failure is caught in stage0 rather than
25 minutes later.

A first draft printed "More than the pinned set means..." for the missing case too, which
would have misdirected whoever read it. Both directions are now named. Caught by running the
negative control rather than by reading the code.

### 7. [Judgement call] ROADMAP SC1's false premise was left in place

`ROADMAP.md:263` still carries the refuted claim. It is tempting to fix, but
`07.2-04-PLAN.md:177` **explicitly assigns** that correction to plan 04, which also greps the
repo to prove the claim survives nowhere. Editing it here would silently satisfy another
plan's success criterion.

One related fix was made: the manifest's own warning against the claim quoted the forbidden
phrase verbatim, so a repo-wide relapse grep would have flagged the warning as the relapse.
Reworded. **Commit:** `2c47ceb`.

### `overlays/**/*.sh` is deliberately NOT in CI's shellcheck globs

Checked whether to add it. Wave 1's two overlay run scripts are near-verbatim upstream pi-gen
code and carry upstream's own SC2086/SC2001 findings; adding the glob would force divergence
from upstream beyond the minimal change the overlay design exists to preserve. The new
`00-run.sh` is our own file and is shellcheck-clean at default severity, verified manually.
If plan 03 or 04 wants overlay linting, it needs a per-file allowlist, not a glob.

### Dropping the v8 flavour would halve this pin

Per the plan: plausible for a Pi-5-only device, since `linux-image-rpi-v8` is Pi 4 (bcm2711).
It would remove three of the six debs and ~34 MiB. Deliberately not done — changing what the
image ships is a different decision from pinning what it already ships, and it belongs to a
scope conversation, not to this phase.

### Unproven until plan 04

Nothing here has run inside a real pi-gen build; plan 04 owns the single build. What is
established: the debs are correct and verified from three sources, the overlay applies to a
pristine clone with the modes pi-gen requires, the apt command is well-formed, the
host-side logic of `00-run.sh` works against a real cache with a stubbed `on_chroot`, and
the exact-set assertion fails on the precise scenario that broke the build. What remains
unknown is whether any later stage re-adds a kernel — which is exactly what the
`build-image.sh` rootfs gate is positioned to catch.

**SC1 is met.** SC6 stays open until the axcl module compiles against 6.12.96 in plan 04.
