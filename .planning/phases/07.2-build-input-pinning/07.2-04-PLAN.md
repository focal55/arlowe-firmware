<execution_notes>
**The build work dir MUST be destroyed before this build. This is the single highest-risk item in the plan.**
Verified on the arm64 build host: `build/pi-gen-work/{stage0,stage1,stage2,stage-arlowe}/rootfs` all exist right now, `stage0/rootfs/lib/modules` carries `6.12.109+rpt-rpi-2712` and `6.12.109+rpt-rpi-v8`, and `stage2/rootfs/usr/src` carries `linux-headers-6.12.109+rpt-{common-rpi,rpi-2712,rpi-v8}` plus `linux-kbuild-6.12.109+rpt`.

pi-gen guards every expensive step on the rootfs already existing: `stage0/prerun.sh` wraps bootstrap in `[ ! -d "${ROOTFS_DIR}" ]`, and `stage1`/`stage-arlowe` guard `copy_previous` the same way. `build-image.sh` only `mkdir -p`s the work dir and never cleans it. So a build against the existing tree would:
1. Skip debootstrap entirely, defeating the Debian snapshot pin — the base system would stay whatever it rolled to.
2. Install the pinned 6.12.96 debs into a tree that already carries 6.12.109. Because — per plan 02's own central argument — these are differently-NAMED packages, apt has no reason to remove the old ones. BOTH remain.
3. Hit `00-run-chroot.sh:193`, which picks `IMG_KVER` with `find /lib/modules -name '*-rpi-2712' | sort -V | tail -1`. That selects 6.12.109. The axcl compile then fails at `ax_pcie_dev_host.c:220` again, roughly 25 minutes in, and the log reads exactly like "the pin did not work" when in fact the pin was never given a clean tree.

That failure would be indistinguishable from a real defect in plans 01-03 and would burn a gap-closure cycle chasing nothing. Task 1 step 1 is the removal, and it is a step, not a note.

This plan runs on the arm64 build host, not the Mac — `build-image.sh` requires loop devices and privileged mounts that Docker Desktop on macOS cannot provide, and the script says so in its header.

The build host has no GitHub credentials. Do NOT plan or attempt a `git pull` there. Sync the branch to it by rsync from the development machine before building, and sync any generated artifacts back the same way. Refer to the host by role in anything that gets committed; `scripts/sanitize/check.sh` fails on the hostname literal and neither `docs/operations/` nor `.planning/` content should acquire the habit even where allow-listed.

The build is ~30+ minutes. `ARLOWE_KERNEL_FETCH=1` adds ~78 MiB of downloads on the first run only. `AXCL_DEB` must point at the axcl 3.10.2 deb or the pipeline's dependency verification fails immediately — check that before starting a 30-minute run, not after.
</execution_notes>

**`docs/operations/phase-07.2-build-pinning.md`** — the runbook whose absence is how a pin rots. Cover, concretely:
- Where each pin lives: kernel (`third_party/kernel/manifest.yml`), Debian snapshot (the timestamp in `overlays/pi-gen/stage0/...`, in two files — `sources.list` and `prerun.sh` — which must be changed together), pi-gen (`PIGEN_REF` in `build-image.sh`), axcl / node / ax-llm (existing manifests).
- **Bumping the kernel:** fetch the new debs from the pool, record digests, update the manifest, AND re-verify the axcl compile. A kernel bump is never just a number — that is the entire lesson of issue #137. Say so in one line at the top of that section.
- **Why the Pi side uses pool URL plus checksum, stated correctly.** Do NOT write "the Pi archive index carries only the newest version" — it is false; the index carries 6.12.19 through 6.12.109 including every version pinned here. What carries exactly one version is the META package, which is why the meta packages are removed rather than pinned. The three actual reasons for pool-plus-checksum are: the digest is the pin, the local cache makes a rebuild independent of the archive, and there is no Raspberry Pi snapshot service. The thing that can change and therefore the thing to watch is pool RETENTION of 6.12.96.
- **Bumping `PIGEN_REF`:** the overlay's `upstream_sha256` assertions will fail by design — **on the re-clone path**. Say that explicitly: on a cached pi-gen tree the applier sees its own prior output (`overlay_sha256`) and accepts it, so an ordinary build does not re-check upstream. The alarm is a `PIGEN_REF`-bump alarm, not a per-build one, and an operator who expects otherwise will misread its silence as reassurance. The correct response is to re-read each upstream file, decide whether our change still makes sense against the new upstream content, and re-record. Explicitly: do not delete the assertion, and do not blindly re-record without reading. Name the failure message the operator will see.
- **Bumping the Debian snapshot:** both overlay files, then re-run the resolve-twice check, then expect and accept an input manifest diff via `ARLOWE_INPUTS_ACCEPT=1`.
- **Reading an input manifest diff:** what a `pkg` row change means versus a `pin` row change, and that a `pin` change with no corresponding manifest edit means someone tampered with a cache.
- The pool-retention caveat: `archive.raspberrypi.com` retains old debs today (6.12.19 through 6.12.109 at time of writing) but does not guarantee to. Mirror the six pinned debs somewhere the project controls.

**ADR-0009** — extend the record written in plan 01 with what the build actually showed: the SC6 result, the reference manifest's package count, and any surprise. If the build produced no surprises, say that explicitly; an ADR that only records the plan and never the outcome is how the next person learns nothing.

Three corrections that must land in the ADR text and not only here:
- The Pi-side mechanism rationale, stated as above. The false version ("the index carries only the newest version") must not appear.
- The `upstream_sha256` alarm fires on the re-clone path only.
- Record the stale-work-dir hazard as a build-procedure consequence of the prevent-don't-downgrade design: because the pinned and unpinned kernels are differently-named packages, an unclean work dir leaves both installed and `IMG_KVER` selects the newer one. Anyone re-running this build needs that on the page, not in a plan file that stops being read once the phase closes.
