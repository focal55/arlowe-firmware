<execution_notes>
This plan runs on the arm64 build host, not the Mac — `build-image.sh` requires loop devices and privileged mounts that Docker Desktop on macOS cannot provide, and the script says so in its header.

The build host has no GitHub credentials. Do NOT plan or attempt a `git pull` there. Sync the branch to it by rsync from the development machine before building, and sync any generated artifacts back the same way. Refer to the host by role in anything that gets committed; `scripts/sanitize/check.sh` fails on the hostname literal and neither `docs/operations/` nor `.planning/` content should acquire the habit even where allow-listed.

The build is ~30+ minutes. `ARLOWE_KERNEL_FETCH=1` adds ~78 MiB of downloads on the first run only. `AXCL_DEB` must point at the axcl 3.10.2 deb or step 1 fails immediately — check that before starting a 30-minute run, not after.
</execution_notes>

After the build, gather this evidence from the build log and the rootfs and quote it verbatim into the SUMMARY:

1. **The kernel install happened and nothing was resolved.** The `stage0/02-firmware/00-run.sh` section of the log shows the six pinned debs installed by file path. 3. **The axcl module compiled — SC6.** Locate the `.ko` in the rootfs and record its path and `modinfo` output, specifically the `vermagic`, which must name `6.12.96+rpt-rpi-2712`. `00-run-chroot.sh` tolerates an axcl postinst failure only when the `.ko` was actually built and treats a missing `.ko` as a real failure, so a clean build plus a present `.ko` with the right vermagic is the SC6 evidence. Quote the `ax_pcie_dev_host.c` region of the log too: last time it carried `error: too few arguments to function 'pci_resize_resource'` and this run must not.

**`docs/operations/phase-07.2-build-pinning.md`** — the runbook whose absence is how a pin rots. Cover, concretely:
- Where each pin lives: kernel (`third_party/kernel/manifest.yml`), Debian snapshot (the timestamp in `pi-gen/overlay/stage0/...`, in two files — `sources.list` and `prerun.sh` — which must be changed together), pi-gen (`PIGEN_REF` in `build-image.sh`), axcl / node / ax-llm (existing manifests).
- **Bumping the kernel:** fetch the new debs from the pool, record digests, update the manifest, AND re-verify the axcl compile. A kernel bump is never just a number — that is the entire lesson of issue #137. Say so in one line at the top of that section.
- **Bumping `PIGEN_REF`:** the overlay's `upstream_sha256` assertions will fail by design. The correct response is to re-read each upstream file, decide whether our change still makes sense against the new upstream content, and re-record. Explicitly: do not delete the assertion, and do not blindly re-record without reading. Name the failure message the operator will see.
- **Bumping the Debian snapshot:** both overlay files, then re-run the resolve-twice check, then expect and accept an input manifest diff via `ARLOWE_INPUTS_ACCEPT=1`.
- **Reading an input manifest diff:** what a `pkg` row change means versus a `pin` row change, and that a `pin` change with no corresponding manifest edit means someone tampered with a cache.
- The pool-retention caveat: `archive.raspberrypi.com` retains old debs today (6.12.19 through 6.12.109 at time of writing) but does not guarantee to. Mirror the six pinned debs somewhere the project controls.

**ADR-0009** — extend the record written in plan 01 with what the build actually showed: the SC6 result, the reference manifest's package count, and any surprise. If the build produced no surprises, say that explicitly; an ADR that only records the plan and never the outcome is how the next person learns nothing.

  <how-to-verify>
1. Read the SUMMARY's quoted evidence for the five task-1 checks. The one to read hardest is check 1 — zero hits on `linux-image-rpi-2712` and friends in the build log. That is the difference between "the pin worked" and "the pin was a no-op and 6.12.96 happened to be installed alongside whatever apt chose".
2. Read `modinfo`'s `vermagic` on the axcl `.ko`. It must say `6.12.96+rpt-rpi-2712`. A `.ko` built against a different vermagic will refuse to load on the device and this phase would have shipped a second silent failure.
3. Skim `docs/operations/phase-07.2-inputs.reference`. The `pin` rows should match the manifests; the `pkg` rows should look like a plausible bookworm package set.
4. Decide on the two open judgements recorded in the SUMMARY:
   - **Drop the `rpi-v8` kernel flavour?** The device is Pi 5 only. Keeping v8 costs ~32 MiB of image and doubles the kernel pin surface. It was kept deliberately so that this phase reproduces the known-good rootfs rather than changing what ships. Follow-up phase, or leave as is?
   - **Snapshot timestamp advance policy.** `20260915T000000Z` is fixed until someone moves it. Does this get a scheduled bump, or does it move only when a security update forces it? A pin nobody ever advances becomes an unpatched image.
5. Confirm Phase 7.1 SC6 should now proceed to its hardware checkpoint — this phase proves the driver COMPILES; it does not prove the device boots and loads it, which is 7.1's remaining work.
