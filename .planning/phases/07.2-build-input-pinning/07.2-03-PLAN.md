<design_decisions>

**`SOURCE_DATE_EPOCH` needs a consumer that can fail, or it is another paper requirement.**
Exporting the variable and declaring victory is exactly the state this phase is correcting. pi-gen itself references it nowhere (`grep -rn SOURCE_DATE_EPOCH` over the whole provisioned pi-gen tree returns only our own comment). So this plan gives it one specific, falsifiable consumer: a clamp over arlowe-authored rootfs content, plus an assertion that the clamp worked. "No file under `/opt/arlowe` has an mtime greater than `SOURCE_DATE_EPOCH`" is a claim a test can disprove; "the variable is exported" is not.

The clamp is deliberately scoped to arlowe-authored paths (`/opt/arlowe`, `/etc/systemd/system/arlowe-*`), NOT the whole rootfs. Clamping Debian-installed files would fight dpkg, break nothing visibly, and make the assertion meaningless because most of the rootfs is not ours to date. Honest narrow scope beats broad theatre.

**Derived from the commit, and the dirty-tree case is a WARN not a FAIL.**
`SOURCE_DATE_EPOCH="$(git -C "${REPO_ROOT}" log -1 --format=%ct)"`. If the worktree has uncommitted changes to tracked files, the epoch no longer identifies what is being built — warn loudly and record the dirty state in the manifest. Failing outright would make every iterative build on the build host impossible, which is a worse outcome than a labelled inaccuracy.

**Pin versus record — a distinction this phase must not blur.**
`third_party/*/manifest.yml` and the snapshot timestamp are PINS: inputs we chose. The input manifest is a RECORD: an observation of everything that resolved, roughly 400 Debian packages we did not individually choose. SC5 asks for "a recorded manifest that a gate diffs", not for 400 hand-maintained pins — that is what snapshot.debian.org exists to make unnecessary. So the manifest covers everything resolved; the pins cover only what we control; the gate diffs the record.

**Where the reference manifest comes from.**
`scripts/record-build-inputs.sh` writes `build/arlowe-inputs.manifest` (gitignored). `docs/operations/phase-07.2-inputs.reference` is the committed baseline. This plan ships the recorder and the differ; the reference itself is produced by plan 04's single real build and committed there. That ordering is not bureaucracy: a reference generated by anything other than a real build would be a guess, and a guess in the baseline is worse than no baseline.

`ARLOWE_INPUTS_ACCEPT=1` re-records the reference for a deliberate pin bump. It must print what changed before writing, so accepting a diff is a decision rather than a reflex.

**SC5's evidence is a double resolve, not a double build.**
A full build is ~30 minutes; two would be an hour to observe one bit. The claim under test is "two builds from the same commit RESOLVE an identical set of package versions", and resolution is separable from installation. `tests/phase-07.2/resolve-twice.sh` runs `apt-get install --print-uris -y --no-install-recommends <the declared set>` twice in a bookworm arm64 container against the snapshot and the pinned kernel filenames, and asserts the two sorted outputs are byte-identical. That is the direct evidence. The recorded manifest and its gate are the durable mechanism that keeps it true; plan 04's real build is what proves the mechanism describes reality.

CI already has an `ubuntu-24.04-arm` runner in use by the `unit-import-bookworm` job, so this costs a job, not new infrastructure.

**Record what happened, not what was intended.**
Every field in the manifest that describes the BUILD must be read from the built rootfs, never from the declaration that was supposed to produce it. Specifically `debian_snapshot`: reading it out of `overlays/pi-gen/.../sources.list` records the timestamp we asked for, and a manifest that asserts a snapshot the rootfs never came from is F7 #18 reproduced inside this phase — and frozen as the committed authority, which is worse than not recording it. Read it from `${ROOTFS}/etc/apt/sources.list`, and hard-fail if that file does not name a snapshot at all.

The `pin` rows are the exception and they are genuinely declarations: they record what we chose, and `build-image.sh` separately gates that the rootfs matches. `pigen_ref` is also a declaration; label it as such in the header comment so the distinction is on the page and not just in someone's head.

**A green result from a broken probe is the failure mode this phase exists to kill, so probes assert their own health.**
`apt-get update` exits 0 even when every index fetch failed TLS verification — measured in a stock arm64 `debian:bookworm` container, which ships no `ca-certificates`. A `--print-uris` run against that state resolves nothing, and two empty sorted lists compare byte-identical. `resolve-twice.sh` would report `IDENTICAL` and the job whose only purpose is to notice drift would be passing hardest precisely when it is blind. Plan 01 addresses the cause (`http://` in the overlay); this plan addresses the class, independently, by making the probe assert it measured something before it compares anything.

**Manifest determinism is the whole point, so sort everything.**
`dpkg-query -W -f='${Package}\t${Version}\t${Architecture}\n'` over the rootfs, piped through `LC_ALL=C sort`. Any unsorted or timestamped field makes the diff gate fire on noise and it will be switched off within a week.
</design_decisions>

  <name>Task 2: Write the input manifest recorder and diff gate</name>
  <files>scripts/record-build-inputs.sh, tests/phase-07.2/test-record-build-inputs.sh, scripts/build-image.sh</files>
  <action>
**`scripts/record-build-inputs.sh`** with two modes:

    record-build-inputs.sh --rootfs DIR --out FILE
    record-build-inputs.sh --diff FILE --reference FILE

The manifest is plain text, deterministic, with a small keyed header followed by a sorted package table:

    # arlowe build inputs manifest v1
    source_date_epoch<TAB>...
    worktree_clean<TAB>true|false
    pigen_ref<TAB>2026-06-18-raspios-bookworm-arm64
    debian_snapshot<TAB>20260915T000000Z
    kernel_version<TAB>6.12.96
    pin<TAB>third_party/kernel/<filename><TAB><sha256>     # one line per pinned deb
    pin<TAB>third_party/node/<filename><TAB><sha256>
    pin<TAB>third_party/axcl/<filename><TAB><sha256>
    pin<TAB>third_party/ax-llm<TAB><commit>
    pkg<TAB><name><TAB><version><TAB><arch>                # sorted LC_ALL=C

Read every value from its source of truth, and be strict about which values have the ROOTFS as their source of truth rather than a declaration:
- **Hard-fail on zero `pkg` rows.** `dpkg-query --admindir <dir with an empty status file> -W` exits **0** with no output, so an unreadable or empty admindir yields a zero-package manifest at exit 0. The determinism probe and the self-test would catch that; plan 04 would not — it hits the "no reference yet" warn, continues, and commits the empty result as the permanent baseline every later diff compares against. The plan's own rule that an unpinned rootfs must not be silently blessed as the reference applies just as much to an empty one.
- `debian_snapshot` — parse it out of `${ROOTFS}/etc/apt/sources.list`. **Never** out of `overlays/pi-gen/stage0/00-configure-apt/files/sources.list`. The overlay is what we asked for; the rootfs is what we got. If the rootfs sources.list names no snapshot, hard-fail rather than recording an empty or defaulted value — an unpinned rootfs must not be silently blessed as the reference baseline.
- `kernel_version` — derive from the module directories under `${ROOTFS}/lib/modules`, not from `third_party/kernel/manifest.yml`.
- `source_date_epoch`, `worktree_clean` — from the build environment.
- `pigen_ref` and the `pin` rows — these ARE declarations (what we chose), read from `build-image.sh` and `third_party/*/manifest.yml`. Say so in the manifest header comment so the observed/declared split is on the page.

Never read a value from a second hardcoded copy. `pkg` rows come from `dpkg-query --admindir "${ROOTFS}/var/lib/dpkg" -W -f='${Package}\t${Version}\t${Architecture}\n'` piped through `LC_ALL=C sort`. Emit `LF` only, no trailing whitespace, no timestamps beyond the epoch field.

Note the rootfs needs root to read in places; mirror how `build-image.sh` already uses `sudo` for `du` and the substrate gates, and say why in a comment.

`--diff` prints a unified diff and exits 1 when the manifests differ, exits 0 when identical, and exits 2 when the reference file does not exist (distinct from "differs" — the first build has no baseline and that is not a failure). Under `ARLOWE_INPUTS_ACCEPT=1`, print the diff, then overwrite the reference, then exit 0.

**`tests/phase-07.2/test-record-build-inputs.sh`** — fixture-based, no real rootfs and no network.

Build a fixture ROOTFS, not just a dpkg admindir. The recorder reads three things out of the rootfs, so a fixture that supplies only one exercises only one: a fake dpkg admindir holding at least three packages, an `etc/apt/sources.list` naming a snapshot, and a `lib/modules/<version>` directory. Support a `--emit-fixture` mode that builds the fixture, prints its path on stdout and exits 0 — the determinism probe in `<verify>` runs against it, because `--rootfs /` is a rootfs this recorder is specified to REJECT (see the note there).

Assert, each as a named case:
- Two recordings over the fixture are byte-identical, and the `pkg` table is non-empty — check the floor BEFORE the comparison, since two empty manifests compare identical.
- `pkg` rows are `LC_ALL=C`-sorted.
- The recorded `debian_snapshot` equals the fixture's `etc/apt/sources.list` value and is not any overlay value.
- A fixture whose `etc/apt/sources.list` is EMPTY, or which carries only deb822 `sources.list.d/*.sources`, makes the recorder exit non-zero. This is not a hypothetical edge: the arm64 build host's own `/etc/apt/sources.list` is 0 bytes because trixie moved to deb822, so this is the case most likely to be hit for real.
- `--diff` returns 1 with a readable diff on a one-version change, 0 on identity, and 2 on a missing reference.

**build-image.sh** — after the kernel-version assertion from plan 02, call the recorder against `${PIGEN_ROOTFS}` writing `build/arlowe-inputs.manifest`, then `--diff` it against `docs/operations/phase-07.2-inputs.reference`. Exit 2 (no reference yet) is a `warn` and continues; exit 1 is a `fail` that aborts with the diff printed and a line telling the operator that `ARLOWE_INPUTS_ACCEPT=1` re-records a deliberate bump. Place this before the image is partitioned — an input drift should cost a rootfs build, not a full partition-and-image cycle, the same reasoning the substrate gates are placed on.

3. Twice, with a deliberate pause between the runs so a same-second cache cannot manufacture a false pass: `apt-get install --print-uris -y --no-install-recommends` over the union of `pi-gen/stage-arlowe/00-packages/00-packages-nr` and `overlays/pi-gen/stage0/02-firmware/01-packages`, plus `initramfs-tools`. If it ever equals 6.12.96, the drift that caused this phase has reversed and someone should be told rather than left to assume the pin is doing the work.

This test needs the Pi archive source too (for the madison check), so add `raspi.list` and the Pi archive key from `pi-gen/stage0/00-configure-apt/files/` — note those live in the provisioned pi-gen tree, which is NOT in git. Fetch the key from the Raspberry Pi archive at `http://archive.raspberrypi.com/debian/raspberrypi.gpg.key` instead, and say why in a comment.
