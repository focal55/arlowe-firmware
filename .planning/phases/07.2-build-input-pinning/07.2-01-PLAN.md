<objective>
Build the mechanism that makes every later pin in this phase survive pi-gen's re-clone, and use it to land the first real pin: the Debian snapshot.

Purpose: `scripts/build-image.sh` re-clones upstream pi-gen at `PIGEN_REF` and restores only `config` and `stage-arlowe`. Three upstream files carry unpinned build inputs (`stage0/prerun.sh`'s debootstrap mirror, `stage0/00-configure-apt/files/sources.list`, and `stage0/02-firmware/01-packages`). Editing them in place is erased on the next re-clone — and, worse, erased silently. SC4 is the hardest criterion in this phase precisely because a pin that stops applying without saying so is the F7 #18 shape. This plan builds the loud version once so plans 02 and 03 only have to add content.

Output: a tracked `pi-gen/overlay/` tree, an applier that asserts four distinct failure modes, and Debian package resolution pinned to snapshot timestamp `20260915T000000Z`.
</objective>

<design_decisions>
Resolved here so the executor does not have to re-litigate them. Every claim below was verified on the arm64 build host, not inferred.

**Why a whole-file overlay and not a `sed` patch step.**
A `sed -i` against upstream text is a silent no-op the day upstream's text changes — the same defect class this phase exists to close. A whole-file copy plus a digest assertion cannot no-op: either the bytes are there or the build stops.

**Why the MANIFEST records the UPSTREAM digest too.**
The failure this design is really guarding is not "the copy failed" (rare) but "someone bumped `PIGEN_REF` and the upstream file now means something different, and our overlay quietly reverted their change" (likely, and invisible). Recording `upstream_sha256` turns a `PIGEN_REF` bump into a build failure that names the file and demands a human re-read it. That is the loudness the brief asks for, chosen over elegance.

**Why apt version pinning is NOT used for the Pi archive (context for plan 02).**
`apt-cache madison linux-headers-rpi-2712` returns exactly one line, `1:6.12.109-1+rpt1`. The Pi archive index carries only the newest version, so an apt preferences pin to 6.12.96 has no candidate to select. Verified against `http://archive.raspberrypi.com/debian/dists/bookworm/main/binary-arm64/Packages.gz`. The overlay is therefore load-bearing for the kernel, not a stylistic choice.

**Snapshot timestamp: `20260915T000000Z`.**
Verified reachable, HTTP 200 after redirect, for all three suites:
- `https://snapshot.debian.org/archive/debian/20260915T000000Z/dists/bookworm/Release`
- `https://snapshot.debian.org/archive/debian/20260915T000000Z/dists/bookworm-updates/Release`
- `https://snapshot.debian.org/archive/debian-security/20260915T000000Z/dists/bookworm-security/Release`
Note the `debian-security` suite lives under a DIFFERENT archive root (`archive/debian-security/`), not under `archive/debian/`. Getting that wrong yields a 404 at `apt-get update`, mid-bootstrap.
Chosen as mid-September 2026 because the known-good reference rootfs — the flashed card carrying `6.12.96+rpt-rpi-2712` — was built in the September rebuild. A snapshot from that window reproduces the closest thing to a rootfs already proven to boot.

**`Acquire::Check-Valid-Until "false"` is mandatory, not hygiene.**
A snapshot's `Release` file carries a `Valid-Until` in the past by construction. Without this apt.conf entry the build works today and fails roughly a week from now with `Release file ... is not valid yet` / `expired`, which reads like a network fault rather than a pinning consequence. Ship it with the snapshot, in the same commit, or the pin has a fuse on it.

**`prerun.sh` must stay executable.**
pi-gen's `run_stage` guards with `if [ -x prerun.sh ]`, and `run_sub_stage` guards `NN-run.sh` with `if [ -x ${i}-run.sh ]`. An overlay entry that lands without its exec bit is skipped in total silence — pi-gen logs nothing at all for a non-executable run script. The MANIFEST therefore records a mode per entry and the applier asserts it after copying. This is the fourth failure mode and the least obvious one.

**Scope boundary.** This plan pins the Debian side only. The Raspberry Pi archive has no snapshot service (`snapshot.raspberrypi.com` and `snapshot.raspberrypi.org` both return HTTP 000 from the build host) and is handled by pool-URL-plus-checksum in plan 02. Splitting them is deliberate: different mechanism, different blast radius, and a snapshot outage should not be indistinguishable from a kernel hash mismatch.
</design_decisions>

  <name>Task 1: Write the overlay applier and its MANIFEST format</name>
  <files>scripts/lib/pigen-overlay.sh, pi-gen/overlay/MANIFEST</files>
  <action>
Create `scripts/lib/pigen-overlay.sh` exporting one function, `apply_pigen_overlay <pi_gen_dir> <overlay_dir>`. It must be sourceable (no top-level side effects) and pass `shellcheck -S warning`.

MANIFEST format — one record per entry, tab-separated, comments on `#` lines:

    path<TAB>mode<TAB>upstream_sha256<TAB>overlay_sha256

`upstream_sha256` is the literal string `NEW` when the entry has no upstream counterpart. `path` is relative to the pi-gen root.

The applier processes each record and hard-fails (return 1, message names the path) on any of these four conditions:

1. **Upstream drift.** `upstream_sha256` is not `NEW` and the file at `<pi_gen_dir>/<path>` either does not exist or does not hash to `upstream_sha256`. Message must say the upstream file changed under the pin, name `PIGEN_REF`, and instruct the operator to re-read the upstream file and re-record the digest — NOT to delete the check.
2. **Unexpected pre-existing file.** `upstream_sha256` is `NEW` but the file already exists upstream. Upstream grew a file we intended to add; a blind overwrite would hide that.
3. **Copy did not land.** After copying, the installed file does not hash to `overlay_sha256`.
4. **Mode did not land.** After copying, the installed file's `stat -c %a` does not equal `mode`.

Order matters: check 1/2 BEFORE copying, 3/4 after. Copy with `install -m "${mode}" -D`.

The function prints one `[OK]` line per applied entry and a final count, matching the `[OK]`/`[FAIL]` visual grammar already used by `scripts/verify-third-party.sh` and `scripts/build-image.sh`.

Populate MANIFEST with the four plan-01 entries. Compute `upstream_sha256` from a pristine clone at the pinned ref — do NOT read it from the working pi-gen tree on the build host, which may already be dirty:

    git clone --quiet --branch 2026-06-18-raspios-bookworm-arm64 --depth 1 \
      https://github.com/RPi-Distro/pi-gen.git /tmp/pigen-pristine

Entries and their modes:
- `stage0/prerun.sh` — mode `755`, upstream digest recorded
- `stage0/00-configure-apt/00-run.sh` — mode `755`, upstream digest recorded
- `stage0/00-configure-apt/files/sources.list` — mode `644`, upstream digest recorded
- `stage0/00-configure-apt/files/99arlowe-pinned` — mode `644`, `NEW`

Do not reference the build host's hostname or any founder path anywhere in these files — `scripts/sanitize/check.sh` fails the build on those literals and `scripts/` is not allow-listed. Say "the arm64 build host".
  </action>
  <verify>
    shellcheck -S warning scripts/lib/pigen-overlay.sh

    wc -l < pi-gen/overlay/MANIFEST                                              # expect: >= 4 records
  </verify>
  <done>shellcheck is clean, MANIFEST holds exactly four non-comment records each with four tab-separated fields, and every recorded upstream digest was computed from a pristine clone at the pinned ref.</done>

**build-image.sh.** Source `scripts/lib/pigen-overlay.sh` alongside the existing library sources near the top. Then call `apply_pigen_overlay "${PI_GEN_DIR}" "${REPO_ROOT}/pi-gen/overlay"` immediately AFTER the `if [[ -f "${PIGEN_MARKER}" ... ]] ... fi` block closes — outside both branches. This placement is the whole point: the cached-pi-gen branch currently short-circuits to `ok "pi-gen pinned at ..."` and does no work, so an overlay applied only inside the clone branch would stop applying the moment a build reuses a cached tree, which is the common case. Abort the build with a `fail` line if the applier returns non-zero.

Note for the executor: the clone branch does `cp -a "${PI_GEN_DIR}/config"` and `stage-arlowe` into the temp tree. Do NOT add `overlay` to that copy list — `pi-gen/overlay/` is a source directory that lives in the repo and is read from `${REPO_ROOT}`, never from inside the provisioned pi-gen tree. Copying it in would create a second stale copy that drifts.

**tests/phase-07.2/test-pigen-overlay.sh.** A self-contained bash test. Build a throwaway fixture tree (not a real pi-gen clone — the test must run in CI without network) containing files matching the MANIFEST's recorded upstream digests, then assert, each as a named case:
1. Happy path: applier returns 0 and every target file hashes to its `overlay_sha256`.
2. Upstream drift: append a byte to one upstream fixture file; applier returns non-zero and its stderr names that path.
3. NEW collision: pre-create `stage0/00-configure-apt/files/99arlowe-pinned` in the fixture; applier returns non-zero.
4. Mode assertion: after a successful apply, `stat -c %a` on `stage0/prerun.sh` equals `755`.
5. Idempotence: a second consecutive apply on the already-applied tree returns 0 — the upstream-digest check must be written so it does not mistake our own overlay for upstream drift. (Read this carefully: after the first apply, `stage0/prerun.sh` hashes to `overlay_sha256`, not `upstream_sha256`. The applier must accept EITHER digest and fail only on a third, unknown value. Getting this wrong makes every second build fail.)

Each case prints `[PASS]`/`[FAIL]` with its name; the script exits non-zero if any failed.

**ADR-0009.** Record: the problem (three unpinned inputs in upstream-owned files, erased every build); the overlay mechanism and its four assertions; why `sed`-patching and apt version pinning were rejected, with the madison evidence; the snapshot timestamp and why mid-September 2026; the `Check-Valid-Until` consequence; and the explicit scope boundary that image-hash equality remains out of scope per the existing Phase 6 ADR — only input reproducibility is gated. Reference the build host by role ("the arm64 build host"), never by hostname.
