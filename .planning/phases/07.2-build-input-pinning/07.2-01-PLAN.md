<objective>
Build the mechanism that makes every later pin in this phase survive pi-gen's re-clone, and use it to land the first real pin: the Debian snapshot.

Purpose: `scripts/build-image.sh` re-clones upstream pi-gen at `PIGEN_REF` and restores only `config` and `stage-arlowe`. Three upstream files carry unpinned build inputs (`stage0/prerun.sh`'s debootstrap mirror, `stage0/00-configure-apt/files/sources.list`, and `stage0/02-firmware/01-packages`). Editing them in place is erased on the next re-clone — and, worse, erased silently. SC4 is the hardest criterion in this phase precisely because a pin that stops applying without saying so is the F7 #18 shape. This plan builds the loud version once so plans 02 and 03 only have to add content.

Output: a tracked `overlays/pi-gen/` tree, an applier that asserts four distinct failure modes, Debian package resolution pinned to snapshot timestamp `20260915T000000Z`, and a post-build check that the built rootfs actually used it.
</objective>

<design_decisions>
Resolved here so the executor does not have to re-litigate them. Every claim below was verified on the arm64 build host, not inferred.

**The overlay lives at `overlays/pi-gen/` in the repo root — NOT under `pi-gen/`.**
This is not cosmetic and it is not negotiable. Two independent facts make `pi-gen/overlay/` unusable:
1. `.gitignore:81` is `/pi-gen/*` with only `!/pi-gen/config` and `!/pi-gen/stage-arlowe` re-included. `git add pi-gen/overlay` is a silent no-op — `git check-ignore -v pi-gen/overlay/MANIFEST` confirms it. The PR would carry zero overlay files, CI would check out a tree without them, and every "diff under 400 lines" gate would pass *because the deliverable is invisible*. A green gate measuring nothing is the exact defect this phase exists to eliminate.
2. `scripts/build-image.sh:93` is `sudo rm -rf "${PI_GEN_DIR}"` on the re-provision path, and `PI_GEN_DIR="${REPO_ROOT}/pi-gen"`. Anything under it is destroyed, two lines before `apply_pigen_overlay` would try to read it.

`overlays/pi-gen/` clears both in one move: it is outside the ignore rule and outside the `rm -rf` blast radius. Every task below carries a `git ls-files overlays/pi-gen | wc -l` check with an expected count, so an invisible deliverable fails loudly instead of passing quietly.

**Why a whole-file overlay and not a `sed` patch step.**
A `sed -i` against upstream text is a silent no-op the day upstream's text changes — the same defect class this phase exists to close. A whole-file copy plus a digest assertion cannot no-op: either the bytes are there or the build stops.

**Why the MANIFEST records the UPSTREAM digest too.**
The failure this design is really guarding is not "the copy failed" (rare) but "someone bumped `PIGEN_REF` and the upstream file now means something different, and our overlay quietly reverted their change" (likely, and invisible). Recording `upstream_sha256` turns a `PIGEN_REF` bump into a build failure that names the file and demands a human re-read it.

Be precise about when that alarm can fire: the upstream digest is only meaningful on a tree that was freshly cloned at `PIGEN_REF`. On the cached path the tree already carries our overlay, so the applier sees `overlay_sha256` and must accept it. The alarm is a re-clone-path alarm, and the ADR must say so rather than implying every build re-checks upstream.

**Snapshot access is over `http://`, deliberately.**
Measured in a native arm64 `debian:bookworm` container: that base image ships no `ca-certificates`, so every `https://snapshot.debian.org` index fetch fails TLS verification — and `apt-get update` still **exits 0**. Downstream, plan 03's `resolve-twice.sh` would then compare two empty lists, find them byte-identical, and report `IDENTICAL`. The job whose only purpose is to notice drift passes hardest when it is broken. Over `http://` all 12 index files fetch and `--print-uris` resolves real pool URLs.

Inside the real pi-gen build the https form would probably work, since `bootstrap()` passes `--include=ca-certificates` — which is the worst of both worlds: survivable in one environment and silently broken in the other. Use `http://` everywhere. Content authenticity comes from the gpg signature on `Release`/`InRelease`, not from the transport, and http is snapshot.debian.org's documented usage.

**Snapshot timestamp: `20260915T000000Z`.**
Verified reachable, HTTP 200 after redirect, for all three suites:
- `http://snapshot.debian.org/archive/debian/20260915T000000Z/dists/bookworm/Release`
- `http://snapshot.debian.org/archive/debian/20260915T000000Z/dists/bookworm-updates/Release`
- `http://snapshot.debian.org/archive/debian-security/20260915T000000Z/dists/bookworm-security/Release`
Note the `debian-security` suite lives under a DIFFERENT archive root (`archive/debian-security/`), not under `archive/debian/`. Getting that wrong yields a 404 at `apt-get update`, mid-bootstrap.
Chosen as mid-September 2026 because the known-good reference rootfs — the flashed card carrying `6.12.96+rpt-rpi-2712` — was built in the September rebuild. A snapshot from that window reproduces the closest thing to a rootfs already proven to boot.

**`Acquire::Check-Valid-Until "false"` is mandatory, not hygiene.**
A snapshot's `Release` file carries a `Valid-Until` in the past by construction. Without this apt.conf entry the build works today and fails roughly a week from now with `Release file ... is not valid yet` / `expired`, which reads like a network fault rather than a pinning consequence. Ship it with the snapshot, in the same commit, or the pin has a fuse on it.

**`prerun.sh` must stay executable.**
pi-gen's `run_stage` guards with `if [ -x prerun.sh ]`, and `run_sub_stage` guards `NN-run.sh` with `if [ -x ${i}-run.sh ]`. An overlay entry that lands without its exec bit is skipped in total silence — pi-gen logs nothing at all for a non-executable run script. The MANIFEST therefore records a mode per entry and the applier asserts it after copying. This is the fourth failure mode and the least obvious one.

**Observe the snapshot in the built rootfs; do not re-read the declaration.**
Reading the timestamp back out of `overlays/pi-gen/.../sources.list` proves only that we wrote what we wrote. The rootfs is where it either happened or did not. Task 3 therefore asserts over `${PIGEN_ROOTFS}`: its `/etc/apt/sources.list` names the snapshot, its `/var/lib/apt/lists/` filenames name `snapshot.debian.org`, and **no** list file names `deb.debian.org`. That last one is the real check — a rolling-mirror list file present means base packages resolved from somewhere other than the pin.

**Scope boundary.** This plan pins the Debian side only. The Raspberry Pi archive has no snapshot service (`snapshot.raspberrypi.com` and `snapshot.raspberrypi.org` both return HTTP 000 from the build host) and is handled by pool-URL-plus-checksum in plan 02. Splitting them is deliberate: different mechanism, different blast radius, and a snapshot outage should not be indistinguishable from a kernel hash mismatch.
</design_decisions>

  <name>Task 1: Write the overlay applier and its MANIFEST format</name>
  <files>scripts/lib/pigen-overlay.sh, overlays/pi-gen/MANIFEST</files>
  <action>
Create `scripts/lib/pigen-overlay.sh` exporting one function, `apply_pigen_overlay <pi_gen_dir> <overlay_dir>`. It must be sourceable (no top-level side effects) and pass `shellcheck -S warning`.

MANIFEST format — one record per entry, tab-separated, comments on `#` lines:

    path<TAB>mode<TAB>upstream_sha256<TAB>overlay_sha256

`upstream_sha256` is the literal string `NEW` when the entry has no upstream counterpart. `path` is relative to the pi-gen root.

The applier processes each record and hard-fails (return 1, message names the path) on any of these four conditions. **Read rules 1 and 2 carefully — both must tolerate an already-applied tree, because that is the normal path, not an edge case.** The build host's pi-gen tree persists across builds, so every build after the first overlays a tree that already carries our files.

1. **Upstream drift.** `upstream_sha256` is not `NEW`, and the file at `<pi_gen_dir>/<path>` either does not exist or hashes to **neither** `upstream_sha256` (pristine clone) **nor** `overlay_sha256` (already applied by a previous build). A third, unknown digest is the failure. Message must say the upstream file changed under the pin, name `PIGEN_REF`, and instruct the operator to re-read the upstream file and re-record the digest — NOT to delete the check.
2. **Unexpected pre-existing file.** `upstream_sha256` is `NEW`, the file already exists, and it does **not** hash to `overlay_sha256`. That means upstream grew a file we intended to add, and a blind overwrite would hide it. A file that hashes to `overlay_sha256` is our own prior apply and is fine.
3. **Copy did not land.** After copying, the installed file does not hash to `overlay_sha256`.
4. **Mode did not land.** After copying, the installed file's `stat -c %a` does not equal `mode`.

Order matters: check 1/2 BEFORE copying, 3/4 after. Copy with `install -m "${mode}" -D`.

The function prints one `[OK]` line per applied entry and a final count, matching the `[OK]`/`[FAIL]` visual grammar already used by `scripts/verify-third-party.sh` and `scripts/build-image.sh`.

When iterating MANIFEST records, skip blanks and comments with an unambiguous guard. Do not use `[ -z "$p" ] || [ "${p#\#}" != "$p" ] && continue` — it is correct only by accident of `&&`/`||` precedence and reads as its opposite. Use:

    case "$p" in ''|'#'*) continue;; esac

Populate MANIFEST with the four plan-01 entries. Compute `upstream_sha256` from a pristine clone at the pinned ref — do NOT read it from the working pi-gen tree on the build host, which is already dirty:

    git clone --quiet --branch 2026-06-18-raspios-bookworm-arm64 --depth 1 \
      https://github.com/RPi-Distro/pi-gen.git /tmp/pigen-pristine

Entries and their modes:
- `stage0/prerun.sh` — mode `755`, upstream digest recorded
- `stage0/00-configure-apt/00-run.sh` — mode `755`, upstream digest recorded
- `stage0/00-configure-apt/files/sources.list` — mode `644`, upstream digest recorded
- `stage0/00-configure-apt/files/99arlowe-pinned` — mode `644`, `NEW`

Do not reference the build host's hostname or any founder path anywhere in these files — `scripts/sanitize/check.sh` fails the build on those literals and `scripts/` is not allow-listed. Say "the arm64 build host".
