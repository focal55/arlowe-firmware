<design_decisions>
Resolved here. Every claim was verified against the live Pi archive from the arm64 build host; do not re-derive, but do re-run the checksums.

**Prevent, do not downgrade.** The overlay strips the four meta packages from `stage0/02-firmware/01-packages` and a new `stage0/02-firmware/00-run.sh` installs the six pinned debs first. No apt decision ever selects a kernel version, so there is nothing to downgrade and no window in which the wrong one exists.

Installing 6.12.109 and downgrading afterwards was rejected: it leaves `linux-headers-6.12.109+rpt-common-rpi` in `/usr/src`, which is exactly the header the axcl postinst would find. A half-downgraded kernel in the rootfs is worse than either endpoint, as the brief says.

**Why pool URL plus checksum — stated correctly.**
An earlier draft justified this mechanism with "the Pi archive index carries only the newest version". That is FALSE and must not be repeated in the manifest header, in ADR-0009, or in the runbook. `dists/bookworm/main/binary-arm64/Packages.gz` carries the versioned packages for 6.12.19 through 6.12.109, including all six pinned here. What carries exactly one version is the **meta** package: `apt-cache madison linux-headers-rpi-2712` returns one line, `1:6.12.109-1+rpt1`. That is why the four meta packages must be REMOVED from `01-packages` — there is no older candidate to pin them to — but it is not why we fetch by pool URL.

The three real reasons, and the ones that belong in the manifest header:
1. **Digest pinning.** The manifest's sha256 is the pin. An index entry is whatever the archive serves today; a recorded digest is a claim that can be falsified.
2. **Offline cache.** The six debs land in a local cache, so a rebuild does not depend on the archive being reachable or on what it still carries.
3. **No Pi snapshot service.** `snapshot.raspberrypi.com` and `snapshot.raspberrypi.org` both return HTTP 000 from the build host, so the Debian-side mechanism is unavailable here.

The thing that can actually change — and therefore the only thing worth a positive control — is pool/index RETENTION of 6.12.96, not the imaginary claim that the index never had it. Plan 03's control is written against this corrected premise.

**Removing the meta packages is safe, and this was checked rather than assumed.** Parsing `http://archive.raspberrypi.com/debian/dists/bookworm/main/binary-arm64/Packages.gz` (46,701 lines) for any `Depends`, `Pre-Depends` or `Recommends` naming `linux-image-rpi-2712`, `linux-image-rpi-v8`, `linux-headers-rpi-2712` or `linux-headers-rpi-v8` returns **zero results**. Nothing in the entire Pi archive depends on them. Re-run that check in task 3 — if it ever returns a hit, this design is wrong and the build must stop rather than proceed.

**Why 00-run.sh runs early enough.** pi-gen's `run_sub_stage` loops `for i in {00..99}` and, within each index, handles `NN-debconf`, `NN-packages-nr`, `NN-packages`, `NN-patches`, `NN-run.sh`, `NN-run-chroot.sh` in that order. Index `00` is fully processed before index `01`, so `02-firmware/00-run.sh` runs before `02-firmware/01-packages`. It must be mode 755 — `run_sub_stage` guards with `if [ -x ${i}-run.sh ]` and skips a non-executable script with no log line at all. Plan 01's applier asserts the mode; that assertion is what makes this safe.

**The pin is loud by construction, which is the best property of this design.** `linux-image-6.12.96+rpt-rpi-2712` is a distinct PACKAGE NAME, not a version constraint on `linux-image-rpi-2712`. apt cannot upgrade a package to a differently-named one, so no later `apt-get install` or `dist-upgrade` can drift it. (There is exactly one `dist-upgrade` in the whole stage list, at `stage0/00-configure-apt/00-run.sh`, and it runs before this install.) The only way to change the kernel is to edit the manifest, which changes a sha256, which the gate asserts.

**Install with `apt-get install ./file.deb`, not `dpkg -i`.** The pinned debs have real dependencies that are NOT in the six-deb set: `kmod`, `linux-base`, `initramfs-tools` (from `linux-image-*`) and `libc6`, `libelf1`, `libssl3` (from `linux-kbuild`). `dpkg -i` cannot resolve those and leaves the chroot half-configured. apt with a local file path resolves them from the (now snapshot-pinned) Debian archive. `initramfs-tools` remaining in `01-packages` is harmless — apt will already have pulled it in as a dependency.

**All six debs, both flavours.** Upstream requests v8 (Pi 4, bcm2711) and 2712 (Pi 5) images and headers; `linux-headers-*-common-rpi` is `_all` and shared; `linux-kbuild` is required by both headers packages. Pinning only 2712 would leave `linux-headers-rpi-v8` resolving to 6.12.109 and dragging `linux-headers-6.12.109+rpt-common-rpi` back into `/usr/src` — reintroducing the exact header that broke the compile. Dropping the v8 flavour entirely is plausible for a Pi-5-only device and would halve the pin, but changing what ships is not this phase's business; record it as a follow-up in the SUMMARY.

**Pool retention is a fetch source, not an archive.** The pool currently retains 6.12.19 through 6.12.109, but that is Raspberry Pi's retention policy and not a guarantee. The manifest's `url` is how to obtain the deb the first time; the sha256 is the pin, and the local cache is what makes a rebuild independent of the pool. `INSTALL.md` must say so plainly and document mirroring the six debs somewhere durable.

**Verified pool URLs and digests** (all six fetched complete from `http://archive.raspberrypi.com/debian/pool/main/l/linux/`, version `6.12.96-1+rpt1`, kernel string `6.12.96+rpt`):
