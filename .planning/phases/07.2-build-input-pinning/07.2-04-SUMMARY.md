# Phase 7.2 Plan 04: The one full build Summary

**The kernel pin works: one full build against a destroyed work dir produced a rootfs carrying exactly 6.12.96 in both flavours with zero kernel meta packages resolved, and the axcl driver — whose compile failure is the reason this phase exists — built five `.ko` files with `vermagic: 6.12.96+rpt-rpi-2712`. All six phase criteria are met. The build then aborted, after every one of them was satisfied, on a Phase 7.1 gate that reads the build host's systemd units instead of the rootfs's — so no `.img` was emitted and the hardware checkpoint cannot run yet.**

**A correction to this plan's own verify block.** It instructs a post-build

It is the exact trap the plan's own comment warns about one paragraph earlier, with the guard placed one condition short. The honest evidence is the in-build gate line above (29 files observed, 0 off-pin), not the post-hoc `ls`. I measured it both ways and am reporting the one that means something.

## Deviations from Plan

### 1. [Rule 3 — Blocking] `scripts/build-image.sh` was tracked non-executable

**Found during:** Task 1, launching the build.
**Issue:** the file has been mode `100644` since at least `178c377` (Phase 6). The host had run it before only because its working copy carried a stray local exec bit; resetting to the recorded mode reverted that and the launch failed with `nohup: failed to run command ... Permission denied`. A fresh checkout or CI could never have run the documented invocation.
**Fix:** exec bit restored; mode-only change, content byte-identical.
**Commit:** `527a550`

This is the same failure shape the phase's own overlay MANIFEST guards for pi-gen run scripts — a lost exec bit is silent — arriving through version control instead of the overlay.

### 2. [Finding — not patched] The Phase 7.1 substrate gates read the build host, not the rootfs

**This is why the build produced no `.img`.** It aborted at the unit substrate gates *after* all six criteria above were satisfied.

```
[unit-execstart] FAIL dbus-org.freedesktop.nm-dispatcher: ExecStart executable missing
                 in rootfs: /usr/libexec/nm-dispatcher
[unit-versions]  FAIL 12 interpreter version assertion(s) failed
```

The gates glob `/etc/systemd/system/*.service` and read the results **without chroot**. Seven of those entries are dbus alias symlinks whose targets are *absolute*:

```
dbus-org.freedesktop.nm-dispatcher.service -> /lib/systemd/system/NetworkManager-dispatcher.service
```

so the read escapes the rootfs onto the build host. Proven directly:

```
cat  (follows to HOST) -> ExecStart=/usr/libexec/nm-dispatcher          # host NM 1.52.1, trixie
chroot cat (true)      -> ExecStart=/usr/lib/NetworkManager/nm-dispatcher # rootfs NM 1.42.4, bookworm

rootfs /usr/lib/NetworkManager/nm-dispatcher  ->  present, 68024 bytes
rootfs /usr/libexec/nm-dispatcher             ->  No such file or directory
```

**The failure is false and the rootfs is correct.** The other 11 are OS daemons (`sshd`, `wpa_supplicant`, `bluetoothd`, `avahi-daemon`, `ModemManager`, `systemd-timesyncd`, plus `/bin/kill`) being demanded an interpreter version floor they cannot meaningfully have.

**Every arlowe unit passed:**

```
[unit-versions] OK arlowe-dashboard: /opt/arlowe/node/bin/node reports 24.21.0 (floor 20.9.0)
[unit-versions] OK arlowe-face:  /opt/arlowe/venvs/voice/bin/python reports 3.11.2 (floor 3.11.0)
[unit-versions] OK arlowe-voice: /opt/arlowe/venvs/voice/bin/python reports 3.11.2 (floor 3.11.0)
[unit-versions] OK qwen-tokenizer: /opt/arlowe/venvs/llm/bin/python reports 3.11.2 (floor 3.11.0)
[unit-versions] OK whisper-stt: /opt/arlowe/venvs/stt/bin/python reports 3.11.2 (floor 3.11.0)
```

So both Phase 7.1 gates *have* now run against a real arm64 rootfs on real silicon, which is what this plan was meant to capture — and the answer is that the version gate's chroot probe works correctly for arlowe's own interpreters and the surrounding path resolution does not.

**Not patched, deliberately.** The fix is chroot-relative path resolution plus a scoping decision about OS daemons — security-relevant surfaces (`sshd`, `wpa_supplicant`) whose allowlisting is the owner's call, not mine. Loosening a gate from inside a verification plan is precisely the move this phase exists to distrust, and the severity runs the other way too: a gate that reads the host can return a false **pass** as readily as this false failure. Belongs in a Phase 7.1 gap-closure plan.

### 3. [Finding — not patched] apt re-fetches the pinned kernel debs from the archive

The build log reads `Need to get 119 MB of archives` with `Get:` lines pointing at `archive.raspberrypi.com` for all six pinned debs, despite those files having just been copied into the chroot. Confirmed in a native arm64 `debian:bookworm` container:

```
'http://archive.raspberrypi.com/debian/pool/main/l/linux/linux-image-6.12.96%2brpt-rpi-2712_...deb'
'http://archive.raspberrypi.com/debian/pool/main/l/linux/linux-kbuild-6.12.96%2brpt_...deb'
... all six, as http URIs, not file: URIs
```

**A false step in my own testing, reported because it is the phase's recurring lesson.** My first run of this test showed `file:` URIs and appeared to exonerate the mechanism — but its `apt-get update` had silently failed, so apt had no archive candidate to prefer. It was measuring an empty index, not apt's preference. The rerun with a verified index (`apt-cache policy` confirming `Candidate: 1:6.12.96-1+rpt1`) reversed the result.

**What it does and does not weaken.** The *version* pin is intact and un-driftable — `linux-image-6.12.96+rpt-rpi-2712` is a distinct package name, only 6.12.96 can install, and the rootfs assertion confirms it did. Weaker than documented are the *digest* pin, which covers the cache rather than the installed bytes, and the "local cache makes a rebuild independent of the archive" rationale, which is **not realised**: a build would fail today if the pool stopped serving 6.12.96, populated verified cache notwithstanding. That is the pool-retention risk the manifest names, unmitigated by the mechanism meant to mitigate it.

Recorded in ADR-0009 and the runbook; not patched, because it changes how `stage0/02-firmware/00-run.sh` installs.

### 4. [Correctness] The reference manifest was re-recorded from a clean tree

The build's own recording carried `worktree_clean false`, because the exec-bit workaround needed to launch it left one mode bit dirty. Freezing that as the permanent baseline would assert a dirty-tree provenance for every future comparison. Re-recorded from the **same rootfs** with the tree restored to a clean `2d57b8b`; the two recordings differ by **exactly one line** and are byte-identical across all 658 pkg rows and all 10 pin rows. It is still this build's own output.

### 5. Documentation corrections found against the repo

- The plan says the Debian snapshot timestamp lives in **two** overlay files. It lives in **three** production locations — `sources.list`, `prerun.sh`, and `PIGEN_SNAPSHOT` in `build-image.sh`. The runbook documents all three and flags `prerun.sh` as the dangerous one to miss, since debootstrap would then use the old snapshot while apt used the new one, with nothing looking wrong.
- The relapse guard is a blunt substring grep, so it fires on a *prohibition* of the refuted claim just as it does on an assertion of it. Both the ADR and the runbook state the prohibition without the literal phrase, the way `third_party/kernel/manifest.yml` already did.

## Next Phase Readiness

**Phase 7.2's own criteria are all met.** SC1–SC5 confirmed against a real build rather than fixtures; SC6 proven.

**Blockers before this phase can close:**

1. **No `.img` exists.** The hardware checkpoint (flash the test card, boot the device) cannot be performed. Unblocking it needs Deviation 2 resolved, then a re-run — and a re-run is cheap in risk but not in time, so it should follow the fix rather than precede it.
2. **Phase 7.1 SC6 is unblocked only in the sense this phase owns.** The driver compiles. Whether the device boots and loads it is 7.1's remaining work, and its hardware checkpoint is gated behind the same missing image.

**Recommended follow-ups, in priority order:**

1. Phase 7.1 gap-closure: chroot-relative resolution in the substrate gates, plus a scoping decision for OS daemons. Highest priority — it blocks the image.
2. Kernel install from the cache rather than the archive (Deviation 3), which is what makes the digest pin and the retention mitigation real.
3. Narrow the input diff gate's environment rows, or accept routine re-acceptance. `source_date_epoch` derives from the commit and the diff is a whole-file `diff -u`, so **every** build from a new commit reports a difference even when no resolved input moved. Documented in the runbook; a gate that fires on noise gets switched off.
