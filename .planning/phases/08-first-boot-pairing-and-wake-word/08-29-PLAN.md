<objective>
Stop the post-build scripts from resetting `/etc/arlowe` to 0755 (checker blocker, confirmed read-only on build A's `build/arlowe.img`: `755` in p2 and p3 while the pre-assembly rootfs has `770`).

Cause: `scripts/lib/boot-config.sh:87` runs `sudo install -d -m 0755 "${mnt_a}/etc/arlowe"` in build step 4b, and `scripts/lib/recovery-stub.sh:246` does the same to slot B. `install -d` resets the mode of an existing directory. Slot B is `rsync -aHAX` of slot A after boot-config runs, so it inherits A's 755 and then gets it again.

Purpose: `arlowe-pair` runs as `arlowe` and writes `config.yml` by rename from `config.yml.tmp` in `/etc/arlowe`; at 755 root-owned every hardware pairing ends `setup_failed`. The same bug is a live Phase 4 regression on current images: the dashboard (User=arlowe) cannot write the overlay either. `tests/phase-4/assertions/01-config-install-shape.sh` asserts 770 but runs on a docker-provisioned tree, never on a built image, which is why nothing caught it. This plan has no dependencies so it can land first.

3 + 3 + 70 + 2 + 4 = 82.

<execution_notes>
- **Exempt from the phase precondition (#201 merged).** This plan touches no login, sudo or sshd path and fixes a live Phase 4 regression (the dashboard cannot write its overlay on current images, #202), so it may execute and merge before #201.
- **Fix choice: `sudo mkdir -p`, not `install -d -g arlowe -m 0770`.** The build host has no `arlowe` group name, so `-g arlowe` fails or, worse, resolves to a host group with a different GID. The directory always exists at step 4b (install-arlowe-fs.sh line 95 creates it `root:arlowe 0770` in the chroot, and the rsync clone preserves it), so `mkdir -p` changes nothing on it and the chroot's owner, group and mode survive. The comment says why in one line: `install -d` would reset the mode of an existing directory.
- Do not touch the `install -m 0644` of `ab-partuuid-map`; a root-owned 0644 file in a 0770 root:arlowe directory is what arlowe-ab expects.
- Leave recovery-stub.sh's other `install -d -m 0755` calls alone (`/opt/arlowe/models` and the rest match their contract mode); the scan targets `etc/arlowe` only.
- Static scan rules, applied to `scripts/**/*.sh`, `pi-gen/**/*.sh` and the shell files under `runtime/cli/` (Task 1 case 3 scans exactly this set): a line matching `install` with `-d` whose target ends in `etc/arlowe` or `etc/arlowe"` (the directory, not a file inside it) must contain `0770`; a line running `chmod` on that directory must set `770` or `0770`. Print every offending `file:line`.
- The behavioural case sources `scripts/lib/recovery-stub.sh`, shadows `sudo() { "$@"; }`, builds `${WORK}/slot/etc/arlowe` at 0770, runs `_rstub_write_partuuid_map "${WORK}/slot" <map>`, and asserts the directory is still 770 and the map is 0644. Use `stat -c %a` with a `stat -f %Lp` fallback so it runs on a Mac too. boot-config.sh's write is inline in a function that loop-mounts the image, so it is covered by the static scan and by 08-27a's image inspection.
