<execution_notes>
- Dev host only. `cryptography>=38.0.4,<46` is already pinned in `scripts/pki/requirements.txt`; use only that API.
- The device side does not change: it still sends `Authorization: Bearer <code>` (ADR-0007). The broker normalizes the presented value with `claim_codes.normalize`; a value that fails to normalize is a 401 like any other.
- Hold the store lock for the whole request (check, issue, bind). A dev broker serving one owner at a time can afford it, and it closes the check-then-bind race.
- `--stub-fail issuance` makes `create_certificate_from_csr` raise `ClientError` (code `InternalFailure`) so the broker returns 502. That is how 08-26 and 08-27b provoke "cert issuance fail".
- `stub_iot.py tls --san <ip-or-name> --out DIR` writes `broker-cert.pem`, `broker-key.pem` and `ca.pem` (self-signed; the device trusts it through `ARLOWE_BROKER_CA_BUNDLE`). `stub_iot.py` is also a library the broker imports only in stub mode, so the AWS path still imports only boto3.
- Update every `ARLOWE_BROKER_TOKEN` reference in `README.md` and the existing tests. Keep `test_token_never_reaches_the_log` as `test_claim_code_never_reaches_the_log`.
</execution_notes>

<feature>
  <name>Claim-code broker and stub IoT</name>
  <files>scripts/pki/broker.py, scripts/pki/stub_iot.py, scripts/pki/tests/*.py</files>
  <behavior>
    - Unused code + valid CSR → 200 with the six frozen fields; store entry now `bound` to the device_id.
    - Same code, same device_id → 200 again; still bound.
    - Same code, other device_id → 401; unknown code → 401; revoked code → 401; the three bodies are identical.
    - Issuance fails (stub `--stub-fail issuance`) → 502 and the code stays `unused`.
    - `load_config` without `ARLOWE_BROKER_CLAIM_CODES`, or with a path that does not exist → SystemExit naming it.
    - `StubIoT.create_certificate_from_csr` returns a PEM that verifies against the stub CA and whose public key equals the CSR's.
    - `describe_certificate(id)` returns that PEM and status `ACTIVE`; after `update_certificate(id, "REVOKED")` it returns `REVOKED`; `list_principal_things(arn)` returns the thing it was attached to.
    - `stub_iot.py tls --san 192.0.2.10` writes a cert whose SAN contains that IP and that verifies against `ca.pem`.
    - The claim code never appears in caplog.
  </behavior>
  <implementation>Stub state is in memory, keyed by certificate id (sha256 of the DER, hex).</implementation>
</feature>
