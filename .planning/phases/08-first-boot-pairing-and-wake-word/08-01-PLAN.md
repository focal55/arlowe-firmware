  <name>Task 1: ADR-0011 pairing setup channel and handoff</name>
  <files>docs/architecture/0011-pairing-setup-channel.md</files>
  <action>
Record:
- **Channel.** A NetworkManager AP plus an HTTP captive portal on `10.42.0.1:80`. No app. BLE is rejected: it needs a companion app or Web Bluetooth, and iOS browsers have no Web Bluetooth.
- **Hotspot security.** WPA2-PSK (`wifi-sec.key-mgmt wpa-psk`, `proto rsn`, `pairwise ccmp`). The password is generated fresh each time the unit enters pairing, shown as text on the Whisplay and in a `WIFI:T:WPA;S:<ssid>;P:<psk>;;` QR. It is never logged and never persisted: the AP profile is created with `nmcli connection add save no`. The open hotspot was the owner's first choice and was reversed because the home PSK, dashboard password and claim code would cross the air in cleartext (research N8). DHCP option 114 / RFC 8908 are not usable: the API must be HTTPS.
- **Discretion values (a table; later plans quote it):**
  - SSID `Arlowe-Setup-<device_id[:4]>` (lowercase hex; research checked all 65,536 suffixes against the banlist)
  - PSK: 12 characters from `23456789ABCDEFGHJKMNPQRSTUVWXYZ` via `secrets.choice`. No QR-special characters, so no escaping.
  - Wi-Fi country `US`, a build constant (`ARLOWE_WIFI_COUNTRY` in `arlowe-radio-init.service`, plus `/etc/modprobe.d/arlowe-wifi-regdom.conf`). Not `raspi-config do_wifi_country`, which edits `cmdline.txt` that `boot-config.sh` owns. A country picker is deferred; units sold outside the US need it.
  - AP on 2.4 GHz (`band bg`), channel 6, `ipv4.addresses 10.42.0.1/24`, `ipv6.method disabled`; captive DNS through `/etc/NetworkManager/dnsmasq-shared.d/arlowe-captive.conf` = `address=/#/10.42.0.1`.
  - Idle timeout 30 minutes with no successful submission: AP down, Whisplay shows "Press the button to start setup". A short press starts a new session with a new password.
  - Error kinds and their owner strings (Whisplay / portal): `wifi_rejected` "Wi-Fi password not accepted", `wifi_not_found` "Wi-Fi network not found", `server_unreachable` "Can't reach Arlowe servers", `claim_rejected` "Setup code not accepted", `cert_failed` "Couldn't get device certificate", `not_configured` "No setup server configured". The first five cover SC3's four modes.
  - Mapping from `arlowe-identity provision --json` failures (research N6): exit 4 with `http_status` null → `server_unreachable`; exit 3 with 401 → `claim_rejected`; exit 3 with any other status, exit 4 with a status ≥ 500, or exit 5 → `cert_failed`.
  - Broker URL supply: `identity.provisioning_url` is empty on the factory image. For dev and the checkpoint, a FAT-partition file `/boot/firmware/arlowe-broker.json` `{"url": "...", "ca_bundle_pem": "..."}` supplies it. Production supply waits on the AWS decision (07-09). Without either source, pairing shows `not_configured`. One resolver, `runtime/lib/arlowe_broker.resolve_broker`, serves both pairing and reset's revoke: the FAT file first (its CA written to a private 0600 temp file and passed as `ARLOWE_BROKER_CA_BUNDLE`), then `identity.provisioning_url` with system trust.
  - NTP gate: no TLS call before `timedatectl show -p NTPSynchronized --value` prints `yes`, or 30 s have passed.
- **Secrets never in argv.** Every NetworkManager profile that needs a secret (the setup AP and the home join) is created without it, then brought up with `nmcli connection up uuid <uuid> passwd-file /dev/stdin`, stdin carrying `802-11-wireless-security.psk:<psk>`. The join profile is system-owned (`psk-flags 0`), so NetworkManager persists the PSK it received for later boots; 08-27b confirms that on hardware.
  - Every profile is addressed by a `uuid4` the daemon generates and passes as `connection.uuid` at add time; `up` and `delete` use `uuid <uuid>`, never the name, because nmcli 1.42 reads a positional connection name through `next_arg`, which consumes `-a`/`--ask`/`-s`/`--show-secrets`-shaped words as global options (an owner's SSID is untrusted input). Values after a property name in `connection add` are taken literally.
  - The passwd-file line is escaped for NetworkManager 1.42.4's parser (`nmc_utils_parse_passwd_file` in `src/libnmc-base/nm-client-utils.c`, the image's `network-manager 1.42.4-1+rpt1+deb12u1`): the value's unescaped leading and trailing whitespace is stripped and `\` starts an escape, so the daemon writes every `\` as `\\` and every space as `\ `, and rejects CR/LF before writing.
  - **polkit `settings.modify.system` is load-bearing for PSK persistence.** Without it NetworkManager cannot write the system-owned join profile's secret, and the unit loses Wi-Fi at the next boot. Never trim it from the 51 rule.
  - **Fallback if the AP profile will not take its PSK from passwd-file on hardware (08-27b SC1):** in-process libnm (`python3-gi` plus the `NM` typelib, `gir1.2-nm-1.0`; `NM.Client.add_connection2` with the in-memory flag and the secret in the settings dict). The image ships `libnm0` but neither package today; the fallback is gated on verifying both (and `gir1.2-glib-2.0`) exist in the pinned snapshot, and it adds reference rows under the N10 merge gate. Never fall back to argv.
- **Handoff.** Optimistic: the form shows `http://<name>.local:3000` and the device IP before submit. On submit the page answers, the AP drops, the unit joins. On any failure the half-made profile is deleted, the AP returns with the same session password, and the error shows on both surfaces. Invariant: an unpaired unit has no saved Wi-Fi profile. Validate-then-commit is rejected: a single radio cannot hold the AP while testing a join, and the owner's phone would lose the portal either way.
- **Commit point.** The six runtime units carry `ConditionPathExists=/etc/arlowe/config.yml` and stay enabled at build. Pairing writes, in order: owner credential and session key; hostname (root oneshot); `config.yml` atomically (the commit point). Then, as the daemon's last act: draw the paired screen (URL and IP), hold it 30 s or until a button press, release the Whisplay (`board.cleanup()`), `systemctl start --no-block` the six, exit 0. A power cut leaves either "unpaired, pairing runs" or "paired, units run"; a cut during the hold is the second case.
- **No `Conflicts=` between `arlowe-pair` and `arlowe-face`.** Both are `WantedBy=multi-user.target`; `Condition*` is evaluated when a job runs, after the boot transaction has already resolved a conflict in favour of the declaring unit, so `Conflicts=arlowe-face.service` would cancel the face's start job on every boot of a paired unit. The daemon hands the display over by exiting instead.
- **Portal binding.** The portal binds `10.42.0.1:80`, not `0.0.0.0`, so it is never reachable from a wired LAN.
- **Setup-AP forwarding.** `ipv4.method shared` turns on IP forwarding and NAT from the setup AP to any other uplink (a bench ethernet cable). `arlowe-radio-init` loads an nftables table every boot that drops forwarded traffic entering or leaving `wlan0` (`nftables` is already in the rootfs; the appliance never routes, so the rule costs nothing once paired).
- **Privilege split.** `arlowe-pair.service` runs as `arlowe`. Root work happens in oneshots it starts through the existing `arlowe-` polkit prefix: `arlowe-pair-commit.service` (hostname, `/etc/hosts`, avahi restart; re-validates its input) and `arlowe-radio-init.service` (rfkill unblock, `iw reg set`, `nmcli radio wifi on`, every boot). NetworkManager access comes from `provision/polkit/51-arlowe-networkmanager.rules` granting `arlowe` exactly: `network-control`, `settings.modify.system`, `wifi.share.protected`, `wifi.scan`, `enable-disable-wifi`. Note that research drafted `wifi.share.open`; WPA2 needs `wifi.share.protected` instead, and `open` is not granted.
- **Residual risks:** the in-memory AP profile, with the per-session PSK, lives while pairing runs as a root-only 0600 keyfile under `/run/NetworkManager/system-connections` (tmpfs; gone at reboot or `ap_down`); Android before 12 cannot resolve `.local`, so the paired screen shows the IP for its 30 s hold; the hashed hostname banlist lets someone confirm a guess.

**ADR-0012:**
- Hash: Argon2id via `python3-argon2`, parameters set explicitly: `time_cost=3, memory_cost=65536, parallelism=4, hash_len=32, salt_len=16`. The PHC string goes to `/var/lib/arlowe/dashboard/owner-credential.json` (`{"hash", "created_at"}`, 0600 `arlowe`). It is not in `config.yml`, because `POST /api/config` rewrites the overlay and every service reads it. The dashboard verifies with Node 24's `crypto.argon2` and `timingSafeEqual`; CI moves to Node 24.
- Session: stateless cookie `arlowe_session = base64url(payload).base64url(HMAC-SHA256(key, payload))`, payload `{v:1, iat, exp}`, 30-day absolute expiry. Key: 32 random bytes at `/var/lib/arlowe/dashboard/session.key`, written at pairing, wiped by reset. Attributes `HttpOnly; SameSite=Strict; Path=/`, **no `Secure`** (plain-HTTP LAN; browsers drop Secure cookies on http). Every mutating route checks the session and that `Origin` matches `Host`. Login throttle: 5 failures, then 30 s.
- Forgotten password = factory reset. The claim code is not a master key.
- Claim codes: 20 Crockford base32 characters (100 bits), printed in groups of five; normalized by uppercasing and stripping `-` and spaces. The broker stores `sha256(normalized) → {state: unused|bound|revoked, device_id, minted_at, bound_at, note}` and returns an identical `401 {"error":"unauthorized"}` for unknown, bound-elsewhere and revoked codes. A code binds to the first `device_id` that redeems it, after IoT issuance succeeds; the same `device_id` redeeming again is idempotent (covers a lost 200). A reset's revoke call releases the binding. A reset that could not revoke leaves the code bound to the orphaned id, and releasing it is an operator action (`claim_codes.py release`). This supersedes "single-use".
- The device stays token-agnostic (ADR-0007): it still sends a bearer token and knows nothing about claim codes. The broker's "no lookup" rule was Phase 7's and lifts here.
- Residual: the hashed banlist; a stolen card cannot claim a unit that is already paired.

**ADR-0013:**
- New identity on reset. Preserving the identity across resets is rejected: it would carry the old owner's cloud binding to the next owner.
- Order (the reset helper follows it exactly): (1) write `/var/lib/arlowe/reset-ledger/in-progress` and fsync; (2) stop the six units and `arlowe-pair`; (3) best-effort `arlowe-identity revoke --json` with a 20 s timeout, against the broker `arlowe_broker.resolve_broker` returns (the same resolver pairing used: FAT file with its CA, then `identity.provisioning_url`), and on failure append `{certificate_id, thing_name, device_id, at, reason}` to `/var/lib/arlowe/reset-ledger/orphaned-certs.jsonl` and fsync; (4) `rm /etc/arlowe/config.yml`, **the commit point**; (5) delete every `802-11-wireless` NetworkManager profile and `/var/lib/NetworkManager/{seen-bssids,timestamps,*.lease}`; (6) `arlowe-identity reset --force`; (7) empty `conversations/`, `wake-word/`, `state/`, `dashboard/`, `logs/*`, `cache/` and recreate the skeleton exactly as `scripts/provision/install-arlowe-fs.sh` does; (8) `journalctl --rotate` then `--vacuum-time=1s`; (9) hostname back to `arlowe` and the `127.0.1.1` line in `/etc/hosts`; (10) append `{at, trigger, revoke: ok|failed|skipped}` to `reset-ledger/resets.log`, remove the marker, sync, reboot. A boot that finds the marker resumes (`arlowe-factory-reset-resume.service`).
- Survives: the reset ledger only (root 0700 on owner_state). Never touched: `/opt/arlowe/models`, `.firstboot-done`, `.models-grow-done`.
- Triggers: dashboard (`POST /api/device/reset`, session plus password re-entry) → `arlowe-factory-reset@dashboard.service`; Whisplay button (hold 10 s, countdown drawn from 3 s, LED red at 10 s, release, confirming press within 5 s; physical access is the authorization) → `arlowe-factory-reset@button.service`; recovery SD card (reflash; documentation only, `docs/operations/phase-8-pairing.md`). Slot B is not a trigger: it has never booted (B7).
- Residual: a unit paired against a self-signed dev broker whose FAT file was removed afterwards cannot verify that broker at reset time; the revoke fails TLS and the certificate lands in the orphan ledger, which is the designed outcome for any failed revoke.
- Open: who reaps orphaned certificates (research open question 9). The ledger records them; the consumer is unassigned.
