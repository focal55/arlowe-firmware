<task type="auto">
  <name>Task 2: Repo builder and swap-back library (GREEN), CI wiring</name>
  <files>scripts/lib/pi-archive-repo.sh, scripts/lib/pi-archive-gate.sh, .github/workflows/ci.yml</files>
  <action>
**`scripts/lib/pi-archive-repo.sh`** (executable, `set -euo pipefail`). Usage `--manifest M --paths P --out O`.
1. Use python3/yaml to read the entries (packages + resolve_only) into `filename<TAB>sha256<TAB>size` rows. Zero rows is a failure.
2. Build into `O.tmp` (rm -rf it first). For each row, find its map path (fail if missing), `cp` it in, and re-hash the COPY against the manifest.
3. Run `(cd O.tmp && dpkg-scanpackages --multiversion . /dev/null > Packages 2> scan.err)`. Drop the expected `missing from override file` and `Wrote N entries` lines; fail on any other stderr. Delete `scan.err`.
4. Cross-check with python3. The stanza count must equal the row count. For each stanza, keyed by Filename with `./` stripped, Package, Version, Architecture, Size and SHA256 must equal the manifest's values. Name every mismatch. On any failure, `rm -rf O.tmp`.
5. `(cd O.tmp && sha256sum *.deb Packages > SHA256SUMS)`, then `rm -rf O && mv O.tmp O`. Print `[pi-archive-repo] N debs, Packages verified against the manifest`.
The header comment gives two reasons:
- **dpkg-scanpackages, not a hand-written index.** It reproduces the control fields faithfully: Pre-Depends, Provides, Breaks, Multi-Arch.
- **`[trusted=yes]` is sound.** The trust anchor is the committed sha256. It is enforced here, and again by apt against the Packages SHA256 at install time. Signing would only prove that the build host signed its own output.

**`scripts/lib/pi-archive-gate.sh`** (new sourced library; not executable; header in the style of `verify-persistent-journal.sh`, describing the library as "Phase 7.3 Pi-archive checks over a built rootfs"). Define the independent constant `PI_REPO_IN_ROOTFS="/var/local/arlowe-pi-archive"` and the flat-repo list name `arlowe-pi-archive.list`. Add `pi_archive_swap_back ROOTFS PIGEN_DIR RELEASE EPOCH`:
1. Validate the template `PIGEN_DIR/stage0/00-configure-apt/files/raspi.list` FIRST. Return 1 if it is missing, before removing anything.
2. `rm -rf` the repo dir and the flat-repo list.
3. `sed "s/RELEASE/${RELEASE}/g"` the template into a temp file, then `install -m 644` it to `ROOTFS/etc/apt/sources.list.d/raspi.list`.
4. `touch -h -d "@${EPOCH}"` `raspi.list`, `etc/apt/sources.list.d` and `var/local`.
5. Assert the result: the repo dir is absent, the flat-repo list is absent, and `raspi.list` has an active `deb http://archive.raspberrypi.com/debian/ ${RELEASE} main` line. Any assertion failing → `[FAIL]` naming it, rc 1.
6. Success → `[OK] Pi flat repo removed; rootfs ships the stock raspi.list.`
The comment records the decision and its reasons (research Pattern 4, four numbered reasons). It also records the consequence: `apt upgrade` on a device mixes the rolling Pi archive with the frozen snapshot, which is unsupported, and the A/B image is the update channel. Slot B is an rsync clone of slot A, so it inherits this state.
