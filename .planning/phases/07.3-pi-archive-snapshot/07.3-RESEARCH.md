# Phase 7.3: Pi archive snapshot - Research

**Researched:** 2026-09-25
**Domain:** apt flat repositories inside pi-gen chroots; build-input pinning for a rolling Debian-format archive with no snapshot service
**Confidence:** HIGH for the mechanics (measured in a debian:bookworm arm64 container and against the live indexes); MEDIUM for the build-host-only behaviour, which can only be confirmed by the one hardware build

## Summary

The phase is buildable as scoped, and it is smaller than it looks. The measurements behind that:

- **Attribution is unambiguous today.** 663 `pkg` rows in the committed 07.2 reference (a real
  build, re-recorded 2026-09-25 in `a453b41`) were classified against the live Pi index and all
  12 snapshot.debian.org `20260915T000000Z` arm64 indexes (main/contrib/non-free/non-free-firmware
  × bookworm/-security/-updates). **97 match the Pi archive by name+version+arch and are absent from
  Debian at that version. 565 are Debian-only. 0 are ambiguous (same name and version in both). 1
  is neither (`axclhost`, the local axcl deb).** All 97 are still served by the live index today,
  at the same versions the 2026-09-20/25 builds installed.
- **The first manifest does not need a record-mode hardware build.** The committed reference *is*
  a real build's resolution. Intersect it with an apt-verified Pi index and you get the manifest.
  That keeps this phase to one hardware plan.
- **A flat `file:` repo with `[trusted=yes]` works as needed.** The container experiment
  showed all of the following. `dpkg-scanpackages` output is accepted without a Release file.
  apt writes a list file named `_<path>_._Packages`, which the gate can count. `--print-uris`
  emits `file:` URIs, so `resolve-twice.sh` parsing keeps working. apt rejects a tampered deb
  with a hash mismatch (rc 100). A missing repo directory fails `apt-get update` with rc 100.
  Removing a source and re-running update deletes its list files.
- **Three hazards were found that the phase description does not mention.**
  1. **Silent substitution.** If the flat repo lacks a package that Debian also carries, apt
     installs the Debian version and says nothing. Demonstrated: with Pi's `python3-gpiozero`
     absent, apt picked Debian's `1.6.2-1+b1`. "apt can't find it → build fails" is therefore true
     only for Pi-only names. The completeness check must run in both directions.
  2. **`firmware-marvell-prestera-`** in upstream `stage2/02-net-tweaks/00-packages` is a removal
     marker for a package that exists **only** in the Pi archive and is never installed. A
     manifest built from installed packages would omit it, and `apt-get install …
     firmware-marvell-prestera-` fails with `E: Unable to locate package` (rc 100, verified). It
     must be carried as a resolve-only entry.
  3. **`SKIP_IMAGES=1` as an environment variable is a no-op in pi-gen at the pinned tag.**
     `build.sh:94` tests `[ ! -f SKIP_IMAGES ]`, a *file* in the stage directory, and the variable
     is read nowhere else. So stage2's `EXPORT_IMAGE` still triggers `export-image`, and its
     `02-set-sources` runs `apt-get update && apt-get -y dist-upgrade` on a copy of the stage2
     rootfs. This doesn't corrupt our rootfs, and it works in pinned mode because the repo is
     inside that copy. But the repo's comments and ADR-0009 state the opposite, and every build
     pays for a throwaway export.

**Primary recommendation:** Build a host-side flat repo from sha256-verified debs named by a
generated one-line-per-package `third_party/pi-archive/manifest.yml`. Copy it into the stage0
rootfs in place of `raspi.list` via the existing `stage0/00-configure-apt/00-run.sh` overlay.
Gate it in `build-image.sh` exactly like the Debian snapshot gate (`0 off-pin`). Add a
two-direction completeness check. After observation, swap the rootfs back to the upstream
`raspi.list`. Bootstrap the manifest from the committed 07.2 reference, not from a record-mode
build.

### Core

|------|---------|---------|--------------|
| `dpkg-scanpackages` (dpkg-dev) | build host's dpkg-dev (trixie 1.22.x); CI runner's (Ubuntu 24.04) | Generate the flat repo `Packages` index from the verified debs | The Debian-documented way to build a trivial/flat repo; emits MD5sum/SHA1/SHA256/Size per stanza, which apt then enforces |
| apt flat repo, `deb [trusted=yes] file:/var/local/arlowe-pi-archive ./` | apt 2.6.1 (bookworm, in the rootfs) | The only Pi-side source visible to the rootfs build | Verified in container: works with no Release file; `file:` URIs appear in `--print-uris`; hash mismatch fails the install |
| python3 + PyYAML | already a build-host requirement | Manifest generator and completeness checker | `record-build-inputs.sh`, `verify-models.py` and the kernel gate already depend on it; no new dependency |
| `curl` + `sha256sum` | host | Pool-URL fetch into the cache and digest assertion | Same as check 7 (kernel) and check 8 (rpt-packages) |
| apt in a `debian:bookworm` container | 2.6.1 | Fetch **signature-verified** Pi indexes for the bootstrap generator | apt verifies `InRelease` against `raspberrypi-archive-keyring`; no hand-rolled gpgv/Release parsing |

### Supporting
| Tool | Purpose | When |
|------|---------|------|
| `actions/cache@v4` | Cache the ~172 MiB of Pi debs in CI keyed on the manifest hash | `build-inputs-resolve` job, so `resolve-twice.sh` can see the flat repo |

### Alternatives Considered
| Instead of | Could use | Why rejected |
|------------|-----------|--------------|
| Flat repo from pinned debs | apt preferences (`Pin: version …`) against the live archive | **The index carries one version per package name** (2103 names, 2113 stanzas in today's `binary-arm64/Packages.gz`). Once Pi publishes, the pinned version leaves the index and apt cannot select it, even though the pool still holds the bytes. A preference also verifies nothing. |
| `[trusted=yes]` | Signing the flat repo with a throwaway or committed key | Signing proves only that the build host signed what the build host generated. The trust anchor is the committed sha256, asserted before the repo exists and enforced by apt against the `Packages` SHA256 at install. A key adds gpg to the host, key storage and a signing step, and no attacker is stopped by it. |
| `dpkg-scanpackages` | `apt-ftparchive packages/release` (apt-utils) | Also a new host dependency. It would also produce a Release file, which silences apt's harmless `Err:3 … Packages.xz` compression probes (see Pitfall 9). Not worth a second tool. |
| Copying the repo into the rootfs | Bind-mounting it per stage | pi-gen `unmount`s everything under `WORK_DIR/<stage>` at every stage boundary. A bind mount would have to be re-created in `stage1/prerun.sh` and `stage2/prerun.sh`, which are upstream files, adding two more overlay entries. A copy is carried forward by `copy_previous` (rsync excludes only `var/cache/apt/archives`) with zero upstream edits. |
| A record-mode hardware build for the first manifest | Bootstrapping from `docs/operations/phase-07.2-inputs.reference` | The reference is a real build's resolution, and all 97 Pi rows still resolve in today's index. A record build would cost a second hardware plan and prove nothing more. |

**Installation (build host, one-time):**
```bash
sudo apt-get install -y --no-install-recommends dpkg-dev
```
`build-image.sh` must preflight `command -v dpkg-scanpackages` and fail with that hint. The header comment listing "Required host packages" gains `dpkg-dev`.

## Architecture Patterns

### File layout
```
third_party/pi-archive/
├── manifest.yml        # GENERATED; one flow-mapping line per deb; absorbs rpt-packages
└── INSTALL.md          # cache locations, ARLOWE_PI_ARCHIVE_FETCH, mirroring
third_party/rpt-packages/   # DELETED (its 3 entries are in pi-archive; its prose moves to the runbook)
third_party/kernel/manifest.yml  # UNCHANGED; still the kernel pin (see SC3 below)
scripts/lib/pi-archive-manifest.py  # generate (record/bootstrap) + check (pinned) modes
scripts/lib/pi-archive-repo.sh      # host: cache -> build/pi-archive-repo/{*.deb,Packages,SHA256SUMS}
overlays/pi-gen/stage0/00-configure-apt/00-run.sh  # MODIFIED overlay: flat repo instead of raspi.list
tests/phase-07.3/                    # self-tests; bootstrap-manifest.sh (container)
docs/architecture/0010-pi-archive-pinning.md       # or an ADR-0009 amendment
docs/operations/phase-07.3-pi-archive-pinning.md   # pin-bump + security runbook
```
`.gitignore` gains `third_party/pi-archive/*.deb` in the same PR that creates the directory.
07.2-02's deviation #1 was exactly this omission.

### Pattern 1: Manifest format — one line per package
**What:** A YAML list of flow mappings, one per line, sorted by name:
```yaml
packages:
  - {name: libc6, version: "2.36-9+rpt2+deb12u14", arch: arm64, filename: "libc6_2.36-9+rpt2+deb12u14_arm64.deb", size: 5001894, sha256: "…", url: "http://archive.raspberrypi.com/debian/pool/main/g/glibc/libc6_2.36-9+rpt2+deb12u14_arm64.deb"}
resolve_only:
  - {name: firmware-marvell-prestera, version: "1:20240709-2~bpo12+1+rpt4", arch: all, filename: "…", size: 61318452, sha256: "0f4958647f1757adcc629ac710bef33222b040fd2c9b4d22fa3021c8decbffc0", url: "…", why: "upstream stage2/02-net-tweaks/00-packages names it as a removal marker; apt must be able to locate it"}
```
**Why:**
- The block YAML used by the kernel manifest costs about 6 lines per entry, so 92 entries come to
  about 550 lines. That breaks the 400 soft cap and nearly the 600 hard cap on its own (the size
  check counts additions plus deletions and excludes only lockfiles and `.planning/`). One line
  per entry is about 92 lines plus a header.
- `record-build-inputs.sh`'s walker already emits a `pin` row for any mapping that has both
  `filename` and `sha256`, so these rows appear with no recorder change.
- `version` carries the **epoch** (`1:…`) because dpkg reports it that way. `filename` is the
  pool basename, which carries no epoch. Keep both; the check compares `version` to dpkg, and
  the fetcher uses `filename`/`url`.

### Pattern 2: Two modes, one switch
`ARLOWE_PI_ARCHIVE_MODE=pinned` (default) or `record`. It is exported by `build-image.sh` and
**named explicitly in the `sudo` env list**, together with `ARLOWE_PI_REPO`. An unlisted
variable silently fails to cross into pi-gen, which is the kernel-cache lesson from 07.2.

| | pinned (default) | record (pin bumps only) |
|---|---|---|
| stage0 Pi source | `deb [trusted=yes] file:/var/local/arlowe-pi-archive ./` | upstream `raspi.list` (live archive) |
| Pre-build | verify-third-party fetches/verifies every manifest deb; `pi-archive-repo.sh` builds `build/pi-archive-repo` | nothing Pi-side |
| Post-pi-gen gate | Pi off-pin gate + completeness check (below) | the generator writes `build/pi-archive.manifest.candidate` from rootfs dpkg status and rootfs apt lists, prints the diff against the committed manifest, then **exits non-zero before partitioning**. A record build never produces an image. |
| Image | yes | no |

Bootstrap (one-time, this phase): `tests/phase-07.3/bootstrap-manifest.sh` runs in
`debian:bookworm`. It installs pi-gen's `raspberrypi.gpg.key`, adds the live Pi archive (signed,
**not** `trusted=yes`) plus the snapshot sources, runs `apt-get update` so apt verifies InRelease,
then runs the same generator with `--installed-from docs/operations/phase-07.2-inputs.reference`
and `--pi-lists /var/lib/apt/lists/archive.raspberrypi.com_*binary-arm64_Packages*` plus
`--resolve-only firmware-marvell-prestera`.

### Pattern 3: Attribution rule (generator)
For each installed `(name, version, arch)` taken from dpkg status (record mode) or `pkg` rows
(bootstrap):
1. Look it up in the Pi archive list (`arch` matches, or the stanza is `Architecture: all`).
2. Look it up in the snapshot.debian.org lists.
3. Classify:
   - Pi-only → a manifest entry, with `url = pool_base + Filename` and `size`/`sha256` taken from
     the stanza.
   - Both with **identical SHA256** → skip. The Debian snapshot already pins it.
   - Both with **different SHA256** → **hard fail** and name it. Origin then depends on apt's
     tie-breaking, which is not a pin. Count today is 0.
   - Neither → allowed only if it is in the explicit local allowlist, which is only
     `third_party/axcl`'s `axclhost` today. Otherwise fail.
   - Names in `third_party/kernel/manifest.yml` → excluded (pinned there). If the generator sees
     a kernel package at a different version, it fails.
4. Hard-fail on zero entries (the 07.2 "empty manifest at exit 0" lesson), on any installed
   `armhf` package, and on an index file compressed in a format it can't read. apt in a docker
   image stores `.lz4` because of `docker-gzip-indexes`; the pi-gen rootfs stores plain files.
   Delete `/etc/apt/apt.conf.d/docker-gzip-indexes` in the bootstrap container, as the experiment
   did.

Read indexes from the **rootfs's `/var/lib/apt/lists`**, which apt already signature-verified,
never from a fresh network fetch at gate time. The gate must read them **before**
`build-image.sh` deletes them (line 326, "observe-then-remove").

### Pattern 4: Where the swap happens
- **In:** `overlays/pi-gen/stage0/00-configure-apt/00-run.sh`, already an overlay, replaces the
  `install … files/raspi.list …` line. In pinned mode it:
  1. Asserts `ARLOWE_PI_REPO` is a directory.
  2. `install -d` + `cp` into `${ROOTFS_DIR}/var/local/arlowe-pi-archive/`.
  3. Runs `sha256sum -c SHA256SUMS` **inside the rootfs copy**, so the bytes that enter the
     rootfs are the bytes asserted.
  4. Writes `sources.list.d/arlowe-pi-archive.list`.

  The existing `apt-get update; apt-get dist-upgrade -y` then upgrades the debootstrap base
  (libc6, dpkg, zlib1g, libpam*) to the flat repo's `+rpt` versions, which is the same behaviour
  as today with the live archive. The overlay's `upstream_sha256` is unchanged. Re-record its
  `overlay_sha256` in `overlays/pi-gen/MANIFEST` by hand; there is deliberately no helper.
- **Carried:** `copy_previous` rsyncs `/var/local/arlowe-pi-archive` into stage1, stage2 and
  stage-arlowe (and into the stage2 export copy while export still runs).
- **Out:** in `build-image.sh`, **after** the Pi gate and completeness check and **before** the
  `rm` of the apt lists and Step 3's `du`, remove `/var/local/arlowe-pi-archive` and
  `arlowe-pi-archive.list`, and install the upstream `raspi.list`. Take that file from
  `pi-gen/stage0/00-configure-apt/files/raspi.list` with `RELEASE` substituted, so the shipped
  file is byte-identical to stock Pi OS. Clamp its mtime with `touch -d @${SOURCE_DATE_EPOCH}`.
  Assert that the removal happened; the kernel installer's "the debs would ship" check is the
  template.

  Slot B is an `rsync -aHAX --delete` clone of mounted slot A (`recovery-stub.sh:112`), so it
  inherits the final state and needs no work of its own.

**What a shipped device sees: the upstream `raspi.list` (the live Pi archive), with the keyring
installed.** This is a decision; the reasons:
1. It keeps the device identical to stock Pi OS for on-device debugging (`apt install i2c-tools`).
2. The update channel is the A/B image, not apt.
3. Shipping nothing breaks every on-device Pi package install for no gain.
4. Shipping the flat repo would cost about 170 MiB of the slot.

Record the consequence in the ADR. An on-device `apt upgrade` mixes the rolling Pi archive with
the frozen Debian snapshot the image already ships. That was already true before this phase, and
it is an unsupported path, not an update mechanism.

### Pattern 5: The in-build Pi gate (SC2), shaped like the Debian gate
At `build-image.sh`, next to the snapshot gate, reading `${PIGEN_ROOTFS}`:
1. No active line in `sources.list` or `sources.list.d/*` names `archive.raspberrypi.com`. This
   runs before the swap-back, so it is meaningful.
2. At least one list file matches `^_var_local_arlowe-pi-archive_._Packages`. The name was
   verified: apt writes `_<path>_._Packages` for `file:/<path> ./`.
3. **Zero** list files match `^archive\.raspberrypi\.com_`. This is the real check, the analogue
   of `ROLLING_LISTS`. apt deletes the list files of removed sources on update (verified), so a
   stale file means the source was active at stage0's update.
4. Log: `Pi archive resolution pinned: N flat-repo list files, 0 off-pin.`

Keep the expected path as an independent constant in `build-image.sh`, as `PIGEN_SNAPSHOT` is,
not derived from the overlay.

### Pattern 6: Completeness check (SC1's "check fails")
`pi-archive-manifest.py --check --rootfs … --manifest … --kernel-manifest …` in pinned mode:
- **Forward:** every `packages:` entry is installed at exactly `version`/`arch`. A missing or
  different version is a failure that prints the installed version and its origin list. This is
  the only check that catches **silent substitution** by a lower Debian version.
- **Reverse:** every installed package is attributable to the flat-repo list, a snapshot list at
  that version, the kernel manifest, or the local allowlist. Anything else is a failure and is
  named.
- **resolve_only:** each entry is **not** installed.
- **Pi-only name missing from the manifest:** apt already fails at the stage that asked for it
  (`Unable to locate package` / `has no installation candidate`). The check does not need to
  duplicate that, but the runbook must say that this is what that failure means.

The existing 07.2 diff gate stays as the third layer. The manifest pins bytes, the check pins the
set, and the diff gate pins everything else.

### Anti-Patterns to Avoid
- **Believing "apt fails if the repo lacks it."** That holds only for Pi-only names. For the
  roughly 40 names both archives carry (libc6, openssl, pam, NM, bluez, alsa, zlib, …) apt quietly
  installs Debian's version. The forward check is not optional.
- **Generating the manifest from `/var/cache/apt/archives`.** pi-gen's `copy_previous` excludes
  it, `export-image` and stage-arlowe run `apt-get clean`, and it is empty by the time a gate
  runs.
- **Generating from `apt-get --print-uris` of a package list.** It doesn't replicate pi-gen's
  staged installs, recommends, or the stage0 `dist-upgrade`. The installed set of a real build is
  the only faithful source.
- **Hand-typing any digest.** The generator writes every `sha256`/`size`; `verify-third-party`
  then proves the served bytes match.
- **A regenerate-and-commit helper for the pinned-mode gate.** As with the MANIFEST digests, the
  only path to a new manifest is a record build and a human reading the diff.

## Don't Hand-Roll

| Problem | Don't build | Use instead | Why |
|---------|-------------|-------------|-----|
| Packages index for the local repo | A Python writer of `Package/Depends/Filename/SHA256` stanzas | `dpkg-scanpackages . /dev/null` | Control-field fidelity (Pre-Depends, Provides, Breaks, Multi-Arch) is exactly what a hand writer gets wrong, and apt resolves on it |
| Pi index authenticity (bootstrap) | `gpgv` + parsing InRelease + hashing Packages.gz | `apt-get update` in `debian:bookworm` with the Pi key in `trusted.gpg.d` | apt already implements the whole chain |
| Epoch/version comparison | String compares | Exact string equality against dpkg's `${Version}`, and `dpkg --compare-versions` if ordering is ever needed | `rpt` vs `deb` ordering is counter-intuitive (see the security section) |
| Fetch/verify loop for 92 debs | A third copy of the ~200-line bash kernel stanza | One Python helper (precedent: `scripts/lib/verify-models.py`) called from a thin `verify-third-party.sh` stanza, with the same cache order (`ARLOWE_PI_ARCHIVE_DIR` → `/var/cache/arlowe-build/pi-archive` → XDG), opt-in `ARLOWE_PI_ARCHIVE_FETCH=1`, and pointer file `build/.arlowe-pi-archive-cache` | Check 8 already duplicates check 7. A third copy is how the three drift apart. |

**Key insight:** every component exists. The engineering is in the gates, because apt's failure
modes here are silent: substitution, `apt-get update` exiting 0 on partial failure, and an
env-var no-op.

## Common Pitfalls

### Pitfall 1: Silent substitution by Debian's version
**What goes wrong:** A package present in both archives is missing from the flat repo, apt
installs the Debian build, and the build is green.
**Evidence:** the container experiment resolved `python3-gpiozero` to Debian's `1.6.2-1+b1`
when Pi's `2.0.1-0+rpt1` was absent.
**Avoid:** the forward completeness check (Pattern 6). The 07.2 diff gate also catches it as a
`pkg` row change.
**Warning sign:** an installed version without `rpt`/`~bookworm` where the reference had one.

### Pitfall 2: Names apt must know but that are never installed
**What goes wrong:** `firmware-marvell-prestera-` (stage2 removal marker) → `E: Unable to locate
package`, and stage2 aborts.
**Avoid:** `resolve_only:` in the manifest (61 MB added to the cache, never installed, asserted
not installed). The alternative is overlaying `stage2/02-net-tweaks/00-packages` to drop the token.
That is behaviour-preserving in pinned mode, because nothing else can supply prestera as a
recommend, but it changes record mode: a live-archive build would install 61 MB of prestera. Pick
resolve-only.
**Detect others:** stage package lists × installed set, done for this research. Only prestera is
listed-but-not-installed today. Re-run it on any `PIGEN_REF` bump.

### Pitfall 3: `SKIP_IMAGES=1` is not doing what the repo believes
**What goes wrong:** pi-gen exports a stage2 image on every build. `export-image/02-set-sources`
runs `apt-get update && dist-upgrade --auto-remove --purge` in that copy. It is harmless to the
stage-arlowe rootfs, and works in pinned mode because the repo is inside the copied stage2 rootfs,
but it wastes minutes, and `build-image.sh:217,271`, ADR-0009 §9 and 07.2-01-SUMMARY all say it is
skipped.
**Avoid:** verify on the build host first
(`ls pi-gen/deploy/`, or `grep 'export-image' <pi-gen work>/build.log`). Then fix it by adding a
`NEW` overlay entry, an empty `stage2/SKIP_IMAGES` file with mode 644. **Recommend filing it as a
separate issue** rather than folding it into 7.3. If it does land in 7.3, it goes in the overlay PR
and the checkpoint plan confirms that no `export-image` line appears.

### Pitfall 4: A stale work dir defeats everything
**What goes wrong:** `stage0/prerun.sh` skips debootstrap and `stage1/2/arlowe prerun.sh` skip
`copy_previous` when the rootfs exists. A surviving stage0 rootfs from a live-archive build keeps
its old `+rpt` packages, and the lists may be refreshed while the installed bytes are not.
**Avoid:** keep the 07.2 procedure (`sudo rm -rf build/pi-gen-work` before every full build). It
matters more now because record and pinned builds alternate during a pin bump.

### Pitfall 5: The sudo env boundary
**What goes wrong:** `ARLOWE_PI_REPO` or `ARLOWE_PI_ARCHIVE_MODE` is exported but not listed in
the `sudo … ./build.sh` command (`build-image.sh:225-233`), so the stage0 overlay sees it unset.
**Avoid:** the overlay hard-fails on an unset or non-directory `ARLOWE_PI_REPO` in pinned mode,
and on an unknown mode, with the same wording as the kernel installer. Never default to record
mode: an unset mode must mean pinned.

### Pitfall 6: The kernel's cached debs are not what gets installed (known 07.2 open question)
**What goes wrong:** `apt-get install ./*.deb` preferred the archive copy because the index
carried the same version ("Need to get 119 MB of archives").
**Resolution by this phase:** with no `archive.raspberrypi.com` source, no index carries those
names, so apt installs the local files. The runbook's open question closes as a side effect, and
the checkpoint build log should show the kernel install downloading ~0 B from the Pi side. Put
the kernel debs **in** the flat repo too only if you also change 00-run.sh to install by name.
Otherwise leave them out (see SC3).

### Pitfall 7: Epochs
**What goes wrong:** dpkg reports `1:6.12.96-1+rpt1` and `1:1.20260915-1~bookworm`, while
filenames carry no epoch. A check that compares a filename-derived version to dpkg fails on every
epoch'd package (15 of the 97: kernel ×6, raspi-firmware, zlib1g ×2, firmware-* ×5,
linux-libc-dev).
**Avoid:** the manifest `version` is the Pi index's `Version:` field, which includes the epoch.

### Pitfall 8: Pool retention
**What goes wrong:** Pi prunes a pinned version from the pool, and a clean host or a CI cache miss
can no longer fetch it.
**Evidence:** retention is observed to be long (buster-era libc6 still served), but bookworm is
now `oldstable` on the Pi archive, and an aging suite is the likeliest to be pruned.
**Avoid:**
1. A HEAD probe of every manifest URL in CI (cheap, about 97 requests) that fails with "pool
   dropped X — the build host cache is now the only copy".
2. `ARLOWE_PI_ARCHIVE_DIR` so a project-controlled mirror plugs in.
3. A decision on a durable mirror (see Open Questions).

### Pitfall 9: apt noise from a Release-less flat repo
**What goes wrong:** `apt-get update` prints `Ign: … InRelease`, `Ign: … Release`, and several
`Err:3 file:/… Packages  File not found - …/Packages.xz` lines. It still exits 0 and uses the
plain `Packages`, as verified.
**Avoid:** a comment in the overlay saying so, so that nobody later adds a `grep '^Err'` failure
or "fixes" it by deleting the repo line. Don't gate on update's exit code either; gate on the list
files, as 07.2 does.

### Pitfall 10: Security fixes never arrive by advancing the Debian snapshot alone
**What goes wrong:** for glibc, pam, network-manager and bluez (`+rptN+deb12uM`), Pi's rebuild
outranks **every** Debian `+deb12uN`, because `rpt` sorts above `deb`. Even today, with the live
archive, a Debian glibc DSA reaches the image only when Pi rebuilds. For openssl
(`~deb12u2+rpt1`) the opposite applies: a Debian `~deb12u3` outranks the pin. After a snapshot
bump, apt would **flip the origin** to Debian silently, and only the forward check catches it.
**Avoid:** the runbook (SC5) must describe both orderings and require that a Debian snapshot bump
and a Pi pin bump are evaluated together.

### Pitfall 11: Installing tools in the CI resolution container changes what it measures
**What goes wrong:** adding `dpkg-dev` or `curl` inside `debian:bookworm` before
`resolve-twice.sh` resolves means those packages and their dependencies show as "already
installed" and drop out of `--print-uris`. The existing script makes the same argument about
curl/gnupg.
**Avoid:** build `build/pi-archive-repo` on the **runner host** (Ubuntu 24.04 has dpkg-dev) and
bind-mount it. The container only adds the `file:` source line.

### Pitfall 12: rpi-eeprom (scope statement, not a code change)
**What it means:** pinning `rpi-eeprom 28.31-1` bounds which bootloader images exist on the
device. It does not stop `rpi-eeprom-update.service` (`rpi-eeprom-update -s -a`, enabled via
`multi-user.target`) from flashing the pinned package's `default` image (`pieeprom-2026-05-26`)
at boot on any device whose EEPROM is older. `FIRMWARE_RELEASE_STATUS` in
`/etc/default/rpi-eeprom-update` selects `default` versus `latest` within the package. Automatic
updates stop only with `systemctl mask rpi-eeprom-update` or the bootloader `FREEZE_VERSION`
config.
**Consequence to record:** bumping the rpi-eeprom pin EEPROM-flashes every device at its next
boot, and an EEPROM write sits **outside A/B rollback**. Slot B cannot undo it.
**In scope:** documenting this in the runbook and ADR.
**Out of scope:** changing the service state. Masking it is a product decision for Joe, listed
below.

### Pitfall 13: Gitignore and PR-size accounting
- Add `third_party/pi-archive/*.deb` to `.gitignore` in the PR that creates the directory.
- The reference re-record in the checkpoint moves about 3 pin rows and adds about 89 (plus the
  prestera row). Budget that PR at around 100 generated lines.
- Pre-warn DEV agents that banlist-sensitive strings (the org URL, the build host name) must not
  appear in new comments or `Documentation=` lines (MEMORY: dev_agents_trip_banlist).

## Code Examples

### Stage0 overlay, pinned branch (replaces the raspi.list line in 00-run.sh)
```bash
# Source: pattern verified in debian:bookworm arm64 container, 2026-09-25
PI_REPO_IN_ROOTFS="/var/local/arlowe-pi-archive"
case "${ARLOWE_PI_ARCHIVE_MODE:-pinned}" in
	record)
		install -m 644 files/raspi.list "${ROOTFS_DIR}/etc/apt/sources.list.d/"
		sed -i "s/RELEASE/${RELEASE}/g" "${ROOTFS_DIR}/etc/apt/sources.list.d/raspi.list"
		;;
	pinned)
		[ -n "${ARLOWE_PI_REPO:-}" ] && [ -d "${ARLOWE_PI_REPO}" ] || { echo "[FAIL] ARLOWE_PI_REPO …" >&2; exit 1; }
		rm -rf "${ROOTFS_DIR}${PI_REPO_IN_ROOTFS}"
		install -d "${ROOTFS_DIR}${PI_REPO_IN_ROOTFS}"
		cp "${ARLOWE_PI_REPO}"/*.deb "${ARLOWE_PI_REPO}"/Packages "${ARLOWE_PI_REPO}"/SHA256SUMS "${ROOTFS_DIR}${PI_REPO_IN_ROOTFS}/"
		( cd "${ROOTFS_DIR}${PI_REPO_IN_ROOTFS}" && sha256sum --quiet -c SHA256SUMS )
		rm -f "${ROOTFS_DIR}/etc/apt/sources.list.d/raspi.list"
		echo "deb [trusted=yes] file:${PI_REPO_IN_ROOTFS} ./" > "${ROOTFS_DIR}/etc/apt/sources.list.d/arlowe-pi-archive.list"
		;;
	*) echo "[FAIL] unknown ARLOWE_PI_ARCHIVE_MODE='${ARLOWE_PI_ARCHIVE_MODE}'" >&2; exit 1 ;;
esac
```
The `raspberrypi.gpg.key` install and the `on_chroot` `update`/`dist-upgrade` block stay verbatim.

### Host-side repo build
```bash
# scripts/lib/pi-archive-repo.sh (sketch)
out="${REPO_ROOT}/build/pi-archive-repo"; rm -rf "${out}"; mkdir -p "${out}"
# for each manifest entry (packages + resolve_only): cp "${cache}/${filename}" "${out}/"
( cd "${out}" && dpkg-scanpackages --multiversion . /dev/null > Packages 2>scan.err )
# Cross-check: stanza count == manifest entries, and every stanza's SHA256 equals the manifest's.
# The index then carries the same digests the manifest pins, and apt enforces them at install.
( cd "${out}" && sha256sum *.deb > SHA256SUMS )
```
`dpkg-scanpackages` warns `Packages in archive but missing from override file`. That is expected
with `/dev/null` overrides; filter it and don't treat it as failure.

## Open Questions

1. **Durable mirror location.**
   - Known: the build host cache plus, after 07.3-05, the CI cache (which evicts after 7 days
     unused) are the only copies. Neither is durable, and the goal says "bytes the project
     controls".
   - Unclear: where the durable copy should live (private GitHub release assets? object storage?).
     Redistribution is plausible for all 92 (GPL/LGPL/MIT plus redistributable firmware), but
     `firmware-*` and `raspi-firmware` licences should be read before publishing anywhere.
   - Recommendation: out of scope for the SCs. `ARLOWE_PI_ARCHIVE_DIR` makes it pluggable. Joe
     decides.
2. **Mask `rpi-eeprom-update.service`?** EEPROM writes escape A/B rollback. Product decision;
   recommend a separate issue.
3. **Does export-image actually run on the build host?** HIGH confidence from code, unconfirmed
   from a log. The 07.3-07 checkpoint confirms it; the fix is a one-line NEW overlay entry.
4. **Stage2 package lists in CI resolution.** `resolve-twice.sh` resolves only the stage0
   firmware list and stage-arlowe's list, not upstream stage1/stage2 (not in the checkout). The
   Pi packages that enter only through stage2 (gpiozero, pigpio, rpi-eeprom, raspi-utils, …) are
   therefore not in the CI determinism claim; the full build is their evidence. Cloning pi-gen at
   `PIGEN_REF` in CI would close this. Probably worth doing later, not in 7.3.
5. **`.github/workflows/build-image.yml` bypasses the overlay entirely.** It uses
   `usimd/pi-gen-action` on the unpinned `arm64` branch. It is tag-triggered only, but any image
   it produces carries none of the 7.2/7.3 pins. Flag it; it is out of scope.
