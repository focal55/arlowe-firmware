Tone as `phase-07.2-build-pinning.md`: concrete commands, and what each failure means.

**§1 Where the Pi-side pins live.** `third_party/pi-archive/manifest.yml` is generated; never hand-edit it. The kernel and the Debian snapshot are in the 07.2 runbook. raspi-firmware is the bootloader (start.elf, fixup.dat, bootcode.bin). Include the ten-hour drift history and the `liblgpio1` exact-version dependency that no manifest pinned before this phase.

**§2 Before any build.**
- `dpkg-dev` must be installed.
- On a fresh host, run `ARLOWE_PI_ARCHIVE_FETCH=1 scripts/verify-third-party.sh` (about 230 MiB).
- Run `sudo rm -rf build/pi-gen-work` before every full build. A stale stage0 keeps its old `+rpt` packages, and record and pinned builds alternate during a bump.

**§3 Reading a failure.** One entry per failure message:
- The Pi gate: a live source was declared, there is no flat-repo list, or an off-pin list exists.
- The check reports silent substitution, an unattributed package, an installed resolve-only package, or flat-index drift.
- pi-gen stops with `Unable to locate package` or `has no installation candidate` for a Pi-only name. The manifest lacks that package; usually a stage list changed. Fix it by bumping through record mode.
- The daily retention workflow's issue `Pi archive pool dropped a pinned deb`. Local caches are now the only copies, so mirror immediately.
- The swap-back failure.

**§4 Bumping the Pi pins.**
1. Destroy the work dir.
2. Run `ARLOWE_PI_ARCHIVE_MODE=record scripts/build-image.sh`. It exits 3 and writes `build/pi-archive.manifest.candidate` plus a diff. **Step 1 still verifies the currently pinned debs in record mode.** This is by design (a gate that a mode flag can skip gets skipped). On a host that has built before, the cache is already warm.
3. Review the diff against the checklist in §5 and §6.
4. Copy the candidate into place and run `ARLOWE_PI_ARCHIVE_FETCH=1 scripts/verify-third-party.sh`.
5. Destroy the work dir and run a pinned build. Re-record the inputs reference with `ARLOWE_INPUTS_ACCEPT=1`, but only after reading the pkg-row diff.
6. Commit the manifest and the reference together.
7. On a `PIGEN_REF` bump, re-run the removal-marker check: take every `-`-suffixed token across the upstream stage lists, confirm it is not installed, and confirm it is carried under `resolve_only`.

**§5 Security (the section SC5 exists for).**
- `libc6`, `libpam*`, `network-manager` and `bluez` ship as `+rptN+deb12uM`. `rpt` sorts above `deb`, so these outrank EVERY Debian `+deb12uN`. A Debian glibc DSA reaches the image only when Raspberry Pi rebuilds AND this manifest moves.
- `openssl` (`~deb12uN+rpt1`, exact version from the manifest) is the opposite: a later Debian `~deb12uN+1` outranks it. After a Debian snapshot bump, apt would silently flip its origin to Debian. The check's forward direction then fails the build.
- Therefore evaluate a Debian snapshot bump and a Pi pin bump together, never one alone.
- How to watch: the Debian security tracker and the DSA feed for glibc, openssl, pam and zlib; the `moved` lines from `tests/phase-07.3/probe-pi-archive.sh --state` for Pi rebuilds.
- Say plainly that until the owner sets a cadence, the image's libc6 and openssl change only when someone happens to bump them. Link the 07.2 snapshot-advance open question.

**§6 rpi-eeprom.**
- Quote the package's `FIRMWARE_RELEASE_STATUS="default"` and `rpi-eeprom-update.service` (`rpi-eeprom-update -s -a`, enabled via `multi-user.target`), using the version from the manifest.
- Pinning bounds which bootloader images exist; it doesn't stop the flash.
- A bump EEPROM-flashes every device at its next boot, and slot B cannot undo that.
- Any diff that touches `rpi-eeprom` needs explicit sign-off.
- Masking the service is an open product decision.

**§7 Retention and mirroring.**
- The cache order and `ARLOWE_PI_ARCHIVE_DIR`.
- The CI cache is evicted after 7 days unused.
- The daily retention workflow.
- "Bytes the project controls" is weak until a durable mirror exists (a p1 follow-up). Check licences for `firmware-*` and `raspi-firmware` first.

**§8 What a shipped device's apt sees**, and why `apt upgrade` on a device is unsupported.
