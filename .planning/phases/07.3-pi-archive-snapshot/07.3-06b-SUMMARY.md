## Prose carried forward (for 07.3-07b's runbook)

The deleted `third_party/rpt-packages/manifest.yml` held prose that no longer exists anywhere outside git history (`git show f6419a3:third_party/rpt-packages/manifest.yml`). 07b should put these points in the pin-bump runbook:

1. **raspi-firmware is the bootloader.** It ships start.elf, fixup.dat and bootcode.bin, the first code the device runs. Leaving it unpinned is a reproducibility hole and a supply-chain hole.
2. **The ten-hour drift.** raspi-firmware moved 1:1.20260907 -> 1:1.20260915 between two builds about ten hours apart with nothing in the repo changed. The inputs gate caught it, but the bump had to be accepted because there was nothing to pin to. archive.raspberrypi.com is a rolling index with no snapshot service (snapshot.raspberrypi.com and snapshot.raspberrypi.org both returned HTTP 000).
3. **The resolve-twice exit-100 story.** apt exits 100 on the whole set when any one package can't be resolved. So the two Pi-only packages didn't just go unmeasured, they silently stopped resolve-twice from measuring the other 26. The gate read as "28 packages pinned" while it pinned nothing. (06a removed the exclusion. This is the reason it existed.)
4. **Confirm digests by hashing the served bytes.** Digests were taken from Packages.gz and then confirmed by downloading each file and hashing it (2026-09-25). This is not ceremony. The piper pin in runtime/tts/manifest.yml was recorded from a local file, never fetched, and matched no upstream artifact.
5. **The Pi 5 GPIO stack has no Debian fallback.** Debian's python3-rpi.gpio 0.7.1 predates BCM2712 and can't address a Pi 5. python3-rpi-lgpio provides the module named RPi.GPIO over lgpio. (00-packages-nr still says this. It is listed here so the runbook's "why these are Pi-only" section is complete.)
