# Phase 7.3 Plan 07a: Record mode and ADR-0010 Summary

**`ARLOWE_PI_ARCHIVE_MODE=record` now regenerates the Pi manifest from the rootfs's own dpkg status and apt-verified live lists through a fixture-tested library function, prints the diff, and exits 3 before the Pi gate and partitioning. ADR-0010 records the mechanism, the SC3 split and the weak-sense caveat on controlled bytes.**

## Accomplishments

- `pi_archive_record_candidate`:
  - collects `archive.raspberrypi.com_*binary-arm64_Packages*` and `snapshot.debian.org_*binary-arm64_Packages*` lists with `_pi_lists`, and needs at least one of each;
  - runs `pi-archive-manifest.py generate --installed-status` with `--allow-local` from `PI_LOCAL_PACKAGES`, `--resolve-only firmware-marvell-prestera` and the Pi pool base;
  - propagates the generator's rc, then prints `diff -u MANIFEST OUT` or "identical to the committed manifest".
- `build-image.sh`:
  - accepts `pinned` or `record`, and warns up front in record mode;
  - skips the dpkg-scanpackages preflight, paths map and repo build in record mode, and logs that Step 1 verified the pinned debs anyway;
  - exports `ARLOWE_PI_REPO=""`, which is still forwarded across sudo;
  - calls the library right after `ok "Debian resolution pinned"`, chowns the candidate, prints next steps and `exit 3`.
- ADR-0010 (151 lines, Proposed) and a "Superseded in part" note in ADR-0009.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] Stale candidate removal**
- **Found during:** Task 1 GREEN
- **Issue:** The generator writes OUT only on success. A failed record run would leave the previous run's `build/pi-archive.manifest.candidate` in place, and it would look current.
- **Fix:** `rm -f "${out}"` at the top of `pi_archive_record_candidate`. `[record-no-pi-lists]` asserts that no candidate exists after a failure.
- **Commit:** abcf4da

## Residual Risk

- **Record mode is exercised only by fixtures and one extracted-call-line run, never inside pi-gen.** Unverified end to end:
  - that stage0's `apt-get update` in the chroot leaves `archive.raspberrypi.com_…_binary-arm64_Packages` under a name the glob matches, with a suffix the generator accepts (plain, .gz or .xz; .lz4 is refused);
  - that `firmware-marvell-prestera` is resolvable exactly once in the live list;
  - that the sudo/chown path works on the build host.
- A record build's rootfs leaves `raspi.list` live and has no flat repo. That work dir must be destroyed before the next pinned build (Pitfall 4). Exit 3 stops the script, but it does not clean the work dir.

## Handoff for 07.3-07b (runbook)

Record build, from a destroyed work dir:
```
sudo rm -rf build/pi-gen-work
ARLOWE_PI_ARCHIVE_MODE=record scripts/build-image.sh
```

Messages and exit codes to document:
- Start: `[WARN] RECORD MODE: Pi packages resolve from the live archive.raspberrypi.com, unpinned.` and `[WARN] The build stops after the Debian gate with exit 3 and produces no image.`
- After Step 1: `Record mode: Step 1 verified the currently pinned Pi debs anyway, by design; no flat repo is built.` Step 1 still needs check 8's pinned debs cached; on a cold host, run `ARLOWE_PI_ARCHIVE_FETCH=1 scripts/verify-third-party.sh` first.
- After the Debian gate:
  - the section header `=== Pi archive record mode: candidate manifest ===`;
  - the generator line `[pi-archive] N packages, 1 resolve_only; skipped: …`;
  - then either a `diff -u` against `third_party/pi-archive/manifest.yml`, or `[OK] candidate … is identical to the committed manifest; no pin moves.`;
  - then `Candidate: build/pi-archive.manifest.candidate`, the next-steps lines, `[FAIL] RECORD MODE: candidate written; no image is produced from the live archive.` and **exit 3**. Exit 3 is the success outcome of a record build.
- **exit 1** with `Record mode could not generate a candidate (see above).` Causes:
  - `[FAIL] record mode needs archive.raspberrypi.com and snapshot.debian.org binary-arm64 lists … found X and Y. Did stage0 run with ARLOWE_PI_ARCHIVE_MODE=record?`;
  - generator `[pi-archive] FAIL …` lines (rc 1), e.g. an unattributed package, "both archives carry it with different bytes", armhf, or prestera resolving to anything but exactly one version;
  - generator `[pi-archive] ERROR …` (rc 2), e.g. an .lz4 list or an unreadable input.
- An unknown mode → **exit 1**, before Step 1: `ARLOWE_PI_ARCHIVE_MODE='…' is not accepted; use 'pinned' or 'record'.`

The next steps printed by the script:
1. review the diff;
2. copy the candidate over `third_party/pi-archive/manifest.yml`;
3. run `ARLOWE_PI_ARCHIVE_FETCH=1 scripts/verify-third-party.sh`;
4. destroy the work dir and rebuild in pinned mode.

The runbook should also cover:
- the security ordering (ADR-0010 consequence a);
- the rpi-eeprom fleet flash (b);
- evaluating a Debian snapshot bump together with a Pi bump;
- that a candidate carrying a kernel row is impossible by design, because kernel names are skipped against the kernel manifest.
