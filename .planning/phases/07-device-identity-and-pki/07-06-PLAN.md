<feature>
  <name>Device keypair, CSR, and certificate storage</name>
  <files>runtime/lib/arlowe_pki.py, runtime/lib/tests/test_arlowe_pki.py</files>

  <behavior>
Use the `cryptography` library. Do not shell out to `openssl` and string-munge its output: there is
no shell-injection surface in a library call, error handling is deterministic, and `cryptography` is
already the ecosystem standard.

**API compatibility floor.** The image runs system `python3` with Debian bookworm's
`python3-cryptography` (38.0.4) — `/opt/arlowe/venvs` is empty on the built image, so nothing
pip-installs the 43.x pinned in `runtime/lib/requirements.txt` for CI. Restrict this module to APIs
present in 38.0.4: `ec.generate_private_key`, `ec.SECP256R1`, `x509.CertificateSigningRequestBuilder`,
`x509.Name`, `x509.NameAttribute`, `NameOID.COMMON_NAME`, `serialization.Encoding.PEM`,
`serialization.PrivateFormat.PKCS8`, `serialization.NoEncryption`,
`serialization.load_pem_private_key`, `x509.load_pem_x509_csr`, `x509.load_pem_x509_certificate`,
`hashes.SHA256`. Do **not** use `x509.verification` (added in 42) or `not_valid_after_utc` /
`not_valid_before_utc` (added in 42 — use `not_valid_after` / `not_valid_before` and treat them as
naive UTC). Note this floor in the module docstring.

**`ensure_keypair() -> ec.EllipticCurvePrivateKey`**
- If `KEY_PATH` exists, load it with `serialization.load_pem_private_key(..., password=None)` and
  return it.
- Otherwise `ec.generate_private_key(ec.SECP256R1())` and persist via `arlowe_identity.write_secret`
  as PEM / PKCS8 / NoEncryption.
- P-256 is within AWS IoT's accepted set (RSA >= 2048, or NIST P-256/P-384/P-521) and is the
  cheapest of them on a Pi 5.
- `write_secret` uses `O_EXCL` and an explicit `chmod 0600`, so the key mode is independent of the
  process umask. This matters: systemd's default `UMask` is `0022` and Python's default file mode is
  `0666 & ~umask`, which would produce `0644` and fail SC3's exact-0600 check. The unit in plan
  07-08 also sets `UMask=0077`; both belts are deliberate.
- The key is never returned as bytes, never logged, and never written anywhere but `KEY_PATH`.
  Add a module-level comment saying so — this is the file whose escape is the entire threat model.

**`ensure_csr(device_id: str) -> str`** returning the CSR PEM.
- If `CSR_PATH` exists and its subject CN already equals `device_id`, return it unchanged.
- If `CSR_PATH` exists with a different CN, that is a real inconsistency: raise
  `IdentityMismatch`. Do not silently regenerate — a CN that does not match the persisted device-id
  means something upstream is wrong and the operator needs to know.
- Otherwise build:
  `x509.CertificateSigningRequestBuilder().subject_name(x509.Name([x509.NameAttribute(NameOID.COMMON_NAME, device_id)])).sign(key, hashes.SHA256())`
  and persist the PEM with `write_secret`.
- Document that the CN is **human-facing provenance only**: AWS is not documented to preserve the
  CSR subject verbatim in the issued certificate, and authorization binds to the IoT Thing name and
  certificate ID instead (ADR-0007). A future reader must not build an authorization decision on
  the CN.

**`store_certificate(pem: str) -> None`**
- Validate it parses as an X.509 certificate before writing anything. A broker returning garbage
  must not leave a corrupt `device.crt` behind.
- Validate the certificate's public key matches the on-disk private key (see below) before writing.
- Write with `write_secret` at 0600. `write_secret` raises `FileExistsError` on an existing path, so
  replacement is an explicit `CERT_PATH.unlink()` inside this function, guarded and commented — a
  re-provision after revocation is a legitimate operation.
- 0600 for a certificate is stricter than necessary (a cert is public), but SC3 states 0600 and the
  build gate in plan 07-04 tests for exact equality. Honour the criterion literally; note the
  reasoning in a comment so nobody "fixes" it to 0644 later.

**`load_certificate()`**, **`certificate_matches_key(cert, key) -> bool`** (compare
`public_key().public_numbers()`), **`certificate_summary() -> dict`** returning
`{"subject_cn", "issuer_cn", "serial_number", "not_valid_before", "not_valid_after", "fingerprint_sha256"}`
for `arlowe-identity status` and `boot-check`. `certificate_summary` must never touch the private key.
  </behavior>

  <implementation>
**RED**: write `runtime/lib/tests/test_arlowe_pki.py` first and confirm failure. Use the
`ARLOWE_IDENTITY_DIR` + module-attribute monkeypatch idiom established in
`test_arlowe_identity.py`. Required cases:
- `ensure_keypair` creates a P-256 key; `isinstance(key.curve, ec.SECP256R1)`.
- Called twice it returns the same key (compare private numbers) and does not rewrite the file.
- Under `os.umask(0o000)`, `KEY_PATH` is exactly `0o600`. Same for `CSR_PATH` and `CERT_PATH`.
- `ensure_csr` produces a CSR whose subject CN equals the device-id, signed with SHA-256, and whose
  signature verifies (`csr.is_signature_valid`).
- `ensure_csr` called twice returns byte-identical PEM.
- `ensure_csr` with a pre-existing CSR carrying a different CN raises `IdentityMismatch`.
- `store_certificate` with non-PEM garbage raises and leaves no `device.crt` on disk.
- `store_certificate` with a well-formed certificate for a *different* keypair raises and leaves no
  `device.crt`.
- Happy path: build a throwaway self-signed certificate in-test over the device's own public key,
  store it, `load_certificate` round-trips, `certificate_matches_key` is True, and
  `certificate_summary()` reports the expected CN and fingerprint.
- Re-provision: `store_certificate` twice with two different valid certificates succeeds and the
  second wins.
- **No key leakage**: assert the private key PEM string does not appear in
  `repr(certificate_summary())` and does not appear in any file under the identity dir other than
  `device.key`.

Do not commit any `.key`, `.crt`, `.csr` or `.pem` fixture. Generate everything in-test. Plan
07-04's build gate treats those extensions as violations, and a committed key fixture anywhere that
gets copied into the image is exactly the failure this phase exists to prevent.
