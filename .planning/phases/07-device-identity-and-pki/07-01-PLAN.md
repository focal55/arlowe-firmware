  <name>Task 1: Write ADR-0007 recording the managed-PKI selection and cert lifecycle</name>
  <files>docs/architecture/0007-managed-pki-service-selection.md</files>
  <action>
Write ADR-0007 in the house style used by ADR-0004..0006: `# ADR-0007: <title>`, an HTML
`<!-- status: proposed -->` comment, then bold `**Status:**` / `**Date:**` / `**Phase:**` /
`**Closes:**` lines, then `## Context` / `## Decision` / `## Consequences` (split into
`**Positive:**` and `**Negative / known constraints:**`) / `## References`.

Status is **Proposed**, not Accepted. Plan 07-09 amends it to Accepted after the staging run
produces measured evidence (this mirrors ADR-0005's amendment convention). Say so in the ADR.

Required content, all of it non-negotiable:

1. **Decision:** AWS IoT Core's native Amazon-Root-CA certificate issuance, via the
   `iot:CreateCertificateFromCsr` API. Name the API explicitly.
2. **Explicitly rule out AWS Private CA on cost** — $400/month general-purpose, $50/month
   short-lived (7-day max validity, which would force a renewal daemon). State that a reader who
   hears "AWS PKI" and reaches for Private CA lands on a ~$4,800/year line item before the first
   unit ships. This distinction is the single most load-bearing sentence in the document.
3. **Rule out the alternatives with their reasons:** Google Cloud IoT Core (retired 2023-08-16);
   Let's Encrypt / ACME (category error — ACME proves control of a public DNS name to issue a
   *server* cert; an Arlowe behind NAT has no DNS name and needs a *client* cert); self-hosted
   step-ca and Vault (rejected on *operational custody* grounds — you would own root-key custody,
   HA, backup and CRL hosting, and a CA outage becomes a pairing outage; do NOT imply the software
   is untrustworthy); Smallstep Certificate Manager (pricing is sales-gated, unplannable);
   Azure IoT Hub + DPS as the runner-up with its free-tier-cannot-be-upgraded trap.
4. **Cert lifecycle:**
   - Issuance: device generates P-256 keypair + CSR locally; an owner-token-authenticated broker
     calls `CreateCertificateFromCsr` + `AttachThingPrincipal` + `AttachPolicy`.
   - Renewal: **none**. AWS-issued IoT certs expire 2049-12-31T23:59:59Z. Rotation is deliberate,
     not scheduled. No renewal daemon, no ACME client, no cron.
   - Revocation: `aws iot update-certificate --certificate-id X --new-status REVOKED`. Status is
     checked server-side at authentication time. The device carries zero revocation logic — no
     CRL, no OCSP, no device-side deny list.
5. **Bootstrap trust — no claim certificates.** State the reasoning as a fact about this project's
   build, not a vendor claim: Phase 6 ships ONE image to every unit, so any credential in the image
   is on every unit and is extractable by anyone who buys one and reads the SD card. AWS fleet
   provisioning by claim is therefore rejected. The device is **token-agnostic**: it accepts a
   bearer token and a broker URL and does not care who issued the token. Record explicitly that the
   owner-account question is DEFERRED to Phase 8, and that a hand-minted token for a single unit and
   a token from a future account system must both work unchanged.
6. **The security tradeoff, verbatim and unhedged.** Include this paragraph essentially as written:

   > The device private key is generated in software and stored as a file on an unencrypted ext4
   > partition (`/var/lib/arlowe/identity/`) on a removable SD card. The Pi 5 has no TPM and no
   > secure element, so there is no hardware protection available. Anyone with physical possession
   > of the SD card can extract the device private key and impersonate that one device. The
   > mitigations are (a) blast radius is one device, not the fleet, because there is no shared
   > secret; (b) the owner can revoke that device's cert, which is honoured by the PKI within one
   > polling interval; (c) the cert authorizes only narrowly-scoped cloud reads — it grants no
   > access to other owners' data and no access to the device's local conversation cache. This is
   > the standard security posture for consumer hardware without a secure element and is accepted
   > for v1.

7. **The revocation-latency bound, with a number.** Revocation takes effect within
   `max(poll_interval, remaining_credential_lifetime)`. Record the design rule that makes this
   collapse to a single number: the IoT role alias is created with
   `credentialDurationSeconds = 900` (the minimum AWS allows), `identity.poll_interval_seconds`
   defaults to 3600, and the device client holds credentials only in process memory for the life of
   a single poll. Therefore the guaranteed bound is **one polling interval**, and SC4 tests against
   that number.
8. **Identity binding.** CSR subject is `CN=<device-id>`, but authorization binds to the IoT Thing
   name and certificate ID, which are under our control. Record that whether AWS preserves the CSR
   CN verbatim is an open question to be answered empirically in plan 07-09 and recorded here as an
   amendment.
9. **Escape hatch.** AWS IoT supports registering your own CA later (BYOC/JITP), so a migration to a
   self-controlled hierarchy is possible without re-flashing, by issuing a second cert over the
   existing authenticated channel.
10. **Open questions carried forward,** flagged as unverified: whether provisioning and the
    credentials provider are genuinely unbilled (absence from a pricing page is weaker evidence than
    an explicit "no charge" statement — the owner reads a real bill before Accepted).

`docs/architecture/**` is on `.sanitize-allowlist`, so the ADR may quote freely; no founder literals
are needed here anyway.

<task type="auto">
  <name>Task 2: Add the identity config block as an OPTIONAL top-level key</name>
  <files>config/schema.yml, config/defaults.yml</files>
  <action>
Add an `identity` object to `config/schema.yml` under `properties:`, placed after `ota:`.

**Do NOT add `identity` to the schema's top-level `required` list.** `config/schema.yml` has
`additionalProperties: false` and an 8-entry top-level `required` list that
`runtime/dashboard/app/audio/save-body.ts` hard-codes as `REQUIRED_KEYS`. `POST /api/config`
AJV-validates the raw body and returns 422 on a partial body. A 9th required key without a matching
dashboard edit 422s every dashboard audio save. Optional + always present in `defaults.yml` gives
the same guarantee via deep-merge with zero dashboard risk.

Schema block:

```yaml
  identity:
    type: object
    additionalProperties: false
    description: >
      Device identity / PKI knobs (ADR-0007). This key is intentionally NOT in the
      top-level `required` list: defaults.yml always supplies it, so the merged dict
      always carries it, while a raw partial body from the dashboard stays valid.
      See runtime/dashboard/app/audio/save-body.ts REQUIRED_KEYS.
    required:
      - provisioning_url
      - credentials_endpoint
      - role_alias
      - poll_interval_seconds
    properties:
      provisioning_url:
        type: string
        default: ""
        description: >
          Owner-authenticated CSR-broker endpoint. Empty until set at pairing (Phase 8).
          Used as the default for `arlowe-identity provision --ca-broker-url`.
          Never a tracked literal: the URL is account-identifying (see ADR-0007).
      credentials_endpoint:
        type: string
        default: ""
        description: >
          Owner override for the IoT credentials-provider host. Empty by default; the
          value written by `arlowe-identity provision` into
          /var/lib/arlowe/identity/identity.json is used when this is empty.
          Account-identifying — never a tracked literal.
      role_alias:
        type: string
        default: ""
        description: >
          Owner override for the IoT role alias. Empty by default; the provisioned
          value in identity.json is used when this is empty.
      poll_interval_seconds:
        type: integer
        minimum: 900
        maximum: 86400
        default: 3600
        description: >
          Cloud polling interval. This is the number SC4 tests against: revocation
          takes effect within max(poll_interval, remaining_credential_lifetime), and
          the role alias is provisioned with credentialDurationSeconds=900 <= this
          value, so the guaranteed bound is one polling interval (ADR-0007).
```

Add the matching block to `config/defaults.yml` after `ota:`:

```yaml
identity:
  provisioning_url: ""
  credentials_endpoint: ""
  role_alias: ""
  poll_interval_seconds: 3600
```

Do not touch `runtime/dashboard/app/audio/save-body.ts` or its `CONFIG_DEFAULTS`. The block is
optional precisely so that file does not have to change; `buildSaveBody` spreads `currentConfig`,
so an identity-bearing overlay round-trips untouched.
  </action>

`PYTHONPATH=runtime/lib ARLOWE_SCHEMA_PATH=config/schema.yml ARLOWE_DEFAULTS_PATH=config/defaults.yml ARLOWE_CONFIG_PATH=/nonexistent python3 -c "from arlowe_config import load; c=load(); assert c['identity']['poll_interval_seconds']==3600; print('ok')"`
`grep -A 12 "^required:" config/schema.yml | grep -c identity` returns 0
  </verify>
  <done>The merged config carries `identity` with all four keys; `identity` is absent from the schema's top-level `required` list; the loader validates a config both with and without an identity overlay.</done>
