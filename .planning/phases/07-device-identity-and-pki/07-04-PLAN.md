never appears under `/opt/arlowe/`.

image. Building it early means every subsequent plan is developed under the gate.

`boot-check`, and a self-test for the assertion.

<task type="auto">
  <name>Task 1: Write the identity-store assertion and its self-test</name>
  <files>scripts/lib/identity-store-check.sh, tests/phase-7/test-identity-store-check.sh</files>
  <action>
Create `scripts/lib/identity-store-check.sh` defining one function:

```
check_identity_store <root>
```

`<root>` is a filesystem prefix — `/` on a running device, or a mountpoint when scanning an image.
The function returns 0 on clean, 1 on violation, and prints GitHub-Actions-style `::error` lines
plus a human line on stderr, matching the reporting style already used by `scripts/sanitize/check.sh`.

It asserts, in order:

1. **No key material under `${root}/opt/arlowe`.** Find any file matching `*.key`, `*.pem`,
   `*.crt`, `*.csr`, `*.p12`, `*.pfx`, or named `device-entropy`, `device-id`, `identity.json`.
   Any hit is a violation. This is the literal SC3 requirement: "never appear in `/opt/arlowe/`".
   Use `find` with `-type f` so a symlink pointing out of the tree is reported as a link, not
   followed.
2. **No key material at `${root}/etc/arlowe` or `${root}/boot` or `${root}/boot/firmware`.**
   `/boot/firmware` is a FAT partition with no permission bits at all — a key there would be
   world-readable by construction. This assertion is not in the SC text but is the same class of
   defect and costs one more `find`.
3. **Mode check on `${root}/var/lib/arlowe/identity/`.** If the directory exists, every regular file
   inside it must be exactly `0600`, and the directory itself exactly `0700`. Use
   `stat -c '%a'` (GNU coreutils; the build host and the device are both Linux).

   **This check DOES fire at image-build time — verify that assumption rather than assuming it
   away.** `scripts/provision/install-arlowe-fs.sh:71` runs
   `install -d -o arlowe -g arlowe -m 0700 /var/lib/arlowe/identity` inside the pi-gen chroot
   (invoked from `pi-gen/stage-arlowe/01-runtime/00-run-chroot.sh:59`), so the directory exists **in
   the slot-A rootfs** that the build scans, at `arlowe:arlowe 0700`. The separate owner_state
   partition (p4) is mounted *over* that path at runtime; the chroot-created directory underneath is
   what a slot-A scan sees. So the expected build-time shape is: **present, a directory, mode 0700,
   and empty** — and the self-test must assert exactly that shape, because it is the shape a real
   build produces.

   Treat "directory absent" as a violation under `--factory` (it means `install-arlowe-fs.sh` did
   not run, which is the F7 #18 silent-skip class all over again), and as a violation on a running
   device too. Do not paper over an absent directory with an informational pass — an absent identity
   directory is never correct on either surface.
4. **Emptiness on a factory image.** The directory exists under the scanned root (see above), so
   this assertion fires for real at build time, not hypothetically. If it contains
   `device.key`, `device-entropy`, `device-id`, `identity.json` or `device.crt`, that is a
   violation for an image scan: a factory image must ship with an EMPTY identity store, because one
   image is flashed to every unit and any material present would be identical on every unit. Gate
   this assertion behind a second argument, `check_identity_store <root> [--factory]`, so the same
   function serves both the build gate (with `--factory`) and a device check (without).

Shellcheck-clean is mandatory: `scripts/lib/*.sh` is already in the shellcheck job's glob in
`.github/workflows/pr-checks.yml`, so a violation goes red on the PR automatically.

Write `tests/phase-7/test-identity-store-check.sh` (follow the style of
`scripts/sanitize/test-check.sh`).

**Every fixture tree is constructed at test runtime under `mktemp -d` and removed on exit via a
`trap`. Nothing under `tests/phase-7/` is committed except the test script itself.** This is not a
style preference. The fixtures include files named `device.key` and `ca.pem`; committing them would
(a) trip plan 07-06's `git ls-files | grep -E '\.(key|crt|csr|pem|p12|pfx)$'` check — in the phase
whose entire purpose is preventing key-shaped files from being tracked — and (b) land them inside a
scanned path, since `pi-gen/stage-arlowe/01-runtime/00-run-chroot.sh:95` rsyncs `runtime/` into
`/opt/arlowe/runtime/` with no excludes. Generate every byte in the test; commit no `.keep`.

It asserts:
- a clean tree passes;
- a tree with `opt/arlowe/config/device.key` fails with exit 1;
- a tree with `opt/arlowe/runtime/lib/ca.pem` fails;
- a tree with `var/lib/arlowe/identity/device.key` at mode 0644 fails;
- the same file at 0600 passes;
- a tree with `var/lib/arlowe/identity/device-id` present fails under `--factory` and passes without;
- **the real build-time shape passes**: `var/lib/arlowe/identity/` present, a directory, mode 0700,
  and empty, with `--factory` — this is precisely what `install-arlowe-fs.sh` produces in the
  slot-A rootfs, so this case is the one that proves the gate will not false-alarm the next build;
- a tree where `var/lib/arlowe/identity/` is **absent** fails under `--factory`;
- the directory at mode 0755 instead of 0700 fails.
  </action>
  <verify>
`bash tests/phase-7/test-identity-store-check.sh` exits 0 and prints a pass line per case
`shellcheck scripts/lib/identity-store-check.sh` is clean
  </verify>
  <done>`check_identity_store` catches every violation class in the self-test and passes a clean tree, in both `--factory` and device modes — including the real build-time shape (`/var/lib/arlowe/identity` present, empty, 0700), which is what a slot-A scan will actually encounter. `git status --porcelain tests/phase-7/` shows only the test script; no fixture file is tracked.</done>

  <files>scripts/build-image.sh</files>
  <action>
Wire `check_identity_store` into `scripts/build-image.sh` **inside step 5**, after the
`check.sh --scan-dir` call succeeds and **before** `cleanup_loop` runs. Step 5 already loop-mounts
slot A and unmounts it at the end of the block; adding a separate numbered step would need a second
mount, and a second mount is exactly the hazard that cost a flash in July.

Specifically:
- `source "${SCRIPT_DIR}/lib/identity-store-check.sh"` near the top of the script, alongside the
  other `scripts/lib` sourcing.
- After `ok`-ing the sanitize gate and before `cleanup_loop`, call
  `check_identity_store "${SLOT_A_MOUNTPOINT}" --factory`, and on failure `fail`, `cleanup_loop`,
  `trap - EXIT`, `exit 1` — mirroring the existing sanitize-gate failure path exactly.
- Update the step-5 banner comment to say it now runs two gates.

**Do not change the mount to read-write.** The existing `sudo mount -o ro` must stay. A read-write
loop-mount rewrites the ext4 superblock after the `.bmap` has been generated, and `bmaptool flash`
then aborts on a checksum mismatch. That cost a full re-flash cycle once already.

Also update the header comment at the top of `build-image.sh` (the `measure both -> repartition(5)
-> clone A + seed models -> sanitize gate -> ...` summary line) so the pipeline description matches
what the script does.

  <name>Task 3: Add a check_identity block to boot-check</name>

  <action>
`runtime/cli/boot-check` is a ~97-line bash script with `check_service` / `check_port` helpers and
`PASS` / `FAIL` counters. Add a `check_identity` block in the same style, in a new
`IDENTITY:` section placed after `HARDWARE:`.

It must report:
- `/var/lib/arlowe/identity/` exists, is a directory, owned `arlowe:arlowe`, mode `0700`.
- `device-id` present and mode `0600` -> PASS; absent -> **WARN, not FAIL**.
- `device.key` / `device.crt` present and mode `0600` -> PASS; absent -> **WARN, not FAIL**.
- No key material under `/opt/arlowe` — reuse the assertion by sourcing
  `/opt/arlowe/runtime/lib/../../..`? No: `boot-check` runs from `/opt/arlowe/runtime/cli/` on the
  device and `scripts/lib/` is not installed into the image. Inline the `/opt/arlowe` find as a few
  lines rather than shipping the build-host library into the rootfs. Keep the find predicate list
  identical to `check_identity_store`'s and add a comment naming
  `scripts/lib/identity-store-check.sh` as the authority the two must agree on.

**Unpaired is not a failure.** A factory device has no cert and no device-id until first boot /
pairing, and `/etc/arlowe/config.yml` being absent is the established pre-pairing signal from
Phase 4. Key the expectation on that: if `/etc/arlowe/config.yml` is absent, a missing cert is
expected state and must report `OK (not yet paired)`, not `FAIL`. This repo already ships a
`boot-check` that tells a correctly-behaving unpaired device that 14 things are broken; do not add
a fifteenth.

Write structured JSON to `/var/lib/arlowe/state/identity-selfcheck.json`, following the
`audio-selfcheck.json` precedent established in Phase 5 for the Phase 11 dashboard health view.
Shape:
```json
{"paired": false, "identity_dir_ok": true, "device_id_present": true,
 "key_present": false, "cert_present": false, "modes_ok": true,
 "opt_arlowe_clean": true, "checked_at": "<ISO-8601 UTC>"}
```
Write it with `install -m 0644 -o arlowe -g arlowe` semantics or a `umask 0022` subshell — the JSON
is a status file, not a secret, and the dashboard reads it.

Do not touch the rest of `boot-check`. The pre-existing "0 passed, 14 failed on a healthy unpaired
device" problem is a real defect but it belongs to its own change.
