`scripts/pki/sc4-revocation-test.sh` runs the SC4 sequence and exits non-zero at the first step that
does not behave as SC4 requires. It sources `scripts/pki/.staging-env`, takes
`--identity-dir DIR` (defaulting to a fresh `mktemp -d`, so the harness can run on a dev host
without touching a real device's identity store) and `--broker-url URL`, and reads the owner token
from `ARLOWE_OWNER_TOKEN`.

**Resolve the CLI, and export the environment it needs. Both of these are load-bearing.**

```sh
IDENTITY_CLI="${IDENTITY_CLI:-./runtime/cli/identity}"
```

`arlowe-identity` is the `/usr/local/sbin` symlink that plan 07-08b installs **in the image**. It
does not exist on a dev host, where the binary is `./runtime/cli/identity`. Resolving through an
overridable variable makes the same harness run in both places: unset on a dev host, and
`IDENTITY_CLI=arlowe-identity bash scripts/pki/sc4-revocation-test.sh` on a provisioned device.
Never hard-code `arlowe-identity`.

The harness must export the full environment block before the first CLI call, copied from plan
07-08a's smoke-test line — `07-09` does not inherit it, and every one of these is a hard failure
without it:

```sh
export ARLOWE_IDENTITY_DIR="$IDDIR"
export ARLOWE_SERIAL_ROOT="${ARLOWE_SERIAL_ROOT:-runtime/lib/tests/fixtures/identity/all_three}"
export ARLOWE_LIB="${ARLOWE_LIB:-runtime/lib}"
export ARLOWE_DEFAULTS_PATH="${ARLOWE_DEFAULTS_PATH:-config/defaults.yml}"
export ARLOWE_SCHEMA_PATH="${ARLOWE_SCHEMA_PATH:-config/schema.yml}"
export ARLOWE_CONFIG_PATH="${ARLOWE_CONFIG_PATH:-/nonexistent}"
export PYTHONPATH="${ARLOWE_LIB}"
```

Why each is required, so nobody trims the block:
- `ARLOWE_DEFAULTS_PATH` / `ARLOWE_SCHEMA_PATH` — `arlowe_config.load()`
  (`runtime/lib/arlowe_config.py:25-27`) defaults to `/opt/arlowe/config/{defaults,schema}.yml` and
  raises `FileNotFoundError` when they are absent. Both `provision`'s `--ca-broker-url` config
  fallback and `resolve_endpoints` inside `fetch_credentials` go through `load()`, so the harness
  dies at step 2 on a dev host without these.
- `ARLOWE_CONFIG_PATH=/nonexistent` — pins the "pre-pairing, no overlay" state so a developer's
  local `/etc/arlowe/config.yml` cannot change what the harness measures.
- `ARLOWE_SERIAL_ROOT` — `read_serial()` has no source on a dev host: no `rpi-duid`, no devicetree
  `serial-number`, and x86 `/proc/cpuinfo` has no `Serial` field. Step 1 raises
  `IdentitySourceUnavailable` without it. On a real device leave it unset via the `:-` default
  being overridden, or better, pass the real root — the fixture is a dev-host affordance only.
- `ARLOWE_LIB` / `PYTHONPATH` — the CLI resolves the lib through `ARLOWE_LIB`; the in-process probe
  below is plain `python3` and needs `PYTHONPATH`. Set both to the same value.

On a provisioned device, override the block: `ARLOWE_LIB=/opt/arlowe/runtime/lib`,
`ARLOWE_DEFAULTS_PATH=/opt/arlowe/config/defaults.yml`,
`ARLOWE_SCHEMA_PATH=/opt/arlowe/config/schema.yml`, `ARLOWE_CONFIG_PATH=/etc/arlowe/config.yml`,
`ARLOWE_SERIAL_ROOT=/`, `IDENTITY_CLI=arlowe-identity`. The `${VAR:-default}` shape above is what
makes that possible without editing the script.

Sequence, with a timestamp printed before and after every step. **The order below is the order the
script must run in — there is exactly one revocation, and it happens after the credential cache has
been warmed, not before.** Revoking earlier makes the residual-validity measurement impossible to
capture, because the cache-warming call would itself raise `CertificateRevoked`.

1. `$IDENTITY_CLI init` in the temp identity dir. Assert `device-id`, `device.key`, `device.csr`
   exist at mode 0600 and the CSR subject CN equals the device-id
   (`openssl req -in .../device.csr -noout -subject`).
2. `$IDENTITY_CLI provision --ca-broker-url "$BROKER" --owner-token-file <fd>`. Assert exit 0 and
   that `device.crt` and `identity.json` now exist at 0600. Capture the `certificate_id`.
3. **Record the issued certificate's subject** — `openssl x509 -in device.crt -noout -subject -issuer`.
   This is the ten-minute experiment that settles the open question of whether AWS preserves the CSR
   CN verbatim. Record whatever is observed, including "it does not". Nothing depends on the answer
   (authorization binds to the Thing name and certificate ID), but an unrecorded ambiguity in a PKI
   design becomes a wrong assumption later.
4. `$IDENTITY_CLI check-cloud`. Assert exit 0 — this is the OTA-shaped cloud fetch succeeding with
   a valid certificate.

**Steps 5 through 8 are one Python process.** The credential cache in `arlowe_cloud` is
module-level and does not survive process exit, so warming it in one process and probing it in
another measures nothing. The revocation in step 6 therefore happens *inside* that process, by
shelling out to `scripts/pki/revoke.sh` with `subprocess.run`. Do not split this block across
several `python3 -` invocations, and do not move the revocation out to the shell.

```
python3 - "$CERT_ID" "$REVOKE_SH" <<'PY'
import json, subprocess, sys, time
from datetime import datetime
import arlowe_cloud as c
cert_id, revoke_sh = sys.argv[1], sys.argv[2]

# 5 - warm the cache while the certificate is still valid
warm = c.fetch_credentials()
expiration = warm["expiration"]                          # ISO-8601 from the CLI contract
expiration_epoch = datetime.fromisoformat(expiration).timestamp()

# 6 - the single revocation
revoked_at = time.time()
# capture_output: revoke.sh writes status to stdout, which would otherwise interleave
# with this probe's JSON return value that the shell parses.
rv = subprocess.run(["bash", revoke_sh, cert_id],
                    capture_output=True, text=True, check=True)
assert "REVOKED" in rv.stdout, f"revoke.sh did not observe REVOKED: {rv.stdout!r}"

# 7 - cached read, NO force_refresh: must still succeed
cached = c.fetch_credentials()
residual = expiration_epoch - revoked_at

# 8 - drop the cache and force a real exchange: must be refused.
# Bounded retry: AWS status propagation is not instantaneous, and a false
# "SC4 failed" here costs a whole live staging run.
propagation = None
deadline = time.time() + 120
while True:
    c.clear_credential_cache()
    try:
        c.fetch_credentials()
    except c.CertificateRevoked:
        propagation = time.time() - revoked_at
        break
    if time.time() > deadline:
        raise SystemExit("FAIL: cold-cache fetch still succeeded 120s after revocation")
    time.sleep(5)

assert residual > 0, f"residual validity is not positive ({residual}s) - tz-naive expiration?"
print(json.dumps({"revoked_at": revoked_at, "expiration": expiration,
                  "residual_validity_seconds": residual,
                  "in_process_propagation_seconds": propagation}))
PY
```

5. **Warm the cache and record the expiry.** In-process `fetch_credentials()` populates the
   module-level cache; record `expiration`. The certificate is still valid here — that is the whole
   point of doing this before the revocation.
6. **Revoke, once.** `scripts/pki/revoke.sh "$CERT_ID"`, called from inside the probe process.
   Pass it as an absolute path derived from `$0`'s directory, not the repo-relative literal in the
   sketch — the harness must not silently depend on being launched from the repo root for this one
   call. Assert the script reports the observed status as `REVOKED` (it re-reads with
   `describe-certificate` rather than assuming). Record `revoked_at`.
7. **Cached read — the half `check-cloud` cannot see.** Call `fetch_credentials()` **without**
   `force_refresh`. It must still return credentials, served from the cache: revoking a certificate
   does not retroactively invalidate an STS token already issued against it. Record
   `expiration - revoked_at` as the **residual credential validity**.
   Assert it is `<= 900s` (the `credentialDurationSeconds` plan 07-05a sets) and
   `<= poll_interval_seconds`. That inequality is the whole reason the bound collapses to one
   polling interval; if it does not hold, SC4 has not been met regardless of what step 9 prints.
   A step-7 call that *raises* is a FAIL, not a pass — it would mean the cache was bypassed and the
   measurement never happened.
8. **Cold-cache read — must be refused.** `clear_credential_cache()` then `fetch_credentials()`,
   retried every 5s for up to 120s; assert it raises `CertificateRevoked` within that window and
   record the elapsed time as **in-process propagation latency**. The retry is not optional: a
   single immediate attempt turns a few seconds of AWS status propagation into a reported SC4
   failure, during the one run that costs live resources. Only a window that expires is a FAIL. This is the in-process counterpart of step 9 and proves
   the refusal is attributable to revocation rather than to a stale cache.
9. **Auth-time refusal latency.** Back in the shell, poll `$IDENTITY_CLI check-cloud` every 15
   seconds for up to 5 minutes, measuring elapsed time from the `revoked_at` the probe printed.
   **Assert the exit code is exactly 6** (`CertificateRevoked`). Exit code 4 (`CloudUnavailable`) is
   a FAIL, not a pass — "the call failed" is not the criterion; "the call was refused because the
   certificate was revoked" is. `check-cloud` runs `fetch_credentials(force_refresh=True)` in a
   fresh process, so what this measures is how fast AWS began refusing **new** credential
   exchanges — the `force_refresh` path, which says nothing about already-issued tokens. Label it
   **"auth-time refusal latency (AWS status propagation)"**.

10. Print a PASS/FAIL summary table of all nine steps, with the two latency numbers **labelled
   separately** — "auth-time refusal latency" (step 9) and "residual credential validity" (step 7) —
   and the SC4 bound stated as `max(poll_interval, residual credential validity)`. Do not print a
   single unqualified "measured revocation latency"; that number does not exist.

Clean up the temp identity dir on exit. Never print the owner token or the secret access key.
Shellcheck-clean (`scripts/pki/*.sh` was added to the shellcheck glob in plan 07-05a).
