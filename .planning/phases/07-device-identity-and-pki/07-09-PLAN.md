<task type="auto">
  <name>Task 1: Write the SC4 harness and the staging runbook</name>
  <files>scripts/pki/sc4-revocation-test.sh, docs/operations/phase-7-pki-staging.md</files>
  <action>
`scripts/pki/sc4-revocation-test.sh` runs the SC4 sequence and exits non-zero at the first step that
does not behave as SC4 requires. It sources `scripts/pki/.staging-env`, takes
`--identity-dir DIR` (defaulting to a fresh `mktemp -d`, so the harness can run on a dev host
without touching a real device's identity store) and `--broker-url URL`, and reads the owner token
from `ARLOWE_OWNER_TOKEN`.

Sequence, with a timestamp printed before and after every step:

1. `arlowe-identity init` in the temp identity dir. Assert `device-id`, `device.key`, `device.csr`
   exist at mode 0600 and the CSR subject CN equals the device-id
   (`openssl req -in .../device.csr -noout -subject`).
2. `arlowe-identity provision --ca-broker-url "$BROKER" --owner-token-file <fd>`. Assert exit 0 and
   that `device.crt` and `identity.json` now exist at 0600. Capture the `certificate_id`.
3. **Record the issued certificate's subject** — `openssl x509 -in device.crt -noout -subject -issuer`.
   This is the ten-minute experiment that settles the open question of whether AWS preserves the CSR
   CN verbatim. Record whatever is observed, including "it does not". Nothing depends on the answer
   (authorization binds to the Thing name and certificate ID), but an unrecorded ambiguity in a PKI
   design becomes a wrong assumption later.
4. `arlowe-identity check-cloud`. Assert exit 0 — this is the OTA-shaped cloud fetch succeeding with
   a valid certificate.
5. `scripts/pki/revoke.sh "$CERT_ID"`. Assert the script reports the observed status as `REVOKED`
   (it re-reads with `describe-certificate` rather than assuming).
6. Poll `arlowe-identity check-cloud` every 15 seconds for up to 5 minutes, recording the elapsed
   time at which it first fails. **Assert the exit code is exactly 6** (`CertificateRevoked`).
   Exit code 4 (`CloudUnavailable`) is a FAIL, not a pass — "the call failed" is not the criterion;
   "the call was refused because the certificate was revoked" is. Print the measured latency.
7. Print a PASS/FAIL summary table of all six steps.

Clean up the temp identity dir on exit. Never print the owner token or the secret access key.
Shellcheck-clean (`scripts/pki/*.sh` was added to the shellcheck glob in plan 07-05).

`docs/operations/phase-7-pki-staging.md` is the runbook, in the style of
`docs/operations/phase-5-audio.md`. Sections: prerequisites; the exact command sequence
(`setup-staging.sh` -> generate the broker's self-signed TLS pair -> start `broker.py` ->
`sc4-revocation-test.sh` -> `teardown-staging.sh`); how to read the result; the teardown checklist;
and an **Evidence** section left empty for task 2 to fill.

Add `docs/operations/phase-7-pki-staging.md` to `.sanitize-allowlist` only if the captured evidence
genuinely needs a banned literal — it should not. Prefer redaction: the runbook must **not** contain
the AWS account id, the credentials-endpoint prefix, the broker URL, the owner token, or any secret
access key. Redact them as `<account-id>`, `<endpoint-prefix>`, `<broker-host>`. Certificate ids and
Thing names (which are device-ids) are fine — they are opaque and the resources are torn down.
  </action>
  <verify>
`shellcheck scripts/pki/sc4-revocation-test.sh` is clean
`bash -n scripts/pki/sc4-revocation-test.sh`
Running it with no `.staging-env` exits non-zero with a message naming the missing file
`grep -q "exit code is exactly 6\|-eq 6" scripts/pki/sc4-revocation-test.sh`
  </verify>
  <done>The SC4 sequence is a single runnable script that fails loudly on any step that does not match SC4, and distinguishes "refused because revoked" from "failed for another reason".</done>
</task>

<task type="auto">
  <name>Task 2: Run it against staging and capture the evidence</name>
  <files>docs/operations/phase-7-pki-staging.md, docs/architecture/0007-managed-pki-service-selection.md</files>
  <action>
With the owner's staging AWS profile configured (see `user_setup`), execute the runbook:

1. `AWS_PROFILE=... AWS_REGION=... bash scripts/pki/setup-staging.sh` -> `.staging-env`.
2. Generate the broker's self-signed P-256 TLS pair into a gitignored path; start `broker.py` with
   `ARLOWE_BROKER_TOKEN` set to a hand-minted random token. That hand-minted token is the point:
   it proves the device side is token-agnostic and needs no owner-account backend.
3. `bash scripts/pki/sc4-revocation-test.sh --broker-url https://localhost:<port>` with
   `ARLOWE_BROKER_CA_BUNDLE` pointing at the broker's self-signed cert.
4. Capture the full output.
5. `bash scripts/pki/teardown-staging.sh` and verify with `aws iot list-certificates` /
   `list-things` / `list-role-aliases` that nothing under the prefix remains. Paste that
   verification into the runbook — a staging teardown that was not checked is a recurring billing
   surprise.

Fill the **Evidence** section of `docs/operations/phase-7-pki-staging.md` with, at minimum:
- the date, region and `credentialDurationSeconds` used;
- the six-step PASS/FAIL table verbatim;
- the **measured revocation latency** from step 6 and the poll interval it was measured against;
- the issued certificate's subject and issuer from step 3, and an explicit statement of whether the
  CSR CN was preserved;
- the teardown verification output;
- anything that did not work the first time and what was actually wrong. Write down surprises. A
  runbook that records only the happy path is how this project lost seven weeks to an inverted
  claim about an empty directory.

Then amend `docs/architecture/0007-managed-pki-service-selection.md`, following the amendment
convention ADR-0005 demonstrates:
- flip `<!-- status: proposed -->` and `**Status:**` to accepted, dated;
- add an `## Amendment: measured staging results (<date>)` section carrying the measured revocation
  latency, the observed CSR-CN behaviour (resolving that open question), and the observed cost so
  far;
- if the cost question is still open because a full billing cycle has not elapsed, say so
  explicitly and keep it listed as an open question rather than quietly dropping it. Absence from a
  pricing page is not the same as a zero line on a bill.

**Do not mark SC4 passed if the measured latency exceeds the poll interval, or if the failure came
back as exit 4 instead of exit 6.** Record the failure, stop, and report it. A criterion recorded as
passing on a misread observation is the single most expensive failure mode in this project's
history.
  </action>

<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 3: Owner confirms the SC4 evidence</name>
  <what-built>
The full Phase 7 identity path, verified end to end against a staging AWS IoT Core account with no
human in the loop for the issuance itself:
- `arlowe-identity init` derived a device-unique ID and generated a P-256 key + CSR offline.
- `arlowe-identity provision --ca-broker-url ... --owner-token ...` obtained an Amazon-CA-signed
  certificate via `CreateCertificateFromCsr`, brokered by a hand-minted bearer token with no
  owner-account backend anywhere in the path.
- `arlowe-identity check-cloud` exchanged that certificate for short-lived cloud credentials over
  mutual TLS.
- The certificate was revoked with `update-certificate --new-status REVOKED`, and the next call was
  refused with exit code 6 (`CertificateRevoked`).
- The staging resources were torn down and the teardown verified.
  </what-built>
  <how-to-verify>
1. Read the **Evidence** section of `docs/operations/phase-7-pki-staging.md`. Confirm the six-step
   table is all PASS and that the measured revocation latency is at or below the poll interval it
   was measured against.
2. Confirm step 6 recorded exit code **6**, not 4. Exit 4 means the call failed for an unrelated
   reason and SC4 did not actually pass.
3. Read the `## Amendment` section of `docs/architecture/0007-managed-pki-service-selection.md` and
   confirm the recorded CSR-CN behaviour matches what the evidence section shows.
4. Open the AWS staging console (IoT Core -> Security -> Certificates, and IAM -> Roles) and confirm
   nothing under the `arlowe-staging` prefix survives. The script checked this; check it yourself,
   because a leftover role alias is a small recurring bill.
5. In 30 days, check the staging account's actual bill and record the figure in the ADR amendment.
   The claim that IoT Core issuance and the credentials provider are unbilled is inferred from their
   absence on a pricing page — that is weaker evidence than a real invoice, and this phase should
   not close pretending otherwise.
  </how-to-verify>
