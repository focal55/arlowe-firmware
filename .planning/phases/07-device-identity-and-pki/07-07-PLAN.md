<objective>
Build the cert-authenticated cloud client: submit the CSR to the broker, and exchange the resulting
certificate for short-lived cloud credentials over mutual TLS.

Purpose: this is IDENT-04 and it is the mechanism SC4 depends on. The credentials exchange is the
exact point where AWS checks certificate status, so it is where revocation bites — which is why
Phase 7 can verify revocation end-to-end without building an OTA client.
Output: `runtime/lib/arlowe_cloud.py`, driven by the CLI in plan 07-08a.

This is a TDD plan: failing tests first, against a mocked HTTP layer. No network in the test suite.

<feature>
  <name>Certificate-authenticated cloud client</name>
  <files>runtime/lib/arlowe_cloud.py, runtime/lib/tests/test_arlowe_cloud.py</files>

  <behavior>
Standard library plus `requests` only. **No `boto3`, no `botocore`, no AWS IoT MQTT SDK on the
device.** The whole point of the brokered design is that the device needs one HTTPS POST and one
HTTPS GET. Keep the bookworm floor in mind: `python3-requests` is 2.28.1 on the image.

**Exception hierarchy** — the distinguishability is the deliverable, not decoration:
```
CloudError(Exception)
  NotProvisioned(CloudError)        # no cert and/or no key on disk
  ProvisioningRejected(CloudError)  # broker returned 4xx; carries .status and .reason
  CertificateRevoked(CloudError)    # credentials provider returned 403
  CloudUnavailable(CloudError)      # network error, 5xx, timeout
```
`CertificateRevoked` must be raised only for the revoked/inactive/unauthorized case, never as a
catch-all — SC4's pass condition is that the caller can tell "revoked" apart from "the wifi is
down", and a broad `except` here would make SC4 untestable.

**`resolve_endpoints() -> tuple[str, str]` returning `(credentials_endpoint, role_alias)`**
Precedence, documented in the docstring because two sources is inherently confusing:
1. `config["identity"]["credentials_endpoint"]` / `["role_alias"]` when non-empty — the owner-facing
   override.
2. Otherwise the values recorded in `/var/lib/arlowe/identity/identity.json` by `provision` — the
   device's own provisioning result. **Read it via `arlowe_identity.read_metadata()`, never by
   opening `METADATA_PATH` directly.** That file is written by `ensure_device_id` and mutated by
   07-08a's `provision` through `arlowe_identity.update_metadata()`; keeping the read on the same
   side of that contract means the JSON shape has exactly one owner (plan 07-03). `read_metadata()`
   returns `{}` when the file is absent and raises `ValueError` on corrupt JSON — let the
   `ValueError` propagate rather than treating a corrupt identity.json as "unprovisioned", because
   a provisioned device with a corrupt metadata file is a fault, not a factory state.
Raise `NotProvisioned` if neither yields a value. Neither is ever a tracked literal: the credentials
endpoint is `<account-specific-prefix>.credentials.iot.<region>.amazonaws.com` and that prefix is
account-identifying, is not on the sanitize banlist, and must not appear in source.

**`request_certificate(broker_url, owner_token, device_id, csr_pem) -> dict`**
One HTTPS POST implementing the contract frozen in plan 07-05b:
`POST {broker_url}/v1/certificates`, `Authorization: Bearer {owner_token}`, JSON body
`{"device_id", "csr"}`. On 200 return the parsed body and validate all six expected fields are
present (`certificate_pem`, `certificate_id`, `certificate_arn`, `thing_name`,
`credentials_endpoint`, `role_alias`); a missing field is a `ProvisioningRejected`, because a
half-populated response would otherwise produce a device that looks provisioned and cannot talk to
anything. On 4xx raise `ProvisioningRejected` carrying the status and the broker's `error` string.
On 5xx or a transport error raise `CloudUnavailable`.
- Reject a non-`https://` `broker_url` outright. This call carries an owner token.
- Honour `ARLOWE_BROKER_CA_BUNDLE` as the `verify=` argument when set, for the staging broker's
  self-signed certificate. Default is `True` (system trust store). Document it as staging-only.
- **Never log the owner token.** Log the broker host, the device_id and the status code.
- Timeout: `(5, 30)` connect/read. A pairing flow that hangs forever is a bug.

**`fetch_credentials(force_refresh=False) -> dict`**
`GET https://{credentials_endpoint}/role-aliases/{role_alias}/credentials` with:
- `cert=(str(CERT_PATH), str(KEY_PATH))` — mutual TLS, this is the authentication.
- header `x-amzn-iot-thingname: {device_id}`. It must match the Thing the certificate is attached
  to or AWS returns 403 — a mismatch is loud, which is what we want.
- `verify` defaults to the system CA bundle. Debian's `ca-certificates` already carries Amazon Root
  CA 1, so **do not vendor a `AmazonRootCA1.pem` into the image**: a vendored PEM is one more file
  to rotate, and a `*.pem` under `/opt/arlowe` is exactly what plan 07-04's build gate rejects.
  Allow `ARLOWE_CLOUD_CA_BUNDLE` as an override for staging.
- SNI must be the credentials endpoint exactly, which `requests` does by default from the URL host.
  Do not construct the request in a way that overrides the `Host` header.

Response handling:
- 200 -> return `{"accessKeyId", "secretAccessKey", "sessionToken", "expiration"}` from the
  `credentials` object.
- 403 -> `CertificateRevoked`. Include the response body in the exception message; AWS distinguishes
  a revoked certificate from a thing-name mismatch there, and a field diagnosis needs it.
- 5xx / `requests.RequestException` -> `CloudUnavailable`.
- Missing `CERT_PATH` or `KEY_PATH` -> `NotProvisioned`, raised **before** any network call, so an
  unpaired device fails fast with a clear reason instead of a confusing TLS error.

**Credential caching — this is where trap 3 is closed.**
- In-memory only, module-level. **Never write credentials to disk.**
- TTL is `min(expiration - 60s, identity.poll_interval_seconds)`. Revoking a certificate stops new
  exchanges but does not retroactively invalidate an already-issued STS token, so the honest bound
  is `max(poll_interval, remaining_credential_lifetime)`. The role alias is provisioned with
  `credentialDurationSeconds=900` (plan 07-05a) and `poll_interval_seconds` has a floor of 900, so
  capping the cache at the poll interval collapses that bound to **one polling interval** — the
  number SC4 tests against. Put this derivation in the docstring; it is the non-obvious WHY.
- Because the poller is a short-lived process per poll, in-memory caching means effectively no
  cross-poll reuse. That is intentional, not an oversight.
- `force_refresh=True` bypasses the cache; `clear_credential_cache()` exists for tests.

Phase 9 (OTA) and Phase 10 (support-mode keys) consume `fetch_credentials()` and do their own
SigV4 signing with a real SDK. **Do not hand-roll SigV4 here.** Canonicalization is notoriously
easy to get subtly wrong and Phase 7 does not need a signed downstream call to prove revocation —
the credentials exchange itself is the authenticated call that fails. Say so in the module
docstring so a later reader does not think it was forgotten.
  </behavior>

**RED**: write `runtime/lib/tests/test_arlowe_cloud.py` first. Patch `requests.get` / `requests.post`
with `unittest.mock`; the suite must make zero real network calls. Use the `ARLOWE_IDENTITY_DIR`
idiom and generate a throwaway key/cert with `arlowe_pki` helpers or `cryptography` directly.

**Generate that key and certificate at test runtime into the temp `ARLOWE_IDENTITY_DIR`. Do not
commit a `.key`, `.crt`, `.csr` or `.pem` fixture anywhere under `runtime/`.** Two independent
reasons, both concrete: plan 07-06's verification runs
`git ls-files | grep -E '\.(key|crt|csr|pem|p12|pfx)$'` and expects nothing; and
`pi-gen/stage-arlowe/01-runtime/00-run-chroot.sh:95` rsyncs **all** of `runtime/` into
`/opt/arlowe/runtime/` with no excludes, so anything committed under `runtime/lib/tests/fixtures/`
lands inside the exact path plan 07-04's build gate scans and fails the image build. A throwaway
test key is still a key-shaped file to both gates.

Required cases:
- `fetch_credentials` with no cert on disk raises `NotProvisioned` and `requests.get` is never called.
- Happy path: mocked 200 returns the four credential fields; assert the call was made with
  `cert=(<CERT_PATH>, <KEY_PATH>)`, with the `x-amzn-iot-thingname` header equal to the device-id,
  and to a URL ending `/role-aliases/<alias>/credentials`.
- 403 raises `CertificateRevoked` and NOT `CloudUnavailable`.
- 500 and `requests.ConnectionError` both raise `CloudUnavailable` and NOT `CertificateRevoked`.
- Cache: two calls in a row issue one HTTP request; `force_refresh=True` issues a second; a cached
  entry whose TTL has elapsed (monkeypatch the clock) issues a second.
- Cache TTL is capped at `poll_interval_seconds` even when `expiration` is 12 hours out. Assert the
  computed TTL numerically — this is trap 3's regression test.
- No credential value is ever written under `ARLOWE_IDENTITY_DIR`: after a successful fetch, walk
  the directory and assert the secret access key string appears in no file.
- `resolve_endpoints` precedence: config wins when non-empty; identity.json is used when config is
  empty; `NotProvisioned` when both are empty.
- `request_certificate`: rejects an `http://` URL before any call; 200 with all six fields returns
  them; 200 missing `role_alias` raises `ProvisioningRejected`; 401 raises `ProvisioningRejected`
  with `.status == 401`; 503 raises `CloudUnavailable`; the owner token appears in the outgoing
  `Authorization` header and in no log record (capture with `caplog`).
