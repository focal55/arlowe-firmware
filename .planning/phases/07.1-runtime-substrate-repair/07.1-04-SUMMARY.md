## The things the plan asked to be recorded

### How the requirement files reach the chroot, and the resolved default

The mechanism is the **host-side `00-run.sh` staging loop**. `pi-gen/stage-arlowe/01-runtime/files` was added to it, alongside the `third_party/node` entry 07.1-01 added to the same loop. Before this, the requirement files reached the chroot *not at all*.

The resolved default, which is what `build-venvs.sh` uses when nothing overrides it:

```
ARLOWE_VENV_REQ_DIR=/root/arlowe-build/repo/pi-gen/stage-arlowe/01-runtime/files/venv-requirements
```

Proven by running the real `00-run.sh` rather than a reconstruction of it:

```
[01-runtime]   staged third_party/node/
[01-runtime]   staged pi-gen/stage-arlowe/01-runtime/files/
### staged. Did the requirement files arrive at build-venvs.sh's DEFAULT path?
constraints.txt
llm.txt
stt.txt
voice-nodeps.txt
voice.txt
[00-run-chroot] step 7: build-venvs.sh
[build-venvs] requirement dir: /root/arlowe-build/repo/pi-gen/stage-arlowe/01-runtime/files/venv-requirements
```

No fixture path exists anywhere in the script. The `ARLOWE_VENV_REQ_DIR` override is there so 07.1-05's container can invoke this same script instead of forking it; the container verify deliberately does **not** set it, so the default is what got exercised.

### Sizes, and the card-sizing consequence

| Measured | Size |
|---|---|
| voice venv (build time) | 98 MB |
| llm venv (build time) | 176 MB |
| stt venv (build time) | 285 MB |
| **venvs subtotal, build time** | **559 MB** |
| **`/opt/arlowe/venvs`, as shipped** | **430 MB** |
| `/opt/arlowe/runtime/dashboard` | 75 MB |
| `/opt/arlowe/node` | 200 MB |
| **`/opt/arlowe` total, per slot** | **705 MB** |

Two figures matter and they are different. Build-time is 559 MB; **shipped is 430 MB**, because `00-run-chroot.sh`'s reproducibility cleanup purges `__pycache__` from `/opt/arlowe`. The 129 MB delta is bytecode that CPython regenerates on first start. Wave 1's ~552 MB was measured immediately after install and is the build-time number.

**For issue #135, the number to use is 705 MB per slot, 1.41 GB across A and B.** ADR-0004's "16 GB is VIABLE" conclusion rested on a 2–3 GB model-free slot estimate made when `/opt/arlowe/venvs` was empty. 705 MB fits inside that estimate but consumes a quarter to a third of it, and `/opt/arlowe` is not the whole slot. ADR-0004 is deliberately **not amended here** — that is not this plan's change — but #135 can now be argued from measurement instead of from an empty directory.

**A 597 MB per-slot find that `du /opt/arlowe` cannot see.** pnpm's content-addressed global store and corepack's cache live under `/root`, outside both the directory `build-dashboard.sh` swaps and `00-run-chroot.sh`'s cleanup:

```
[build-dashboard] === removing package-manager caches (build-only, must not ship) ===
[build-dashboard]   removing 575M /root/.local/share/pnpm
[build-dashboard]   removing 20M /root/.cache/node
[build-dashboard]   removing 1.8M /root/.cache/pnpm
```

Without that step the image carries ~597 MB of package-manager cache per slot — 1.2 GB across both — and every size check aimed at `/opt/arlowe` reports clean. Deleting the store after relocation is safe: Next's file tracing copies traced files into the standalone tree, and where a copy shares an inode with a store entry, removing the entry drops a link and not the data.

### Node: prefix, version, digest, and the exact ExecStart

- **Interpreter:** `/opt/arlowe/node/bin/node`, from `node_bin`

### pnpm: pinned once, derived twice

Pinned in `runtime/dashboard/package.json`:

```json
"packageManager": "pnpm@10.15.0"
```

10.15.0 is confirmed against the tree, not guessed: `pnpm-lock.yaml` is `lockfileVersion: '9.0'` (pnpm 9/10), and `ci.yml`'s own comment recorded that `node_modules` was authored by 10.15.0. No discrepancy to note.

Both consumers derive from that one field:

- **`.github/workflows/ci.yml`** — all four `version: 10` call sites removed. `pnpm/action-setup@v4` reads `packageManager` when no version is given, but its default `package_json_file` is `./package.json`, which does not exist at this repo's root, so the path is named explicitly: `package_json_file: runtime/dashboard/package.json`. `grep -c "version: 10$"` is now **0**.
- **`build-dashboard.sh`** — reads the same field with the vendored Node (`node -p "require(...).packageManager"`, so no `jq` dependency the chroot does not have), activates it via **corepack**, and hard-fails if `pnpm --version` disagrees. Corepack because Node 24 still bundles it and it resolves `packageManager` natively; there is a pinned `npm install -g` fallback for the Node 25 line, which drops corepack.

Verified: `pnpm --version` → `10.15.0`, matching the pin.

## Deviations from Plan

Every wave-1 executor found somewhere its plan contradicted the repo. So did this one, in six places. The repo won each time.

### Auto-fixed

**1. [Rule 1 — Bug] `pip check` cannot be clean on the voice venv, and the plan required it to be**

- **Found during:** Task 1 container verify
- **Issue:** The plan's done-criterion is "`pip check` is clean in each". It cannot be. ADR-0008 installs `noisereduce` with `--no-deps` to drop a 74 MB matplotlib chain, so pip's metadata necessarily reports `noisereduce 3.0.3 requires matplotlib, which is not installed.` A blanket hard-fail contradicts a recorded decision; deleting the check throws away a real gate.
- **Fix:** `pip check` stays enforced, but the tolerated *subjects* are computed from `<name>-nodeps.txt` itself. A complaint is excused only when the package making it is one installed `--no-deps`. Every tolerated line is still printed (`EXPECTED voice: ...`), and a future `noisereduce` bump that acquires a genuinely new dependency surfaces as a new subject rather than vanishing into an allowlist.
- **Files:** `pi-gen/stage-arlowe/01-runtime/files/build-venvs.sh` · **Commit:** `143f3cb`

**2. [Rule 1 — Bug] The version gate could not apply the floor it documents for venv interpreters**

- **Found during:** Task 3, first integration run — 7 FAILs
- **Issue:** The gate keys `ARLOWE_RUNTIME_FLOOR` on the **resolved** basename. A venv interpreter is a symlink chain (`venvs/voice/bin/python` → `python3` → `/usr/bin/python3` → `python3.11`), so every venv stanza resolved to `python3.11`, which is not a key, and all seven were reported as undeclared interpreters. The table's own comment states it covers `/opt/arlowe/venvs/*/bin/python`. Lookup and documented intent disagreed. The fixture self-test could not catch it because its interpreters are plain files, not symlinked venvs.
- **Fix:** Fall back to the literal token's basename when the resolved one carries no floor. This loses no detection power — the basename selects which floor *applies* while the probe still measures the resolved binary — so the Node-18-at-`/usr/bin/node` trap is caught exactly as before, which the self-test's `node18-trap` case still proves.
- **Files:** `scripts/lib/verify-unit-execstart.sh` · **Commit:** `4cf6cc3`
- **Note:** this modifies plan 07.1-03's deliverable. Flagged deliberately.

**3. [Rule 1 — Bug] The gate fails on a unit apt installs, so it would have failed the first real build**

- **Found during:** Task 3, first integration run
- **Issue:** The gate globs the rootfs's own `/etc/systemd/system`, which is deliberate — but apt puts units there too. bookworm's `network-manager`, declared in `00-packages-nr` for Phase 8 wifi provisioning, installs `dbus-org.freedesktop.nm-dispatcher.service`. A real rootfs has **9** units, not the 8 the unit source directory suggests, and the gate FAILed on `/usr/lib/NetworkManager/nm-dispatcher`, an interpreter apt owns and we have no floor for.
- **Fix:** Added to `EXPECTED_UNDECLARED` with a reason — the gate's own documented extension point, not a relaxation. The glob was left alone: seeing everything installed is the design.
- **Files:** `scripts/lib/verify-unit-execstart.sh` · **Commit:** `4cf6cc3`
- **Why it matters:** 07.1-03's self-test uses a synthetic rootfs with no apt-installed units, so this would have surfaced for the first time in a real image build.

**4. [Rule 3 — Blocking] The gate self-test hardcoded `/usr/bin/node` while consuming the live units**

- **Found during:** Task 3, after the ExecStart change
- **Issue:** `tests/phase-07.1/test-verify-unit-execstart.sh` copies the repo's real `units/*.service` into its fixtures but created `/usr/bin/node` by hand. Repointing the dashboard unit at the vendored prefix broke 7 cases for a reason unrelated to the behaviour they cover — including `[prefix-image] names the dashboard entry point`, which failed because the gate FAILs on the missing executable and never reaches the script argument.
- **Fix:** The test reads the interpreter path out of `units/arlowe-dashboard.service`. Derived, so it follows the unit.
- **Files:** `tests/phase-07.1/test-verify-unit-execstart.sh` · **Commit:** `4cf6cc3`

**5. [Rule 2 — Missing critical] 597 MB of package-manager cache would have shipped per slot**

- **Found during:** Task 2
- **Issue:** The plan's cleanup step lists `node_modules`, `.next/cache` and the test surfaces — all inside the dashboard directory, all removed by the directory swap. It does not mention pnpm's global store (575 MB) or corepack's cache (20 MB), which live under `/root`, outside both the swap and `00-run-chroot.sh`'s cleanup. `du /opt/arlowe` cannot see them.
- **Fix:** `build-dashboard.sh` removes the store (via `pnpm store path`) and the caches after relocation, reporting each size.
- **Files:** `pi-gen/stage-arlowe/01-runtime/files/build-dashboard.sh` · **Commit:** `4cf6cc3`

**6. [Rule 1 — Bug] Two smaller ones**

- `mktemp -t node.XXXXXX.tar.xz` — GNU mktemp requires the X's to terminate the template and rejects a trailing suffix. Would have failed every real build at the Node fetch. Replaced with `mktemp -d`. Caught by reading before running. **Commit:** `2306671`
- `00-run-chroot.sh`'s header block listed `5. install-arlowe-cli.sh` / `6. install-arlowe-udev-polkit.sh` while the body did the reverse. Pre-existing, same defect class as the stale `install-arlowe-fs.sh` comment this plan was sent to fix. Corrected while renumbering. **Commit:** `143f3cb`

### Plan text contradicted by the repo, followed the repo

- **"pip install -r voice.txt" (single pass).** Wave 1 split the voice set in two because `--no-deps` is not a valid requirements-file directive. `build-venvs.sh` runs `voice.txt` then `voice-nodeps.txt --no-deps`, and the input gate requires **five** files, not the four the plan names. The condition is on the *file* (`<name>-nodeps.txt`), not the venv name, so a second one is a file drop rather than an edit.
- **"vendored Node 20".** The manifest pins Node 24.21.0. Not corrected back. The floor stays `>= 20.9.0` because it comes from `next@16.1.6`'s `engines`, and 24 satisfies it.
- **`jq` in the chroot.** The plan suggests reading `packageManager` with `jq` if needed. `jq` is not in `00-packages-nr` and the chroot does not have it. The vendored Node reads its own `package.json` instead — no new package.

### Not done, deliberately

- **ADR-0004 not amended.** Issue #135 now has measured numbers (705 MB per slot) instead of an empty-directory estimate, but re-deciding 16 GB viability is not this plan's change.
- **ROADMAP not corrected.** Its 07.1-04 line still says "vendored Node 20" and its 07.1-01 line says "Node-20 floor decision". Both predate ADR-0008's Node 24 decision. Plan 07.1-06 owns ROADMAP/REQUIREMENTS traceability.

### Caveat on the version-probe results

The integration ran in an **emulated** arm64 container on an x86_64 host. The container presents as `aarch64`, so the gate's own cross-arch refusal did not trigger. The version strings are still the arm64 binaries' own — those binaries really are the ones the image ships — but the *execution* was emulated. A native-arm64 run is the stronger evidence and belongs to 07.1-06's hardware checkpoint.
