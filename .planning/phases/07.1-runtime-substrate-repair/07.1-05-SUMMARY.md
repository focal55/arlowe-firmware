## The defect this found

`arlowe-voice` runs `/opt/arlowe/venvs/voice/bin/python -m voice.voice_client`.
`voice_client.py:27` is `from llm.router import route` — at **module scope**.
`llm/router.py:18` is `from filelock import FileLock`. `filelock` was declared only
in `llm.txt`, because the obvious consumer of `runtime/llm` is `qwen-tokenizer`,
which runs the *llm* venv.

```
MISS       filelock           -                                    <- runtime/llm/router.py:18
FAIL arlowe-voice: filelock does not resolve under /opt/arlowe/venvs/voice/bin/python
```

Nothing in the pipeline could have caught this. Wave 1's ledger recorded the right
importer and the right source; what a ledger cannot see is a unit reaching a
first-party module that lives in **another service's directory**. Both SC1 gates
pass regardless — every `Exec*` target exists. The unit would have started, run
`ExecStartPre` successfully, and then died at `import` with `Restart=on-failure`
looping, on every factory device.

Fixed in `764e583`: `filelock==3.32.6` added to `voice.txt` at llm.txt's version,
with the module-scope reasoning in the file. **This is the second defect in this
phase that would have failed the first production boot** (07.1-04 found the venv
interpreter symlink resolution and the apt-installed ninth unit).

## Why `find_spec` and not `import`, measured

The whole design rests on this, so it was measured rather than quoted, in the real
container under the real voice venv:

```
$ docker run --platform linux/arm64 arlowe-import-check:bookworm \
    /opt/arlowe/venvs/voice/bin/python -c '...'
find_spec("RPi")        -> True
find_spec("RPi.GPIO")   -> True
import RPi.GPIO         -> RuntimeError: This module can only be run on a Raspberry Pi!
```

The package is installed and correct. A checker built on real imports would report
it as a missing dependency on every single run, and the gate would become noise
inside a month. `find_spec` on a top-level name performs no module execution at
all, which is why only top-level names are probed.

## Exclusion list — one entry, with a live assertion

| Excluded | Why | Assertion that keeps it valid |
|---|---|---|
| `WhisPlay` | Vendored into the rootfs at image-build time from an external source (provenance is pending todo F2). Not in the repo, so no interpreter anywhere can resolve it from a checkout. | `pi-gen/stage-arlowe/01-runtime/00-run-chroot.sh` must still contain both `WhisPlay.py` and `/opt/arlowe/third_party/whisplay-driver`. If it stops doing so the exclusion is **VOID** and `WhisPlay` is reported as an ordinary failure. |

**The exclusion is not a free pass for what WhisPlay pulls in.** Because the
driver's source is absent, its imports cannot be walked — which would have silently
excused `RPi.GPIO` and `spidev`, two apt packages nothing else in `runtime/`
imports. `third_party/whisplay-driver/PROVENANCE.md` declares them in its
*"For `face.py` to import `WhisPlayBoard` successfully:"* list, and the checker
parses that list and continues the graph through it. Both now resolve and are
version-reported (`RPi.GPIO 0.7.1a4`, `spidev 3.6`) — and they are the two packages
that only exist on arm64, which is what makes the arm64 requirement load-bearing
rather than stylistic.

Nothing else was excluded. Nothing was added to the list during execution.

## `build-venvs.sh` was not modified and not overridden

The plan allowed parameterizing a chroot-coupled line. None was needed, and none
was touched:

```
$ git diff --quiet HEAD -- pi-gen/stage-arlowe/01-runtime/files/build-venvs.sh && echo UNMODIFIED
UNMODIFIED
```

`ARLOWE_VENV_REQ_DIR` exists with the chroot path as its default, so instead of
overriding it the Dockerfile **stages the requirement files at exactly that default
path**:

```dockerfile
ENV ARLOWE_CHROOT_REPO=/root/arlowe-build/repo
COPY pi-gen/stage-arlowe/01-runtime/files/ ${ARLOWE_CHROOT_REPO}/pi-gen/stage-arlowe/01-runtime/files/
RUN bash ${ARLOWE_CHROOT_REPO}/pi-gen/stage-arlowe/01-runtime/files/build-venvs.sh
```

No override is set, so **the default is what gets exercised** — the same script
reading the same path the image build reads. This is stronger than 07.1-04's
requested re-verification: there is no edit to re-verify. `ARLOWE_VENV_ROOT` is
likewise left at its default, so the interpreters land at the literal paths the
units name, and the container output reproduces 07.1-04's own numbers exactly
(three venvs, `pip check` clean modulo the derived `--no-deps` tolerance, all three
sharing the apt `numpy 1.24.2`). The `arlowe` group comes from the real
`install-arlowe-user.sh`, whose own header names the Docker testbed as a supported
invocation.

## Deviations from plan

Every executor in this phase has found somewhere the plan contradicted the repo.
Six here. The repo won each time.

### Auto-fixed

**1. [Rule 2 — Missing critical] `filelock` absent from the voice venv**

Covered in full above. `arlowe-voice` would have crash-looped on every factory
device. Commit `764e583`.

**2. [Rule 2 — Missing critical] The plan's entry-point rule would have skipped the unit that caused the original defect**

- **Found during:** Task 1, reading the units before writing the walker.
- **Issue:** the plan says entry points are `-m pkg.mod` or an absolute
  `/opt/arlowe/runtime/<rest>.py`, and *"skip non-Python entry points (`run_api.sh`,
  `node`)"*. `arlowe-identity-init.service` runs
  `/opt/arlowe/runtime/cli/identity init`. That file is `#!/usr/bin/env python3`
  and is deliberately named **without** a `.py` extension, so the CLI symlink
  installer produces `arlowe-identity`. Under the plan's rule it is a non-Python
  entry point and gets skipped — and it is the single consumer whose missing
  imports (`yaml`, `jsonschema`) are the defect SC4 was written for. A gate that
  skipped it would have skipped its own motivating case.
- **Fix:** a bare executable under `/opt/arlowe/runtime` whose **shebang** names
  python is a Python entry point. `arlowe-identity-init` is now checked, under
  system `python3`, which is the interpreter the image contract gives it.
- **Consequence:** SC4 covers **five** units, not the four the ROADMAP's SC4 line
  anticipated. Recorded for 07.1-06. Commit `92893cf`.

**3. [Rule 1 — Bug] "module-level only" would have walked past the original defect**

- **Found during:** Task 1.
- **Issue:** the plan says to collect imports *"including module-level-only (do not
  follow function-local imports)"*. Read as `ast.Module.body`, that is wrong.
  `runtime/lib/arlowe_config_validate.py`'s only real import is
  `from arlowe_config import load` **inside a `try:`** — and `arlowe_config` is what
  imports `yaml` and `jsonschema`, the two packages that were missing from every
  image. `voice_client.py` has the same shape at line 52. A `Module.body` walk
  reaches neither, and the checker would have reported the `arlowe_config_validate`
  entry point as importing nothing at all.
- **Fix:** start-time vs call-time is decided by **`FunctionDef` nesting**, not by
  top-level position. `try:`, `if:`, `with:` and class bodies all execute at import
  time and are treated as start-time. Only a lexically enclosing function defers.
- **Verification:** the yaml/jsonschema chain appears under all four units that run
  `arlowe_config_validate`, and is absent under `whisper-stt`, which does not.
  Commit `92893cf`.

**4. [Rule 2 — Missing critical] The WhisPlay exclusion was a free pass for two apt packages**

- **Found during:** Task 1 verify; the first host run probed neither `RPi` nor
  `spidev`.
- **Issue:** excluding `WhisPlay` also silently excuses everything it imports,
  because its source is not in the checkout and cannot be walked. Those are
  `RPi.GPIO` and `spidev` — declared in `00-packages-nr` **solely** for this driver

- **Self-disabling:** the trigger is the absence of any `*.py` in the vendored root,

  stops firing on its own. My first implementation used `path.exists()` and

**Open, for whoever picks them up:**

1. **SC4 now covers five units, the ROADMAP says four.** `arlowe-identity-init` is
   checked under system `python3`. 07.1-06's traceability pass should record it.
2. **The gate cannot see transitive third-party imports.** It walks *first-party*
   modules transitively and stops at the third-party boundary — so `scipy`,
   `sklearn`, `joblib`, `onnxruntime` and `ctranslate2` are covered by `pip check`
   inside `build-venvs.sh` and by wave 1's ledger, not by this gate. `sklearn` in
   particular has **no import statement anywhere** (it arrives through
   `pickle.load`), so no AST walk can ever reach it. Wave 1 named this; it is still
   true and this gate does not change it.
3. **The five function-local imports are a Phase 8+ risk**, listed above. They pass
   today only because each module is also imported at start time somewhere in the
   same unit.
4. **`arlowe-firstboot`'s `arlowe-grow-models` is not in the checkout** — the stage
   installs it from `03-firstboot/files/arlowe-grow-models.sh` under a different
   name. It is shell, so nothing is missed here, but it is the one `Exec*` target
   the checker reports as *"not present in the checkout"* rather than as a positive
   classification, and a future Python replacement at that path would be skipped
   silently.
5. **~271 MB per slot of C++ headers and a compiler ship in the apt layer, and
   nothing has counted them.** Noticed while reading this container's own apt
   output — it reproduces the image's package set faithfully, so the image carries
   the same thing. Traced and measured in that container:

   ```
   $ apt-cache rdepends --installed gcc          -> python3-numpy
   $ apt-cache rdepends --installed libboost-dev -> python3-pythran   (from python3-scipy)
   $ du -sh /usr/include/boost /usr/lib/gcc /usr/lib/python3/dist-packages/pythran
   158M  /usr/include/boost
   102M  /usr/lib/gcc
    11M  /usr/lib/python3/dist-packages/pythran
   ```

   These are hard `Depends`, not `Recommends`, so `--no-install-recommends` cannot
   drop them: bookworm's `python3-numpy` depends on `gcc`, and `python3-scipy`
   depends on `python3-pythran`, which needs the Boost headers. Both numpy and
   scipy are required by ADR-0008's apt-over-pip rule, so this is a consequence of
   a decision that is otherwise correct, not a mistake in it.

   **271 MB per slot, ~542 MB across A and B — comparable to all three venvs
   combined (430 MB) and larger than `/opt/arlowe/runtime/dashboard` plus
   `/opt/arlowe/node`.** Issue #135's sizing rests on 07.1-04's 705 MB `/opt/arlowe`
   measurement, which by construction cannot see anything under `/usr`. Whoever
   re-argues ADR-0004's "16 GB is VIABLE" should measure the whole rootfs, not
   `/opt/arlowe`. Deliberately not acted on here: dropping a transitive `Depends`
   after the fact is an image-assembly change, and this plan builds a gate.
