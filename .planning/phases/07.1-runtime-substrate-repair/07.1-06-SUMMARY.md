## Why Task 3 ran before Task 2

The plan orders the checkpoint before the traceability pass, and the checkpoint
is `gate="blocking"`. It was executed the other way round, deliberately.

Task 3 has two kinds of content. The **status wording** depends on the
checkpoint's outcome. The **four stale claims** do not — "vendored Node 20" and
"SC4 covers four units" are wrong today and would still be wrong under every
possible SC6 result. Holding them behind a checkpoint that may not run for weeks
leaves the roadmap asserting a Node version the image does not ship.

So the outcome-independent corrections landed now, and the outcome-dependent
field was written to the **current** truth: SC6 UNPROVEN. That is not a
placeholder. It is what the plan's own must-have asks for — *"Until the
checkpoint runs, SC6 is recorded as UNPROVEN in the roadmap rather than implied
complete."* If the owner defers, nothing needs amending; the documents are
already correct. If the owner runs it, one status line and one table cell change.

Nothing was marked complete that has not been observed.

## The four traceability corrections

Each was verified against the repo before editing. The handoff list was treated
as a lead, not as fact.

### 1. Node 20 -> Node 24 (two ROADMAP plan lines)

| Line | Said | Verified |
|---|---|---|
| 07.1-01 | "Node-20 floor decision" | ADR-0008:235 — *"Node 24, not Node 20. The phase brief recommended Node 20 LTS. Overturned."* |
| 07.1-04 | "vendored Node 20" | `third_party/node/manifest.yml` pins `v24.21.0`; 07.1-04's chroot run reports `node at /opt/arlowe/node/bin/node: v24.21.0` |

Node 20 "Iron" reached EOL **2026-04-30**. The correction note states explicitly
that **the floor is unchanged at `>= 20.9.0`**, because that number comes from
`next@16.1.6`'s own `engines` metadata rather than from the runtime chosen to
satisfy it. Someone reading only "Node 20 was wrong, it is 24" would plausibly
bump the floor too, and the floor is not the thing that changed.

### 2. SC4 covers five units, not four

The ROADMAP's SC4 line anticipated four. Verified against 07.1-05's own output:
five per-unit reports, the fifth being `arlowe-identity-init` under system
`python3`.

`/opt/arlowe/runtime/cli/identity` is `#!/usr/bin/env python3` and deliberately
carries no `.py` extension so the CLI symlink installer produces
`arlowe-identity`. An entry-point rule keyed on `-m` or `.py` skips it — and it
is the single consumer whose missing `yaml` and `jsonschema` were this phase's
motivating defect (F7 #18). **A gate written to the plan's literal rule would
have skipped its own motivating case.** That is the part worth recording, not
the arithmetic.

### 3. "Six shipping runtime units" — six of what

Handed over as "six is the count of units this repo ships". Checked; that is
also not quite right, and the correction as written distinguishes four frames
rather than swapping one number for another:

| Count | What it counts | Verified against |
|---|---|---|
| **6** | runtime *service* units — the SC6 subject | `03-firstboot/00-run-chroot.sh:114`, which names them as shipping installed-but-disabled |
| **7** | first-party units in `units/*.service` | `ls units/` — the six plus `arlowe-identity-init` |
| **8** | first-party units in slot A's `/etc/systemd/system` | the seven plus `arlowe-firstboot` from `03-firstboot/files/` |
| **9** | units a real built rootfs contains | 07.1-04's run: `[unit-execstart] 9 unit(s), 17 target(s)`. The ninth is `dbus-org.freedesktop.nm-dispatcher.service`, installed by apt's `network-manager` |

The 8-vs-9 gap is the load-bearing one. `verify_unit_execstart` globs the
rootfs's **own** `/etc/systemd/system` rather than the repo's unit source
directory, which is the design: a gate that only checks what the repo ships
cannot see what apt adds. It FAILed on the ninth unit on its first real rootfs
run, and that was the gate working, not misbehaving.

### 4. Issue #135 slot sizing — deliberately not resolved here

Three figures exist and none can settle it:

| Figure | Source | Why it is insufficient |
|---|---|---|
| 705 MB/slot for `/opt/arlowe` | 07.1-04, measured under emulation | `/opt/arlowe` is not the slot |
| ~271 MB/slot of Boost headers + gcc | 07.1-05, traced in a container | hard `Depends` of `python3-numpy`/`python3-scipy`, under `/usr`, invisible to a `du` of `/opt/arlowe` |
| "≈2–3 GB per slot", "16 GB is VIABLE" | ADR-0004 | estimated when `/opt/arlowe/venvs` was empty |

**ADR-0004 is not amended.** The checkpoint's step 2 is the first opportunity to
`du` a real built rootfs, and it is written to run **before** flashing, while
the rootfs is still on the build host's disk — after flashing, the figure is
much harder to get. Amending an ADR from container numbers is how the estimate
got stale in the first place.

## What the runbook says that was not in any plan

### The gates' coverage boundary, stated as a limit

The plan asked for this explicitly and it is the section most likely to matter
later. The worked example is the one that already happened: before this phase,
`arlowe-dashboard.service` named `/usr/bin/node`. That path **existed** — apt put
bookworm's 18.20.4 there. `verify_unit_execstart` passed it, correctly and
uselessly. Path existence is not capability, and that is why the version gate
exists.

Four live gaps are named rather than glossed: transitive third-party imports are
not walked; `sklearn` has no import statement anywhere and arrives through
`pickle.load` so no AST walk can ever reach it; five function-local imports are
safe only because each also has a start-time import in the same unit; and slot B
is ungated and would fail if it were (#134).

### A finding: `boot-check` always exits 0

`pi-gen/stage-arlowe/03-firstboot/files/arlowe-firstboot.service:24` runs
`/opt/arlowe/runtime/cli/boot-check --first-boot`, and its comment says the unit
fails if boot-check exits non-zero. Checked: `runtime/cli/boot-check` parses no
arguments at all (`--first-boot` is silently ignored), has no `set -e`, no
explicit `exit`, and its final statement is an `echo` inside an `if`. **It exits
0 unconditionally, including when it has just printed `FAIL` lines.**

Consequence for the checkpoint: a green `arlowe-firstboot` is not evidence that
`boot-check` passed. The runbook says so in the "what is NOT a failure" section
and tells the reader to read the journal rather than the unit state.

**Deliberately not auto-fixed.** Making `boot-check` exit non-zero on FAIL would
make `arlowe-firstboot` fail on every factory device, because the six runtime
units are disabled by design until pairing and boot-check counts each as a FAIL.
That is a behaviour change to a shipping first-boot path, not a bug fix, and it
belongs to whoever owns finding #24. Recorded so it does not evaporate.

### Verified rather than transcribed: the wake word needs no download

The plan asserted `openwakeword==0.4.0` bundles its models. Load-bearing for the
factory image, so it was checked against the actual wheel:

```
openwakeword/resources/models/hey_jarvis_v0.1.onnx      1271370
openwakeword/resources/models/melspectrogram.onnx       1087958
openwakeword/resources/models/embedding_model.onnx      1328103
```

`openwakeword/__init__.py` builds its registry from
`os.path.dirname(os.path.abspath(__file__))`, so
`get_pretrained_model_paths()` — called at `runtime/voice/voice_client.py:344`,
filtering for `'jarvis'` — resolves from the installed package alone.
`openwakeword/model.py` imports `onnxruntime` and nothing else; 0.4.0 has no
tflite backend at all. Confirmed.

This also bounds a real risk in `unit-import-bookworm`: it resolves module
*specs*, so it could in principle pass a package whose *data files* were absent.
For this package it cannot.

## Deviations from Plan

### Plan text contradicted by the repo, followed the repo

**1. The plan's `arlowe-dashboard:18` line reference is stale.** The plan's Task
1 says to enumerate `arlowe-dashboard:18` alongside the venv stanzas. That was
true before plan 07.1-04 repointed the `ExecStart` at the vendored Node; the
stanza is now at **line 28**. All five unit line references were re-read from the
files rather than transcribed. The other four (`arlowe-voice:23,24`,
`arlowe-face:19,20`, `qwen-tokenizer:15,16`, `whisper-stt:11`) are correct.

**2. "Three venv requirement files."** There are **five**. Wave 1 split the voice
set into `voice.txt` + `voice-nodeps.txt` because `--no-deps` is a command-line
flag, not a valid requirements-file directive. The runbook states the two-pass
contract and that the condition is on the *file name*, since running only the
first pass yields a venv where `import noisereduce` raises. This is the fourth
plan in this phase to be handed "three" and find five.

**3. STATE.md not updated.** The plan's Task 3 lists it. The orchestrator owns
STATE.md this phase and instructed executors not to touch it. `git diff --stat
.planning/` shows ROADMAP.md and REQUIREMENTS.md only.

**4. The handoff's "six is the count of units this repo ships" was itself
imprecise.** Corrected to four enumerated frames — see above. The instruction to
verify rather than take the list on faith is what caught it.

### Requirements traceability: a structural note

`.planning/REQUIREMENTS.md`'s traceability preamble asserted *"Every v1
requirement is mapped to exactly one phase."* Citing two phases on three rows
falsifies that sentence. Rather than leave a document contradicting its own
table, the preamble now says **owning** phase and defines the `(+ N)` suffix as
"a later phase that closed a latent gap without introducing a new REQ-ID". The
coverage arithmetic (92/92, 0 unmapped) is unchanged and still true, because 7.1
adds no REQ-IDs by design.

### Not done, deliberately

- **ADR-0004 not amended.** See correction 4.
- **`boot-check`'s exit code not changed.** See the finding above.
- **Issue #135 not closed.** It gets its measurement from the checkpoint.
