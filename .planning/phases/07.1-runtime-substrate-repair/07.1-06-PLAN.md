PART A — substrate reference. What a maintainer needs to know without reading six plans:
  - Where the venvs come from: `pi-gen/stage-arlowe/01-runtime/files/build-venvs.sh`, from the pinned
    files under `venv-requirements/`, with `--system-site-packages` over the apt layer in
    `00-packages-nr`. Point at ADR-0008 for why.
  - Where `server.js` comes from: `build-dashboard.sh`, `output: "standalone"`, and the relocation of
    `.next/static` and `public` beside it.
  - Which Node the image ships and why it is not bookworm's 18.20.4.
  - What the substrate actually consists of, stated precisely, because the imprecise version of this
    sentence is what the phase checker caught: the six shipping units reference **three distinct venv
    interpreter paths** — `/opt/arlowe/venvs/{voice,llm,stt}/bin/python` — across **seven `Exec*`
    stanzas in four units**. `arlowe-voice:23,24` and `arlowe-face:19,20` both use the *voice* venv;
    `qwen-tokenizer:15,16` uses *llm*; `whisper-stt:11` uses *stt*. `arlowe-dashboard:18` runs
    `server.js` under Node. `qwen-api` execs `run_api.sh` and touches no Python at all. Do not write
    a count without the enumeration beside it.
  - The three gates and their exact coverage boundary: `verify_unit_execstart` proves a path exists
    and is executable in the rootfs; `verify_unit_runtime_versions` proves the interpreter at that
    path reports a version at or above a declared floor; `unit-import-bookworm` proves the imports
    resolve under the image's package set. NONE of them proves the service does its job. Node 18 vs
    `next@16` is the worked example of why the first gate alone was never enough — and the reason the
    second exists. Say this plainly — the next person to hit a gap needs to know where the gates
    stop, not be reassured that they are comprehensive.
  - How to add a new Python import to a unit-reachable module without breaking the image: the
    two-declaration-points rule from ADR-0008.
  - `/opt/arlowe/venvs/<name>/FROZEN.txt` on a device is the record of what was installed.
  - One sentence so nobody re-derives it: the wake word needs no download step on a factory image.
    `openwakeword-0.4.0-py3-none-any.whl` bundles
    `openwakeword/resources/models/{hey_jarvis_v0.1,melspectrogram,embedding_model}.onnx`, and 0.4.0's
    `Model.__init__` is pure-ONNX, so `voice_client.py:344`'s `get_pretrained_model_paths()` resolves
    from the installed package alone. This was checked while verifying that plan 07.1-05's `find_spec`
    approach could not be weakened by missing package *data*; it cannot, for this package.

PART B — the SC6 procedure. Do not duplicate build/flash steps; reference
`docs/operations/phase-6-build-flash-deploy.md` and add only what is specific to 7.1. Carry forward
the traps that have already cost time on this hardware — each of these was learned the hard way and
must be in the runbook, not in someone's memory:
  - `CARD_SIZE_GB` is interpreted as **GiB**, not GB. A nominally-32 GB card fails against
    `CARD_SIZE_GB=32`. Use a 64 GB card for `CARD_SIZE_GB=32`.
  - Do not read-write loop-mount the image after the build; it rewrites the ext4 superblock and
    `bmaptool flash` then aborts on a checksum mismatch. Mount `-o ro`, or regenerate the `.bmap`.
  - A build watcher using bare `pgrep -f "build-image.sh"` matches its own poll command line and
    reports RUNNING forever. Use `pgrep -f "build-image[.]sh"`.
  - pi-gen must stay on its bookworm pin; unpinned master targets trixie.

Then the checkpoint steps themselves:
  1. Build from a clean checkout of this phase branch. Capture BOTH `verify_unit_execstart` and
     `verify_unit_runtime_versions` output from the build log — this is their first run against a real
     rootfs and the first real test of whether the container fixtures in plan 07.1-03 matched reality.
     The version gate's chroot probe in particular has only ever run against a fixture with
     `ARLOWE_VERSION_PROBE` set; this is the first time it executes a real binary.
  2. Flash, boot a factory-fresh unit with `/etc/arlowe/config.yml` ABSENT.
  3. `systemctl start` / inspect each of the six units. Record `systemctl is-active` for each:
     `arlowe-face`, `arlowe-voice`, `qwen-tokenizer`, `qwen-api`, `whisper-stt`, `arlowe-dashboard`.
     Note the Phase 11 dependency order (`qwen-tokenizer` -> `qwen-api` -> `qwen-openai`,
     `arlowe-face` -> `arlowe-voice`) and start in it.
  4. Specifically confirm SC5 on hardware: `/var/lib/arlowe/wake-word/verifier.pkl` is absent, and
     `journalctl -u arlowe-voice` shows the generic-mode line and no `FileNotFoundError`.
  5. Specifically confirm SC3 on hardware: `curl -sS -o /dev/null -w '%{http_code}' http://localhost:3000/`
     returns 200 with no config overlay present.
  6. Record `du -sh /opt/arlowe/venvs` and `df -h` on the device against ADR-0004's card budget.

State plainly which of these need the AX accelerator and the Whisplay physically attached, and which
do not. `qwen-api` needs the NPU and the model partition; `arlowe-face` needs the Whisplay. If part
of the unit set cannot be brought up for a hardware reason unrelated to this phase, that is a
partial result to record, not a failure of 7.1 — but it must be written down as partial, not rounded
up.
