<objective>
Produce the dependency ledger the image build has never had: for every third-party module a unit
entry point imports, a single declared source (apt or pinned pip), plus the ADR that records why.

Purpose: `/opt/arlowe/venvs` was never populated partly because nobody ever wrote down what
should go in it. `runtime/*/requirements.txt` are dev pins captured from the founder's dev unit
(`numpy==2.3.5`, `Pillow==11.1.0`) and are NOT installable as-is against Debian bookworm's system
layer — bookworm ships numpy 1.24.2 and Pillow 9.4.0. Installing the dev pins into a venv would
shadow the apt layer that the *system-python* consumers (`arlowe-identity-init`, `boot-check`)
already depend on, producing two divergent numpy builds in one image. This plan decides the split
once, writes it down, and makes it machine-readable so plan 07.1-04 is a mechanical application.
Output: an amended apt list, three pinned venv requirement files plus a shared constraints file,
a SHA-pinned Node manifest, and ADR-0008.
</objective>

Two hazards found during planning that you must resolve deliberately and record:

(a) NUMPY SHADOWING. A naive resolve of `openwakeword==0.4.0 noisereduce==3.0.3` against the apt
    layer produced `Would install ... numpy-1.26.4 ... onnxruntime-1.30.0 ... matplotlib-3.11.2`.
    pip pulled its own numpy over apt's 1.24.2 and floated onnxruntime and matplotlib to latest.
    Both are defects: the shadowed numpy means the image carries two numpy builds and the
    system-python consumers and the venv consumers no longer agree; the floats mean two builds from
    the same commit can install different bytes, which contradicts Phase 6 SC5.
    Resolution, in order of preference:
      1. Add `numpy==<apt version>` to `constraints.txt` and pin onnxruntime to the newest release
         that accepts it. Verify the resolve succeeds.
      2. If unsatisfiable, let the venv carry its own numpy, pin it explicitly, and record in
         ADR-0008 exactly which packages forced it and what the duplicate costs in image bytes.
    Do not silently take option 2. Try option 1 and show the failure if it fails.

(b) MATPLOTLIB. `noisereduce==3.0.3` declares matplotlib, which drags contourpy, fonttools,
    kiwisolver, pyparsing, python-dateutil and six for roughly 60 MB. `voice_client.py` uses
    noisereduce only as `nr.reduce_noise(...)`. Determine empirically whether
    `pip install --no-deps noisereduce==3.0.3` plus explicitly-listed real deps yields a working
    `import noisereduce` and a working `reduce_noise` call on a synthetic array. If it does, take
    that path and comment the `--no-deps` choice in `voice.txt`. If it does not, install with deps
    and record the 60 MB as accepted cost. Measure, do not assume.

  <name>Task 3: Resolve the Node runtime floor and write ADR-0008</name>
  <files>third_party/node/manifest.yml, docs/architecture/0008-image-runtime-dependency-strategy.md</files>

A defect found during planning that is not in the phase brief and must not be dropped:

  `units/arlowe-dashboard.service:18` -> `ExecStart=/usr/bin/node ...`
  `00-packages-nr:34` declares `nodejs`; Debian bookworm arm64 candidate is **18.20.4**.
  `runtime/dashboard/package.json` depends on `next@16.1.6`, whose `engines.node` is **>=20.9.0**.

So even after plan 07.1-04 produces `server.js`, `/usr/bin/node` cannot execute it and
`arlowe-dashboard` never reaches active. The SC1 gate will NOT catch this — `/usr/bin/node` exists,
it is simply the wrong version. Record it as an instance the gate cannot see, which is the honest
limit of SC1 and belongs in the ADR.

Decide and record. Recommended decision, to be justified or overturned in the ADR:

  Vendor the official Node 20 LTS linux-arm64 tarball into `third_party/node/`, SHA-256 pinned in
  `third_party/node/manifest.yml`, in exactly the shape of `third_party/axcl/manifest.yml` and
  `third_party/models/manifest.yml`. Reasons: it reuses a pattern the repo already has a verify gate
  for (`scripts/verify-third-party.sh`); it avoids adding a third-party apt repository with a
  rotating signing key to a shipped consumer device; and it pins the bytes, which a NodeSource
  `apt` repo does not.

  Rejected alternatives to write up: (i) NodeSource apt repo — supply-chain surface on a shipped
  device, unpinned; (ii) downgrade `next` to 15.x to fit Node 18 — pushes a framework downgrade and
  a lockfile churn into a substrate-repair phase and forfeits Next 16 for the life of v1;
  (iii) `nodejs` from bookworm-backports — check whether a >=20.9 candidate actually exists there
  for arm64 before dismissing it; if it does, it is the cheapest option and should win.

Verify (iii) before committing to the recommendation:
  docker run --rm --platform linux/arm64 debian:bookworm bash -c '
    echo "deb http://deb.debian.org/debian bookworm-backports main" > /etc/apt/sources.list.d/bp.list
    apt-get update -qq >/dev/null 2>&1; apt-cache policy -t bookworm-backports nodejs'

Write `docs/architecture/0008-image-runtime-dependency-strategy.md` following the shape of
ADR-0004 and ADR-0007 (Status / Context / Decision / Consequences / Alternatives). It must cover:
  - The `--system-site-packages` hybrid and the apt-vs-pip rule from Task 1.
  - The numpy resolution actually taken in Task 2, with the evidence.
  - The noisereduce/matplotlib call, with the measured size delta.
  - The Node decision and the rejected alternatives.
  - An explicit statement that `00-packages-nr` and the three venv requirement files are the single
    declaration point, and that adding an import to a unit's reachable graph without adding it to
    one of them is the defect class this phase exists to close.
  - The limit of the SC1 gate: it proves a path exists, never that the binary at that path is a
    version that can run the thing it is handed. Node 18 vs next@16 is the worked example.

Status: Accepted (this is an implementation decision, not a service selection awaiting staging
proof like ADR-0007).

If the decision is the vendored tarball, write `third_party/node/manifest.yml` with: version, URL,
sha256, and the extracted-path contract the chroot step will honor. Do not download the tarball
into the repo; `third_party/` is fetch-at-build per the existing pattern.
