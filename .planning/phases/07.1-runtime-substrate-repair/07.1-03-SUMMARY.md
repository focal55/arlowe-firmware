## Declared Version Floors

Plan 07.1-04 must provision interpreters satisfying these. Adding a floor is a one-line edit to `ARLOWE_RUNTIME_FLOOR` in `scripts/lib/verify-unit-execstart.sh`; the reasoning belongs in ADR-0008.

| Basename | Floor | Authority |
| --- | --- | --- |
| `node` | 20.9.0 | `next@16.1.6`'s `engines.node` (`runtime/dashboard/package.json` pins next 16.1.6). Bookworm's `nodejs` is 18.20.4 — ADR-0008. |
| `python3` | 3.11.0 | Bookworm's system python3; the venv interpreters are created from it and inherit the version. |
| `python` | 3.11.0 | Same interpreter; venvs expose both names in `bin/`. |

Floors key on the **resolved basename**, so they cover `/usr/bin/node`, `/opt/node/bin/node` and `/opt/arlowe/venvs/*/bin/python` without enumerating paths.

## EXPECTED_UNDECLARED

Confirmed against the tree, not transcribed from the plan. Every `Exec*` stanza in `units/*.service`, `pi-gen/stage-arlowe/03-firstboot/` and `runtime/recovery/arlowe-recovery.service` was enumerated; the six tokens the plan predicted are exactly the six the tree emits.

| Literal token | Reason |
| --- | --- |
| `/bin/touch` | coreutils; firstboot `ExecStartPost` marker |
| `/opt/arlowe/runtime/cli/arlowe-grow-models` | first-party grow script, firstboot `ExecStartPre` |
| `/opt/arlowe/runtime/cli/boot-check` | first-party entry point |
| `/opt/arlowe/runtime/cli/identity` | first-party entry point |
| `/opt/arlowe/runtime/llm/run_api.sh` | first-party shell wrapper; execs a venv python itself |
| `/opt/arlowe/runtime/recovery/arlowe-recovery.sh` | slot-B recovery unit; first-party shell |

Matched on the **literal token before symlink resolution**. Bookworm is usrmerge, so `/bin/touch` resolves to `/usr/bin/touch`; keying on the resolved path would make this list disagree with both what a reviewer reads in the unit file and what a diff shows. Proven by the `[usrmerge]` case.

## Slot-B Recovery Coverage: DEFERRED, and a finding

The plan asked whether the gates could also run against the slot-B recovery rootfs. They cannot, for two independent reasons, both commented at the call site in `build-image.sh`:

1. **Ordering.** Slot B does not exist when these gates run. It is written in step 4b by `write_recovery_stub`, after partitioning, inside a mount local to that function.

2. **A real defect, found while answering the question.** `scripts/lib/recovery-stub.sh:99` clones slot A into slot B with `rsync -aHAX --delete`, then prunes `/opt/arlowe/runtime/{voice,llm,stt,tts,dashboard,wake-word,face,lib}` — **but leaves every slot-A unit in `/etc/systemd/system`, including the `multi-user.target.wants` symlinks that enable them.** So a *correct* slot B names targets that were deliberately deleted, and running `verify_unit_execstart` against it would FAIL.

   The gate is right and slot B is wrong: `arlowe-voice.service`, `arlowe-dashboard.service`, `qwen-tokenizer.service` and `whisper-stt.service` are all enabled in the recovery slot and will fail at every recovery boot. The recovery stub should prune the units alongside the runtime tree. That is not this plan's change to make — recording it here so it does not evaporate. Once the prune is fixed, running both gates over `mnt_b` inside `write_recovery_stub` becomes a small, correct addition.

## Decisions Made

- **`sudo` for the gate invocation, not in-process.** `scripts/provision/install-arlowe-fs.sh:39` creates `/opt/arlowe` as `0750 root:arlowe`. The build-host user is neither root nor in the image's `arlowe` group. This was checked against the repo rather than assumed, and it is the same reason `du` runs under `sudo` at step 3.
- **`return 2` as a distinct HARD ERROR code** for both gates, propagated to a distinct message in `build-image.sh`. Cross-architecture rootfs, absent `chroot`, absent `dpkg`, and permission walls all land here.
- **The version probe is lazy.** The architecture check runs immediately before the first real probe, so a rootfs whose every interpreter is allowlisted needs no `chroot` at all — which is what lets the `[allowlisted-undeclared]` and `[usrmerge]` cases run unprivileged on `ubuntu-latest`.
- **bash 4+ guard at the top of the library**, before the first `declare -A`. The build host and CI are bash 5; a macOS bash 3.2 would otherwise fail obscurely mid-source.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] The gate would have failed for a permission reason on every build**

- **Found during:** Task 3, while answering the plan's own "verify whether the unit glob and the existence tests need elevation" instruction.
- **Issue:** `install-arlowe-fs.sh` creates `/opt/arlowe` as `0750 root:arlowe`. Run unprivileged, `[[ -e ... ]]` on every `Exec*` target under that tree returns false, so the gate would have reported all eight targets as absent from a perfectly good rootfs. The plan explicitly forbids this ("do not paper over a permission error as a missing file") but the original implementation had no way to tell the two apart.
- **Fix:** `_vue_resolve` now returns a distinct code 3 when a directory on the path is unsearchable; both public functions surface it as a HARD ERROR naming the blocked path and the current user, never a FAIL. The unit-directory glob got the same treatment, since an unreadable `/etc/systemd/system` would otherwise have surfaced as "zero units". `build-image.sh` invokes both gates under `sudo`.
- **Files modified:** `scripts/lib/verify-unit-execstart.sh`, `tests/phase-07.1/test-verify-unit-execstart.sh`, `scripts/build-image.sh`
- **Verification:** New `[permission-wall]` case asserts exit 2, asserts the denial is named, and asserts the output does **not** contain "missing in rootfs". It runs for real as uid 1000 in the container and on `ubuntu-latest`; it self-skips as root, where mode bits are unenforceable.
- **Committed in:** `aadae50`

**2. [Rule 1 — Bug] Absolute symlink targets could have escaped to the build host**

- **Found during:** Task 1.
- **Issue:** Resolving only the final path component lets the OS traverse intermediate symlinks against the real `/`. An absolute link target inside the rootfs would then have been tested against the build host's filesystem, so a gate could pass because the *host* had what the *image* was missing — the exact class of false green this phase exists to eliminate.
- **Fix:** `_vue_resolve` walks path components one at a time and re-roots every absolute link target at the rootfs prefix.
- **Verification:** `[host-escape]` case — a symlink to `/bin/ls`, which exists on every Linux build host and nowhere in the fixture, FAILs.
- **Committed in:** `9e66e46`

### Plan-vs-repo corrections

**3. Verification 5 (`grep -c "units/"` returns 0) conflicted with the header comments**

The library's comments explained *why* it does not read the repo's unit source directory, and in doing so contained the literal string `units/` three times, all in prose. Rather than weaken the check, the comments were reworded to say "the repo's unit source directory". The check keeps its value — it would still catch an actual read — and now returns 0.

**4. Architecture detection reads `<rootfs>/var/lib/dpkg/arch` directly**

The plan named `dpkg --print-architecture --root=<rootfs>` first, "or equivalently reading the rootfs's own dpkg data". The direct file read is the primary path here because it is deterministic and needs neither `dpkg` nor a complete admindir; `dpkg --root` is the first fallback and the ELF `e_machine` field of `<rootfs>/bin/bash` the second. All three are named in the file header, along with the explicit `arm64`↔`aarch64` / `amd64`↔`x86_64` mapping.

## Issues Encountered

- **The dry-run's positive fixture initially failed the real `chroot` probe.** The stub interpreters were `#!/bin/sh` scripts, and the fixture's `/bin/sh` was a dynamically linked copy with no loader or libc inside the chroot, so `exec` failed and the gate correctly reported "did not answer `--version`". Resolved by using a statically linked busybox as the fixture's `/bin/sh`. This was a limitation of the throwaway harness, not of the gate — and the gate reporting a FAIL rather than a pass when the exec failed is the fail-closed behaviour working.
- **The `size-check` job failed on the first PR Checks run** (1156 net lines against the 600 cap). Resolved by applying `size:phase-branch`, which the plan decided at plan time and which `pr-checks.yml` documents as a deliberate human act that re-triggers the check. The re-triggered run is fully green.
