<objective>
Close SC4: prove every Python import reachable from a unit entry point resolves under the image's own
package set, and make that proof run on every PR.

Purpose: `build-image.sh`'s packages guard checks that *declared* packages landed; it cannot see an
import that was never declared. That blind spot is why `python3-yaml` and `python3-jsonschema` were
missing from every image until Phase 7 caught it at the last moment, and why Pillow and numpy are
still missing now. Plan 07.1-03's gate closes the "the file isn't there" half of the class; this plan
closes the "the import isn't there" half. The existing `python-floor-bookworm` CI job is the working
precedent for verifying against the image's environment rather than the developer's — this extends
that pattern from `runtime/lib` to the whole unit-reachable graph.
Output: an import-graph checker, a container that reproduces the image's package set, and a CI job.
</objective>

  <name>Task 1: Import-graph checker driven by the unit files</name>
  <files>tests/phase-07.1/import-graph.py</files>
  <action>
Write `tests/phase-07.1/import-graph.py`. It takes a units directory and a runtime tree, and for each
unit determines the Python entry points from its `ExecStart=`/`ExecStartPre=` lines — derived, not
listed. A `-m pkg.mod` argument maps to `runtime/pkg/mod.py`; an absolute
`/opt/arlowe/runtime/<rest>.py` argument maps to `runtime/<rest>.py`. Skip non-Python entry points
(`run_api.sh`, `node`) with a logged note.

From each entry point, walk the import graph with `ast`:
  - Parse the file, collect `Import` and `ImportFrom` nodes, including module-level-only (do not
    follow function-local imports; note them separately in the report as a lower-severity category,
    because they fail at call time rather than start time and the distinction is worth keeping).
  - Resolve each name against the runtime tree. If it resolves to a file under `runtime/` it is
    first-party — recurse into it. Otherwise record the top-level name as third-party.
  - Handle the PEP 420 namespace-package layout in use here: `runtime/` has no `__init__.py` files
    (verified — `find runtime -name __init__.py` returns only `runtime/lib/tests/__init__.py`), so
    `face.face_service` is `runtime/face/face_service.py` and the relative `from .face import ...`
    inside it resolves to `runtime/face/face.py`. Resolve relative imports by level.
  - Handle the `sys.path.insert` in `runtime/face/face.py:23`, which injects
    `ARLOWE_WHISPLAY_DRIVER_PATH` before `from WhisPlay import WhisPlayBoard`.

Then verify each collected third-party name with `importlib.util.find_spec(name)`, run under the
interpreter passed on the command line.

`find_spec`, not `import`. This is deliberate and must be commented: `import RPi.GPIO` raises
`RuntimeError: This module can only be run on a Raspberry Pi!` even on arm64 in a container (verified
during planning), so a real import cannot distinguish "package missing" — the defect SC4 is about —
from "not running on a Pi". `find_spec` proves the package is installed without executing it.

EXCLUSIONS. Maintain a short, explicit, individually-justified exclusion list in the file with a
comment per entry, not a blanket pattern. Known entry:
  - `WhisPlay` — vendored at image-build time from an external source into
    `/opt/arlowe/third_party/whisplay-driver/`; not present in the repo. Provenance is tracked by
    pending todo F2. The check must instead assert that
    `pi-gen/stage-arlowe/01-runtime/00-run-chroot.sh` has a vendoring step for it, so the exclusion
    is not a free pass.
Anything you are tempted to add to this list is a finding: record it in the SUMMARY with the reason.

VERSION DRIFT. `find_spec` proves presence and nothing more, and presence is not the whole risk here:
`runtime/voice/requirements.txt` pins `numpy==2.3.5`, `scipy==1.17.0`, `scikit-learn==1.8.0` while the
image carries apt's 1.24.2 / 1.10.1 / 1.2.1, and today nothing compares the two numbers. So for each
resolved module also print the version actually installed — `importlib.metadata.version(dist)` where a
distribution name is resolvable, falling back to the module's `__version__` attribute read from the
spec without executing hardware-gated code, and `unknown` (printed, not omitted) where neither works.

Then compare against the dev-side pin: parse `runtime/*/requirements.txt` for a `==` pin of the same
distribution and emit `WARN <module>: image <x> vs dev pin <y> (<file>)` on any mismatch. WARN, not
FAIL — divergence between the dev unit and the image is expected and sometimes correct; the defect is
that it was invisible. Print a WARN total. Plan 07.1-01 replaces those files' stale "keep versions in
sync" comments with a pointer to this job, so this output is the mechanism those comments now name.

Report per unit: entry point, first-party modules walked, third-party modules found, which resolved
and at what version, which did not, which drifted from the dev pin, which were excluded and why, and
which were function-local. Exit non-zero if any non-excluded third-party module fails to resolve; do
not exit non-zero on WARNs.
  </action>
  <verify>

    python3 tests/phase-07.1/import-graph.py --units units --runtime runtime --python "$(command -v python3)"

  </verify>
  <done>The checker derives entry points from unit files, walks first-party imports transitively, reports third-party resolution via `find_spec` with the resolved version beside each module, WARNs on drift from the dev-side pin, and fails on this Mac for the expected reasons.</done>

inside the phase that exists to eliminate exactly that, and it would let `unit-import-bookworm` go
green against a recipe the image does not use.

If a specific line genuinely cannot run outside a chroot, parameterize that line in `build-venvs.sh`
(it is yours to edit — 07.1-04 owns it, but a small extracted variable is a trivial follow-on) rather
than forking the logic. Any variable you extract or override MUST keep the chroot value as its
DEFAULT, with the test container supplying the deviation — `ARLOWE_VENV_REQ_DIR` is already shaped
this way and is the model. A parameterization that defaults to the test path makes the container
green and every real build broken, which is this phase's own defect class. After any edit to
`build-venvs.sh`, re-run 07.1-04 Task 1's arm64 container verify unchanged (it stages at the real
`/root/arlowe-build/repo/...` path and sets no override) and paste its `VENVS_OK` line into this
plan's SUMMARY as proof the chroot path still works. Only if that also fails may you duplicate, and then you must name in the
SUMMARY the exact lines that forced it and add a comment in both files pointing at each other.

Write `tests/phase-07.1/run-import-check.sh` to build the image and run, per unit, the checker under
that unit's venv interpreter:
  arlowe-voice, arlowe-face   -> /opt/arlowe/venvs/voice/bin/python
  qwen-tokenizer              -> /opt/arlowe/venvs/llm/bin/python
  whisper-stt                 -> /opt/arlowe/venvs/stt/bin/python
Set `PYTHONPATH` to each unit's declared value from its own `Environment=PYTHONPATH=` line, re-rooted
at the container's tree. Do not hardcode it — `arlowe-voice` and `arlowe-face` use
`/opt/arlowe/runtime:/opt/arlowe/runtime/lib` while `qwen-tokenizer` uses only
`/opt/arlowe/runtime/lib`, and that difference is exactly the kind of thing that makes one unit work
and another not.

Also run plan 07.1-02's wake-gate tests in the same container invocation, so the factory-state test
runs against the image's package set too.

ARCHITECTURE. Run on arm64 where possible. `python3-rpi.gpio` and `python3-spidev` exist for arm64
bookworm (verified: 0.7.1~a4-1+b4 and 3.6-1+b1) and `find_spec` resolves them there; on amd64 they do
not exist at all and the check would have to stub them, which weakens it. `.github/workflows/
build-image.yml` already uses `ubuntu-24.04-arm`, so an arm64 runner is available to this repo.
