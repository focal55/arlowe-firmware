# Pi archive pinning: bumping the pins, reading a failure, and security

Decision record: `docs/architecture/0010-pi-archive-pinning.md`. The kernel, the Debian snapshot
and `PIGEN_REF` are covered in `docs/operations/phase-07.2-build-pinning.md`. This page covers
everything the image installs from `archive.raspberrypi.com` except the kernel.

**The one rule.** A pinned image gets libc6 and openssl fixes only when someone moves the pins.
Nothing on this page happens by itself. If you read one section, read
[5. Security](#5-security).

---

## 1. Where the Pi-side pins live

`third_party/pi-archive/manifest.yml` has 91 `packages` and one `resolve_only` entry. Each line
gives name, version (epoch included), arch, filename, size, sha256 and pool URL.
**It is generated by `scripts/lib/pi-archive-manifest.py`. Never hand-edit it.** CI
(`tests/phase-07.3/test-pi-archive-committed.sh`) requires every entry to be a `pkg` row of
`docs/operations/phase-07.2-inputs.reference`, so the manifest always equals a real build's
resolution. The only way to change it is [4. Bumping the Pi pins](#4-bumping-the-pi-pins).

Not here: the kernel (`third_party/kernel/manifest.yml`) and the Debian snapshot. Both are in
the 07.2 runbook. A record build can't move the kernel. The generator skips kernel names against
the kernel manifest, and fails with `kernel package off the kernel pin` if one resolves at any
other version.

Why these packages need a pin of their own:

- **raspi-firmware is the bootloader.** It ships `start.elf`, `fixup.dat` and `bootcode.bin`,
  the first code the device runs. Unpinned, it is both a reproducibility hole and a
  supply-chain hole.
- **It moved under us.** raspi-firmware went from `1:1.20260907` to `1:1.20260915` between two
  builds about ten hours apart, with nothing in the repo changed. The 07.2 inputs gate caught
  it, and the bump had to be accepted because there was nothing to pin to. The Pi archive is a
  rolling index with no snapshot service (`snapshot.raspberrypi.com` and
  `snapshot.raspberrypi.org` both returned HTTP 000). Its index keeps one version per name, so
  apt preferences can't select a superseded version either.
- **Exact-version dependencies nobody pinned.** `python3-lgpio` requires `liblgpio1` at exactly
  its own version (`0.2.2-1~rpt1` today). Before this phase, no manifest pinned `liblgpio1`.
  Nor did one pin libc6, openssl, dpkg, network-manager or rpi-eeprom.
- **The Pi 5 GPIO stack has no Debian fallback.** Debian's `python3-rpi.gpio` 0.7.1 predates
  BCM2712 and can't address a Pi 5. `python3-rpi-lgpio` provides the module named `RPi.GPIO`
  over lgpio. Without it the display driver can't open a GPIO line.
- **An unresolvable name hides everything else.** `apt` exits 100 on the whole set when any
  one package can't be resolved. Before 07.3, `tests/phase-07.2/resolve-twice.sh` excluded the
  two Pi-only GPIO packages. They did more than go unmeasured: they stopped it measuring the
  other 26 packages, so the gate read "28 packages pinned" while it pinned nothing. It now
  resolves against the flat repo and has no exclusion.

## 2. Before any build

1. **`dpkg-dev` is a host dependency.** A pinned build indexes the flat repo with
   `dpkg-scanpackages`, and stops before pi-gen if it's missing:
   `dpkg-scanpackages not found. Run: sudo apt-get install -y --no-install-recommends dpkg-dev`
2. **On a fresh host, fetch and verify the pinned debs.**
   ```
   ARLOWE_KERNEL_FETCH=1 ARLOWE_PI_ARCHIVE_FETCH=1 scripts/verify-third-party.sh
   ```
   Check 8 fetches the Pi debs: 178,122,788 bytes, about 170 MiB, of which 61 MB is
   prestera. The kernel debs (check 7) add about 75 MiB. Once every deb verifies, check 8 writes
   `build/.arlowe-pi-archive-paths`, and `build-image.sh` builds `build/pi-archive-repo` from it.
   The cache search order is in [7. Retention and mirroring](#7-retention-and-mirroring).
   Without `ARLOWE_PI_ARCHIVE_FETCH=1` the helper never touches the network. With it, every
   deb is still hashed, fetched or found.
3. **Destroy the work dir before every full build.**
   ```
   sudo rm -rf "${WORK_DIR:-build/pi-gen-work}"
   ls build/pi-gen-work 2>&1        # must report: No such file or directory
   ```
   The 07.2 runbook explains why in full. It matters more here because record and pinned builds
   alternate during a bump. A surviving stage0 rootfs keeps whatever `+rpt` packages it was
   built with, and a record build's rootfs keeps the live `raspi.list`. A pinned build on top of
   it fails the Pi gate with an off-pin list. A worse outcome is that it passes while installing
   bytes from the previous run.

A full build takes about 30 minutes on the arm64 build host. It needs loop devices and
privileged mounts, and it can't run on macOS.

## 3. Reading a failure

Build failures stop the build with exit 1. Record mode is the exception: its exit 3 is the
success outcome (see §4).

**Before pi-gen**
- `[pi-archive] FAIL <file>: not found in any cache; set ARLOWE_PI_ARCHIVE_FETCH=1 to download it`.
  This is a cold cache, not a pin problem.
- `[pi-archive] FAIL <file>: size mismatch: ...` or `sha256 mismatch: expected ..., actual ...`,
  or `fetched bytes rejected, ...`. The bytes aren't the pinned bytes. A cached file that was
  tampered with or truncated shows up this way, and so does a pool that re-published the same
  filename. Don't re-record over it. Find out which it is. The helper names the path it read.
- `Pi archive paths map missing: build/.arlowe-pi-archive-paths`. Check 8 didn't pass. Run it
  (see §2).
- `[pi-archive-repo] FAIL ...: Package/Version/Architecture/Size/SHA256 ..., manifest ...` then
  `Pi flat repo build failed (see above) — aborting before pi-gen.`. A deb's control file
  disagrees with its manifest row. That shouldn't happen for generated rows, so treat it as
  a hand edit or a corrupted cache.

**Inside pi-gen (stage0 onward)**
- `[FAIL] stage0/00-configure-apt/00-run.sh: ARLOWE_PI_REPO unset or not a directory.` The
  variable didn't cross the sudo boundary. It must be named in `build-image.sh`'s explicit sudo
  env list. The overlay refuses to fall back to the live archive.
- `sha256sum: WARNING: ... computed checksum did NOT match` from that same script means the
  copy of the repo inside the rootfs differs from what was verified on the host.
- `Ign:` lines for InRelease/Release and `Err: ... Packages.xz  File not found` during
  stage0's `apt-get update` are **expected**. The flat repo has no Release file. Don't gate on
  them.
- `E: Unable to locate package <name>` or `Package <name> has no installation candidate` for
  a Pi-only name. The manifest lacks that package, usually because an upstream or stage-arlowe
  stage list changed. For a name ending in `-` it's a removal marker (§4 step 7). Don't add a
  row by hand. Bump through record mode.

**The Pi gate** (`=== Pi archive pin observation (built rootfs) ===`). Its summary line is
`Pi archive gate: off-pin — see above.`, or `could not test` for rc 2.
- `[FAIL] the built rootfs declares the live Pi archive:`. A `.list` or `.sources` file
  still names `archive.raspberrypi.com`. The usual cause is a stale work dir left by a record
  build.
- `[FAIL] no apt list file starts with _var_local_arlowe-pi-archive_._Packages; nothing resolved
  from the flat repo`. The stage0 overlay didn't apply, or stage0 ran in record mode.
- `[FAIL] N apt list file(s) name the live Pi archive:`. apt deletes a removed source's lists
  on update, so a surviving list means that source was active at some point.

**The completeness check** (`pi-archive-manifest.py check`). This is followed by
`[FAIL] Pi archive completeness check failed; see docs/operations/phase-07.3-pi-archive-pinning.md,
section 3 (Reading a failure).`
- `[FAIL] dpkg left packages in an unfinished state; check cannot attribute them:` then
  `  <name>: <status>`. A package isn't `install ok installed`, so the check can't account for
  it. `axclhost` is the only exemption (`PI_LOCAL_PACKAGES` in `scripts/lib/pi-archive-gate.sh`).
  stage-arlowe leaves it half-configured on purpose, because its postinst can't modprobe in a
  chroot. That exemption is safe because it's attributed as local, never to an archive. Any
  other name here is a real install failure. Find it in the pi-gen log. Don't extend the
  exemption.
- `[pi-archive] FAIL <name>: pinned <version> <arch>, installed <other version> <arch>`. This is
  **silent substitution**: apt installed another build of a name both archives carry,
  usually Debian's. After a Debian snapshot bump this is the openssl case in §5. With
  `not installed` instead, the package left the installed set. A stage list changed, so bump
  through record mode.
- `[pi-archive] FAIL <name> <version> <arch>: unattributed; in neither the flat repo, the Debian
  lists, the kernel pin nor --allow-local`. An installed package has no pinned origin. Suspect a
  stale work dir first, then a stage that added its own apt source.
- `[pi-archive] FAIL <name> <version>: resolve-only package is installed`. A removal marker
  (prestera) got installed. Record mode would refuse to generate from this state as well.
- `[pi-archive] FAIL flat index only: ...` or `manifest only: ...` is **flat-index drift**:
  the repo inside the rootfs wasn't built from the manifest being checked. Either the manifest
  changed mid-build or the rootfs is stale.
- `[pi-archive] FAIL <name> ...: kernel package off the kernel pin <version>`. Go to the 07.2
  runbook.
- rc 2 (`[ERROR] ... flat-repo list files match ...; need exactly one`, `no snapshot.debian.org
  binary-arm64 list`, `no installed packages; refusing to pass vacuously`). The check couldn't
  run, so this is neither a pass nor a fail.

A pass reads `[pi-archive] check: N manifest packages installed at the pinned version, M
installed packages attributed, 0 unattributed`.

**The swap-back.** `Pi flat repo swap-back failed (see above) — the image would ship it.`, after
one of: `pi-gen raspi.list template missing: ...; flat repo left in place`, `could not clamp
mtimes to SOURCE_DATE_EPOCH`, `flat repo still in the rootfs`, `flat-repo source still in the
rootfs`, or `/etc/apt/sources.list.d/raspi.list has no active archive.raspberrypi.com <release>
line`. The image mustn't ship the 170 MiB repo or its `file:` source. It must ship stock
`raspi.list`. A missing template means the pi-gen tree is damaged, so re-provision it.

**Record mode** (exit 1, not 3): `Record mode could not generate a candidate (see above).`
- `[FAIL] record mode needs archive.raspberrypi.com and snapshot.debian.org binary-arm64 lists
  ... Did stage0 run with ARLOWE_PI_ARCHIVE_MODE=record?`. Most likely stale work dir from a
  pinned build.
- `[pi-archive] FAIL ...` (rc 1). The generator refused, reporting every problem. Examples:
  `in neither archive and not --allow-local`, `both archives carry it with different bytes`,
  `armhf is installed`, `resolve-only needs exactly one Pi version and sha256, found N`.
- `[pi-archive] ERROR ...` (rc 2). An unreadable input, or a refused list compression such as
  `.lz4`.
- `ARLOWE_PI_ARCHIVE_MODE='...' is not accepted; use 'pinned' or 'record'.` is a typo. It stops
  before Step 1.

**The daily retention issue** `Pi archive pool dropped a pinned deb`. `pi-archive-retention.yml`
HEADs every pinned URL and opens this issue, or comments on it if it's already open. The probe
says: `The Raspberry Pi pool no longer serves the files above; the build host cache and the CI
cache are now the only copies`. **That's literally true.** Act the same day:
1. On the build host, run `scripts/verify-third-party.sh` without `ARLOWE_PI_ARCHIVE_FETCH`. A
   pass proves the cache still holds every pinned deb.
2. Copy the named debs, and ideally all 92, somewhere durable outside the build host. Point
   `ARLOWE_PI_ARCHIVE_DIR` at it and re-run check 8 to prove the copy.
3. Don't clear `/var/cache/arlowe-build/pi-archive` or `~/.cache/arlowe-build/pi-archive`.
4. Only then consider a record-mode bump. A bump moves to whatever the pool serves now. That
   isn't a restore of what was pinned.

## 4. Bumping the Pi pins

1. **Destroy the work dir** (§2).
2. **Record build:**
   ```
   ARLOWE_PI_ARCHIVE_MODE=record scripts/build-image.sh
   ```
   It warns first, with `RECORD MODE: Pi packages resolve from the live archive.raspberrypi.com,
   unpinned.` and `The build stops after the Debian gate with exit 3 and produces no image.`

   **Record mode still verifies the currently pinned debs at Step 1**:
   `Record mode: Step 1 verified the currently pinned Pi debs anyway, by design; no flat repo
   is built.`. A gate that a mode flag can skip gets skipped. On a host that has built before,
   the cache is already warm. On a cold host, run §2's fetch first.

   After the Debian gate it prints `=== Pi archive record mode: candidate manifest ===`, then
   `[pi-archive] N packages, 1 resolve_only; skipped: ...`, and then one of two things. Either a
   `diff -u` against `third_party/pi-archive/manifest.yml`, or `[OK] candidate ... is identical
   to the committed manifest; no pin moves.`. It ends with `RECORD MODE: candidate written; no
   image is produced from the live archive.` and **exit 3, which is success**. The candidate is
   `build/pi-archive.manifest.candidate`.

   The candidate is Pi-archive-now crossed with the Debian snapshot currently in the tree. If
   you're bumping the Debian snapshot too (§5), make that edit first, in the same working tree,
   so the candidate is resolved against the new snapshot.

   Record mode has only been proven by fixtures. This is its first end-to-end use. Read a
   surprise as a record-mode defect before you read it as an archive change.
3. **Review the diff** against §5 and §6. Account for every `-`/`+` pair. A name that only
   disappears either left the installed set, or now resolves to Debian's build, which is an
   origin flip. A name that only appears is a new Pi-only package. Any line naming
   `rpi-eeprom`, `raspi-utils-eeprom` or `raspi-firmware` needs explicit sign-off.
4. **Take it and verify the new bytes:**
   ```
   cp build/pi-archive.manifest.candidate third_party/pi-archive/manifest.yml
   ARLOWE_PI_ARCHIVE_FETCH=1 scripts/verify-third-party.sh
   ```
   Fetching hashes the served bytes against the candidate's digests. This isn't ceremony. The
   piper pin in `runtime/tts/manifest.yml` was recorded from a local file, never fetched, and
   matched no upstream artifact.
5. **Pinned build, then the inputs reference.** Destroy the work dir and run
   `scripts/build-image.sh`. It will stop at `=== Build input record (built rootfs) ===` with
   `Build inputs differ from the recorded reference`, because the `pin` and `pkg` rows moved.
   Read the `pkg`-row diff. Every moved row should be explained by the manifest diff you
   reviewed. Then re-record:
   ```
   ARLOWE_INPUTS_ACCEPT=1 scripts/record-build-inputs.sh \
       --diff build/arlowe-inputs.manifest \
       --reference docs/operations/phase-07.2-inputs.reference
   ```
   Destroy the work dir and rebuild for the image. The alternative is to set
   `ARLOWE_INPUTS_ACCEPT=1` on the pinned build itself. It prints the diff before
   re-recording, and you still read it, with `git diff`, before step 6. The flag doesn't replace
   the review.
6. **Commit the manifest and the reference together.** `test-pi-archive-committed.sh` fails on
   a manifest whose rows aren't `pkg` rows of the reference, so committing one without the
   other breaks CI. CI's cache is keyed on the manifest hash, so the first CI run after a bump
   fetches the new debs.
7. **On a `PIGEN_REF` bump, re-run the removal-marker check.** On the build host, with the
   pi-gen tree at the new ref:
   ```
   cat pi-gen/stage[0-9]*/*/[0-9][0-9]-packages* pi-gen/stage-arlowe/*/[0-9][0-9]-packages* \
       | sed 's/#.*//' | tr -s ' \t' '\n\n' | grep -E '.-$' | sed 's/-$//' | sort -u
   ```
   For each name: confirm it isn't installed
   (`grep -P "^pkg\t<name>\t" build/arlowe-inputs.manifest` finds nothing), and confirm it's
   under `resolve_only` in the manifest if only the Pi archive carries it. Today the only marker
   is `firmware-marvell-prestera`. `pi_archive_record_candidate` passes it to the generator by
   name (`--resolve-only firmware-marvell-prestera`). A new marker therefore needs that argument
   list changed, and a record build won't add it for you. Missing it passes the record build
   and then fails the next pinned one with `Unable to locate package`.

## 5. Security

This section is why SC5 exists. Versions below are from the committed manifest.

**glibc, pam, NetworkManager and bluez: Pi's rebuild outranks every Debian update.** These ship
as `+rptN+deb12uM`:

| Package (and its siblings) | Pinned version |
|---|---|
| `libc6`, `libc-bin`, `locales`, `libc6-dev` | `2.36-9+rpt2+deb12u14` |
| `libpam0g`, `libpam-modules`, `libpam-runtime` | `1.5.2-6+rpt2+deb12u2` |
| `network-manager`, `libnm0` | `1.42.4-1+rpt1+deb12u1` |
| `bluez`, `libbluetooth3` | `5.66-1+rpt2+deb12u2` |
| `zlib1g` | `1:1.2.13.dfsg-1+rpt1` |

`rpt` sorts above `deb`, so `2.36-9+rpt2+deb12u14` outranks **every** Debian `2.36-9+deb12uN`.
`dpkg --compare-versions` confirms that `2.36-9+rpt2+deb12u14 gt 2.36-9+deb12u99`, and the
same holds for the pam, NetworkManager, bluez and zlib rows. So a Debian glibc DSA reaches the
image only when Raspberry Pi rebuilds **and** this manifest moves. Advancing the Debian snapshot
alone changes nothing. The pinned Pi build still wins, the check passes, and the
vulnerable libc6 ships **without any failure anywhere**.

**openssl is the opposite.** `openssl` and `libssl3` are `3.0.20-1~deb12u2+rpt1`. The `~` sorts
the Pi build *below* a later Debian `3.0.20-1~deb12u3` or any `3.0.21-*`. After a Debian
snapshot bump that carries one, apt silently installs Debian's openssl. The flat repo is
still present, but it loses. The completeness check's forward direction then fails the build
with `openssl: pinned 3.0.20-1~deb12u2+rpt1 arm64, installed 3.0.20-1~deb12u3 arm64`. A record
build resolves the same way, so its candidate drops both rows. Whether openssl should come from
Debian from then on is a real decision. Make it explicitly.

**So evaluate a Debian snapshot bump and a Pi pin bump together, never one alone.** Do the
snapshot edit (07.2 runbook), then the record build (§4), in one change.

**How to watch:**
- The Debian security tracker and the DSA feed, for glibc, openssl, pam and zlib (plus
  NetworkManager and bluez).
- For Pi rebuilds, `tests/phase-07.3/probe-pi-archive.sh --state`. It prints `inrelease_date`,
  `packages_gz_sha256`, `pinned_moved N`, and one `moved <name> <pinned> <now>` line per pinned
  package that the live index now serves at another version (`absent` if the name is gone). A
  `moved libc6 ...` line means Pi has rebuilt glibc and a bump would pick it up. The probe is
  read-only and fetches no deb. What it downloads is trusted for nothing.

**Plainly: until the owner sets a cadence, the image's libc6 and openssl change only when
someone happens to bump them.** No job bumps them, and no job alerts on a DSA. This is the Pi
half of the 07.2 runbook's open question on snapshot advance policy
(`docs/operations/phase-07.2-build-pinning.md`, "Open questions"). One policy should answer
both.

## 6. rpi-eeprom

The pinned `rpi-eeprom 28.31-1` ships `/etc/default/rpi-eeprom-update` containing
`FIRMWARE_RELEASE_STATUS="default"`. It also ships `rpi-eeprom-update.service`, with
`ExecStart=/usr/bin/rpi-eeprom-update -s -a` and `WantedBy=multi-user.target`. Its Pi 5
`default` image is `/usr/lib/firmware/raspberrypi/bootloader-2712/default/pieeprom-2026-05-26.bin`.
Those contents were read from the pinned deb (sha256 `8982af94…`). Nothing in this repo masks
the service.

- **Pinning bounds which bootloader images exist on the device. It doesn't stop the flash.**
  At every boot, the service writes the package's `default` bootloader to any device whose
  EEPROM is older.
- **A bump EEPROM-flashes every device at its next boot.** That write sits outside A/B
  rollback. Slot B can't undo it, and a bad bootloader is a device that won't reach either
  slot.
- **Any diff that touches `rpi-eeprom` needs explicit sign-off**, as does
  `raspi-utils-eeprom` (the updater tooling) and `raspi-firmware` (the GPU-side bootloader
  files). Read the bootloader release notes for the new `default` image before accepting it.
- **Masking the service is an open product decision.** It could be done with
  `systemctl mask rpi-eeprom-update`, or with the bootloader's `FREEZE_VERSION` config. This
  phase changes neither.

## 7. Retention and mirroring

Check 8 (`scripts/lib/pi-archive-fetch.py`) looks for each deb in this order, first hit wins:

1. `$ARLOWE_PI_ARCHIVE_DIR/<filename>`
2. `third_party/pi-archive/<filename>` (debs are gitignored, never committed)
3. `/var/cache/arlowe-build/pi-archive/<filename>` (`ARLOWE_PI_ARCHIVE_SHARED_CACHE` overrides)
4. `${XDG_CACHE_HOME:-$HOME/.cache}/arlowe-build/pi-archive/<filename>`

With `ARLOWE_PI_ARCHIVE_FETCH=1`, a miss downloads into whichever of 3 and 4 is writable first.
A mirror changes where bytes come from. It never changes the digest.

- **CI cache.** Stored at `~/.cache/arlowe-build/pi-archive` and keyed on the manifest hash.
  GitHub evicts an entry after 7 days unused.
- **Daily retention workflow.** `.github/workflows/pi-archive-retention.yml` runs
  `probe-pi-archive.sh --retention` at 06:17 UTC. It passes with `N/N pinned debs still served at
  their pinned size`. A failure opens the issue in §3. Scheduled workflows run only from the
  default branch, so it's live only once this phase is merged.
- **"Bytes the project controls" holds only in a weak sense until a durable mirror exists.**
  Today the only copies are the build host's cache and a CI cache that can evict itself. If Pi
  prunes a pinned version and both are lost, the pinned image can't be rebuilt. The durable
  mirror is a p1 follow-up. Before publishing one anywhere, read the licence of each
  `firmware-*` package and of `raspi-firmware` (`/usr/share/doc/<package>/copyright`). Their
  terms are narrower than the rest.

## 8. What a shipped device's apt sees

The swap-back replaces the flat repo with pi-gen's stock `raspi.list` (`RELEASE` substituted),
byte-identical to stock Pi OS, plus the Raspberry Pi keyring. The Debian `sources.list` still
names the frozen `snapshot.debian.org` timestamp. So `apt install i2c-tools` works on a device
for debugging, as on stock Pi OS.

**An on-device `apt upgrade` is unsupported.** It mixes the rolling Pi archive with a Debian
side frozen at the image's snapshot. The result is a combination no build produced or
tested. It can also pull a newer `rpi-eeprom` and flash the EEPROM (§6). The update channel is
the A/B image. Slot B is an rsync clone of slot A, so it has the same sources and the same
stance.
